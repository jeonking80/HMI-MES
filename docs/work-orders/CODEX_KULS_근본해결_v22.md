## 1. 왜 이 진단이 필요한가

사용자 판단은 "어제부터 고치고 있는데 전혀 개선이 안 된다. 근본 원인을 모르고 억지로 고치는 것 아니냐"이다. Claude도 같은 결론이다. 증상 단위 수정을 20차 넘게 반복했다. 공개 사이트에서 사람이 쓰는 시스템으로 안정적으로 돌아간 적이 없다.

### 1.2 그 밖에 반복된 문제

- **운영:** 공개 runtime(시뮬레이터·게이트웨이, Codex 기계)이 여러 번 멈췄다. 10-25 09:39Z부터 10-26 09:59Z까지 약 24시간 수집이 없었고, 사이트 전체가 멈춘 것처럼 보였다. 감지·자동 재시작이 없다.
- **화면 안정성:**
  - 상태가 정상↔불명으로 깜빡였다(수정됨).
  - 50초 전송 정지 뒤 느린 따라잡기(CX-38, 미구현).
- **사용성(사용자 지적, 2026-10-25):**
  - "설정 ID 손수 타이핑하는 게 말이 돼?", "되게 수동적이고 자동화 시스템이랑 맞지 않아", "제어를 할 수 있는 기능이 너무 없다"
  - 일부 개선 뒤에도 남은 것:
    - 작업이 끝나면 "원래 실행 기록 조회 → 기록 보관"을 해야 다음 배포가 된다. 안내가 없다.
    - 등록 뒤 입력란이 잠겨 "다른 등록 작성"을 눌러야 한다.
    - 요청마다 원래 ID 추적·확인 단계가 노출된다.
- **결함이 공개 후에야 드러남:** 2026-10-26 Claude 확장 실행에서만 발견된 결함이 6건이다.
  - 첫 품목 등록
  - 정책 플래그 파싱
  - 속도 변경 실행 보관
  - 배포 직후 대기열 후보
  - 대기열 Sealer.Ready 정지
  - 보고서 15초 제한
  - 모두 단위·통합 시험을 통과한 상태였다.
- **검증:** 공개 사이트에서 사람이 등록→운전→정산→보고서를 끝까지 성공한 사례는 실행 2건뿐이다. 8시간·장시간 연속 운전 수락은 미실행이다(사용자가 이전에 제외 지시). Claude 컨테이너에서는 FIFO 1,800건 300초 기준을 main 코드도 통과하지 못한다.
- **규모와 복잡도:** 이관 24개. 작은 기능 하나에도 여러 모듈·이관·권한 배치·문서가 함께 바뀐다.

## 2. 진단 범위 — 영역별로 현재 상태와 근본 원인을 판정한다

각 영역에서 **실측·코드 근거로** 현재 상태를 적고, 원인을 "근본 원인 / 파생 증상"으로 나눈다. 아래의 Claude 가설은 검증 대상이며 결론이 아니다.

### A. 기획서 대비 완성도
- F01~F10, T01~T12, M0~M5의 실제 상태를 표로 낸다. 각 항목을 "구현·검증 근거 있음 / 일부 / 미구현 / 공개 환경 미검증"으로 분류한다.
- `docs/DEVELOPMENT_STATUS.md`와 `ACCEPTANCE_EVIDENCE.md`의 기록 가운데 **실제로 통과로 볼 수 없는 것**(분할 실행, 모의 데이터, 미실행)을 구분한다.
- 남은 범위를 현실적으로 추정한다.

### B. 데이터 모델·보관·용량 (가설: 증거 원칙과 무료 운영 예산의 충돌)
- 1Hz·48태그 원본 전체(약 6.5KB)를 영구 증거로 두고, 중복 판정·시각 판정·알람 판단·보고서가 모두 원본과 capture 단위 행에 기대는 구조가 Neon 무료 0.5GB와 양립하는지 판정한다.
- 원본에 의존하는 기능 전체 목록과, 원본이 지워졌을 때의 영향을 정리한다.
- 공개 DB(읽기만)의 테이블별 크기·행 수·증가율을 실측한다.

### C. 시간·증거 원칙
- 시각 근거(측정 왕복, same-host, UNKNOWN) 체계가 보고서·알람·트렌드에서 실제로 쓸 수 있는 결과를 내는지 판정한다. 예를 들어 시각 근거 없는 구간 하나가 보고서 전체를 덮는 현상이 있다.
- 원칙의 엄격함이 교육용 시스템의 목적에 맞는지, 어디까지 단순화할 수 있는지 판단한다.

### D. 운영 구조
- 공개 runtime을 개인 기계에서 돌리는 구조, 감시·재시작 부재, 게이트웨이 전송 지연(CX-38)을 다룬다.
- 무료 범위에서 가능한 대안을 비교한다(감시 경보, 자동 재시작, 다른 호스팅).

### E. 성능·배포 구조
- Vercel 서버리스 + 폴링 화면 + Neon HTTP 조합의 한계를 정리한다. 보고서 18초, FIFO 복구, 콜드 스타트, 함수 60초 한도를 포함한다.

### F. 사용성·제어·자동화
- 운전자·생산관리자 업무 흐름을 실제 MES/HMI 관행과 비교해 불필요한 단계, 노출이 과한 내부 개념, 빠진 제어·자동화를 정리한다. 내부 개념의 예: 원래 명령 ID 추적, 수집원·스트림 ID, 기록 보관.
- 화면은 Claude 소유이므로 개선안은 요구사항 형태로 낸다. 화면 개선과 서버 변경을 구분한다.

### G. 아키텍처 복잡도
- 모듈 수, 이관 수, 규칙의 중복, 같은 개념의 여러 구현(시각 판정, 중복 판정, 원본 의존 등)을 조사한다.
- 교육용 시연 시스템에 필요한 수준과의 차이, 단순화했을 때 잃는 것과 얻는 것을 정리한다.

### H. 개발·검증 방식
- 증상 단위 지시서 → 단위·통합 시험 통과 → 공개 배포 후 결함 발견이 반복된 원인을 분석한다.
- 앞으로의 검증 기준을 제안한다. 연속 운전 시험, 용량 추세, 원본 만료 이후 보고서, 확장 시나리오(`check-operable-system.py --extended-dir`), 공개 환경 수락을 포함한다.
