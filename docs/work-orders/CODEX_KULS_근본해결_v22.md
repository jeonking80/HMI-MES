- 공개 runtime(시뮬레이터·게이트웨이, Codex 기계)이 여러 번 멈췄다. 10-25 09:39Z부터 10-26 09:59Z까지 약 24시간 수집이 없었고, 그동안 사이트 전체가 정지 상태로 보였다.
- 화면 상태가 정상↔불명으로 깜빡였다(브라우저 시계 비교 → 서버 시계 기준으로 수정).
- 50초 전송 정지와 느린 따라잡기가 있었다(CX-38, 미구현).
- 공개 사이트에서 등록→운전→정산→보고서가 사람 손으로 끝까지 성공한 사례는 실행 2건뿐이고, 장시간 연속 운전 수락은 없다.

## 2. Claude가 보는 근본 원인 가설 (검증 대상이며 결론이 아니다)

1. **증거 원칙과 운영 예산의 충돌.**
   - 설계는 1Hz·48태그 원본 전체(건당 약 6.5KB JSON)를 영구 증거로 두고, 중복 판정·시각 판정·알람 판단·보고서를 모두 원본과 capture 단위 행에 의존한다.
   - 운영은 Neon 무료 0.5GB와 Vercel 서버리스다. 저장량이 capture 수에 비례하는 구조는 어떤 보관 규칙으로도 일정 용량에 수렴하지 않는다.
2. **파생 데이터의 의존 관계가 정의되지 않았다.** 보고서·알람·중복 판정·시각 근거가 원본에 숨은 의존을 갖는다. 그래서 원본 수명을 바꾸면 연쇄로 깨진다. 데이터 수명주기(무엇을 언제 확정·요약하고 무엇을 언제 지우는가)가 처음부터 설계되지 않았다.
3. **검증 방식이 실제 운영을 대표하지 않는다.** 단위·통합 시험과 1분짜리 자동 시나리오만 통과 기준으로 삼았다. 몇 시간 이상 연속 운전, 용량 추세, 원본 만료 후 보고서는 시험하지 않았다.
4. **공개 runtime의 운영 구조가 취약하다.** 개인 기계에서 도는 시뮬레이터·게이트웨이를 감시하지 않고 자동 복구도 하지 않는다.

## 3. 할 일 (1단계: 분석과 설계)

1. **근본 원인 확정.** 위 가설을 코드·이관·공개 DB 실측으로 확인하거나 반박한다.
   - 공개 DB는 읽기만 한다. 테이블별 크기, 행 수, 증가율을 잰다.
   - 원본(`ingest_batches`)에 의존하는 모든 기능을 목록으로 만든다. 예: 보고서 시간 구간, 중복 판정, 시각 근거, 알람 판단, 트렌드, 정산, 감사. 각각 "원본이 지워지면 어떻게 되는가"를 적는다.
2. **데이터 수명주기·용량 예산 설계서** (`docs/architecture/DATA_LIFECYCLE.md`)
   - 테이블(또는 데이터 종류)마다 다음을 적는다:
     - 생성 단위: capture당, 상태 전환당, 실행당, 일당
     - 행 크기
     - 보관 기간
     - 확정 시점
     - 의존하는 기능
     - 1Hz 연속 운전 기준 시간당·일당 증가량
   - **0.5GB 안에서 무기한 운전해도 일정 용량에 수렴함을 계산으로 보인다.** 알람 채널 0개와 1개 이상 모두 포함하고, 목표 정상 상태는 예: 250MB 이하로 둔다.
   - capture 수에 비례해 영구히 남는 데이터는 0을 목표로 한다. 남겨야 한다면 이유와 한계 일수를 적는다.
3. **재설계 대안 2~3개를 비교한다.** 각 대안마다 바뀌는 기준 문서, 약해지는 보장, 이관 위험, 작업량을 적는다. 검토할 방향:
   - 원본은 짧은 운영 버퍼로만 두고, 정산할 때 실행별 확정 요약(상태 구간·정지 사유·UNKNOWN 구간과 사유·근거 해시)을 영구 저장한다. 보고서는 요약만 읽는다.
   - 1초 저장을 "값이 바뀔 때만 기록"과 분 집계로 바꾼다. 원본 JSON 전체 저장을 줄인다.
   - 중복 판정을 영구 ID 목록 대신 (gateway, generation, 단조 증가 capture_seq) 경계로 한다. 게이트웨이 batch_id를 결정적으로 만드는 방안을 포함한다.
   - 알람 판단 기록을 capture마다 쓰지 않고 상태 변화와 알람 사건 위주로 기록한다.
   - 시각 근거가 없는 옛 데이터를 이관 시점에 명시적으로 봉인(실행 경계 밖, UNKNOWN 확정)해서 새 보고서에 영향을 주지 않게 한다.
4. **AGENTS.md 불변 조건과의 관계.** 각 대안이 아래를 어떻게 지키는지 적는다. 기준을 완화해야 한다면 어떤 문장을 어떻게 바꾸고 영향이 무엇인지 적는다. 조용히 완화하지 않는다.
   - 불명을 정상으로 대체하지 않는다.
   - 생산 사건을 원래 execution_id에 귀속한다.
   - 결과 불명이면 재실행하지 않는다.
   - 원자적으로 저장한다.
5. **공개 runtime 운영 구조.** 멈춤 감지(예: 마지막 수집 시각 경보)와 자동 재시작 방법을 제안하고, 무료 범위에서 가능한지 적는다.
6. **수락 기준 제안.** "공개 환경 24시간 연속 운전 + 실행 여러 건 + 원본 만료 이후 보고서 정상 + DB 용량 수렴 + runtime 멈춤 감지"를 측정 가능한 항목으로 정의한다.
7. **단계별 구현 계획.** 이관 순서, 기존 공개 데이터 처리(보존·봉인·삭제), 되돌리기 방법, 예상 작업 차수를 적는다.
