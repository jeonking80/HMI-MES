# CX-36 — 명시적 라인 대기열과 다음 LOAD 연결

## 동작

라인별 정책은 기본 비활성이고 기존 배포 작업을 자동으로 넣지 않는다. 사람이 배포·미연결 작업을 순서대로 선택하고 auto_advance를 켠다. 정책은 사람과 line/gateway/source/stream/generation에 묶이며 실행 시 실제 계정 활성·현재 production_manage/load_job 권한을 다시 확인한다.

인증된 gateway claim이 한 번의 자동 연결 트랜잭션을 커밋한 뒤 기존 명령 claim을 수행한다. 이전 원래 관리 실행 SETTLED, 최신 완전 수집, 동일 물리 실행, REMOTE/AUTO, STOPPED·재공0·정지 출력과 안전 조건이 필요하다. PENDING은 기다리며 다른 실패/불명은 차단하고 사람에게 넘긴다. 새 ID로 자동 재시도하거나 잘못된 선두를 건너뛰지 않는다. 기존 bind_work_order→등록/예약/enqueue→gateway/PLC 경로를 그대로 사용한다. start_when_ready=false이므로 자동 START가 아니다.

각 항목은 고정 entry/LOAD ID와 원래 binding receipt를 갖는다. 같은 요청 키/actor/content는 원래 큐 변경 응답을 반환한다. 순서 변경·승인·연결·차단은 불변 감사에 남긴다. 명시적으로 큐에 넣은 첫 작업을 사람이 연결했다면 원래 성공 LOAD 증거를 확인한 뒤 그 연결을 기록한다.

## DB와 계약

0020_line_queue는 정책/항목/불변 변경 영수증/감사를 추가한다. 항목의 등록 identity와 BOUND 영수증도 SQL trigger로 보호한다. 최소 runtime grants와 정확한0019→0020 HTTP batch/renderer를 준비했다. 기존19 이하 기능 gates를 유지하면서20을 추가하고, 이전 dispatch schema에서는 큐가 no-op이다. 사용된 근거가 있으면 downgrade를 거절한다. 공개 적용은 하지 않았다.

GET/PUT /api/v1/lines/{line_id}/queue는 기존 read 또는 production_manage+session/Origin/CSRF를 요구한다. LINE_QUEUE.md에 명시적 정책·순서·이력과 API를 기록했다. UI/공개 적용은 Claude 담당이다.

## 검증

검증 결과는 아래에 기록한다. 6.1-sol medium 구현/시험과 high 읽기 전용 DB·제어 검토로 분담했다. high 검토에서 사용자→큐 잠금 순서, 이전 schema no-op, 최대 버전 차단 저장, SQL LIMIT1 조회와 immutable identity/receipt를 확인했고 남은 차단 사항은 없다.

운영 runtime·WO-T1·공개 DB·UI·생산 조작·재배포는 수행하지 않았다.
