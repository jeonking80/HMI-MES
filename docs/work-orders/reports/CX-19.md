# CX-19 — 실제 30분 API 단절·5분 회복 실행기

현재 판정: **실제 CX19 통과(PASSED, run5)**. 고정 소스 `fc6296e`에서 실제 **1,800.401859초** API TCP 단절 후 startup을 포함해 **208.339389초** 만에 적체·원래 사건·커서·gap·최신48태그/화면을 회복했고 원래 execution의 PAUSE/END_RUN/SETTLED·세 수량 대조까지 통과했다. 과거 run3/run4 실패는 그대로 보존한다. 30분 한도로 잃은 **240개 태그 관측**은 손실이며, 원래 사건5–12의 재조회 복구와 구분한다. 이 결과가 SSD 하드웨어 근거·8시간 시험·프로젝트 전체 완료를 뜻하지 않는다.

## 실행과 사전 고정 기준

```sh
.venv/bin/python scripts/run-outage-acceptance.py --artifacts /tmp/cx19-real-outage
```

사전 빌드한 polling 웹, Chromium/Playwright, Docker PostgreSQL fixture를 사용한다. 공개 DB·공개 배포는 사용하지 않는다. 주 에이전트의 독점 실행 슬롯에서만 실제 실행한다.

- 기존 실제 CLI driver가 별도 PG/API/시뮬레이터/gateway와 암호화 OPC UA, 브라우저 작업지시·LOAD·START를 준비한다. 기본 100ms 공정은 변경하지 않는다.
- 일회성 내부 API 프로세스만 종료하고 새 TCP 연결이 ConnectionRefused임을 확인한 시점부터 실제 1,800초 이상 연결을 끊는다. 시뮬레이터·OPC·gateway 수집은 계속 돌린다. 관측기는 예상된 API 종료만 허용하며 다른 CLI 종료는 실패다. finally에서 원래 args/env·동일 token·동일 PG·동일 log handle로 API를 재실행하고 driver의 children 목록을 교체하여 정리/감독에 포함한다. args/env 값은 출력하지 않는다.
- 48태그·1Hz 수집을 사용한다. 30분 동안 캡처 증가 최소 1,780회(1Hz 스케줄링 여유 20회), 최신 48태그 fresh/DOM usable을 확인한다. 원래 사건을 저장한 시뮬레이터 SQLite와 API inbox의 event_id/전체 body/적용 여부를 대조한다.
- 기본 30분/100,000,000바이트 예산을 그대로 사용한다. 5초마다 큐 바이트와 oldest age를 기록한다. 오래된 payload가 1,802초를 넘으면 실패한다(1Hz 수집 처리 여유 2초). 물리 SQLite/WAL 파일 크기와 payload 회계 크기는 구분한다. 먼저 바이트 한도에 닿았을 때의 손실 기록은 `resources.jsonl`과 최종 JSON에 남긴다.
- 동일 API 재실행 직전부터 실제 300초 안에 pending/inflight 각각 ≤1(계속 수집하는 최신 배치 허용), 원래 사건 반영·연속 커서 ≥재연결 직전 source head·미해결 gap 0·최신 48태그와 화면 회복을 모두 확인한다. API 시작 시간도 300초 budget에 포함한다. source history 원본과 inbox·cursor·gap은 `reconciliation.json`에 저장한다. gateway eviction으로 생긴 샘플 손실을 사건 재조회로 복구했다고 주장하지 않는다.
- hook 종료 후 기존 driver의 PAUSE/END_RUN과 원래 execution 최종 수량/정산 대조까지 성공해야 전체 실행이 성공한다.

## 재사용 방식과 산출물

Claude 소유 `scripts/check-operable-system.py`는 읽기 전용으로 불러온다. 메모리 AST에 RUNNING 시점 callback 하나를 삽입하며 원본 파일을 변경하지 않는다. 고정 anchor가 각각 정확히 한 번 일치하지 않으면 서비스 실행 전에 실패한다. 실제 driver SHA256 및 확장 목록을 수락 JSON에 남긴다. 장시간 생산을 유지할 작업지시 target 20→4,294,967,295, gateway poll .25→1초, 일회성 로컬 service token 1→12시간 만료로 확장한다. 같은 커널에서 실제 구동하는 로컬 stack에 지원되는 `--trend-clock-policy same-host`를 명시한다. 가속 시계·tick/공정 치수 변경은 없다. 단절 중 내부 API를 거치지 않는 실제 operator `/auth/me`와 시뮬레이터 snapshot 조회로 기본 30분 idle timeout을 정상 갱신한다. `tests/e2e/long_run_runtime.py`가 공통 구현이며 `scripts/run-outage-acceptance.py`가 진입점이다.

## 현재 검증

### 실제 재시도 전 실행기 기준 수정(08:47 UTC)

첫 실제 운전 `/tmp/hmi-v3-cx19-real-1`은 08:38:06 UTC TCP 단절을 시작했으나 약 61초 후 read-only 시뮬레이터 snapshot keepalive의 `APIRequestContext.get: read ECONNRESET`으로 실패했다. 초기 RECOVERY_REQUIRED 이외 시뮬레이터 fatal exit가 없고 48태그 수집·생산 tick은 유지된 원본 로그를 확인했다. 5초 keepalive 경계의 HTTP 연결 재사용 문제를 피하도록 `Connection: close`와 ECONNRESET에 한정한 최대 2회 읽기 재시도를 적용했다. 감독 중인 프로세스 생존을 먼저 확인하고 실제 snapshot run_output=true도 확인하며 쓰기는 재시도하지 않는다. 실패 JSON/JUnit의 request credential header를 redaction했고 새로운 오류/로그도 자동 redaction한다. 이전 실패를 성공으로 바꾸지 않는다.

두 번째 실제 운전 `/tmp/hmi-v3-cx19-real-2`는 08:41:57.560321 UTC 새 단절을 시작했고 08:46:44 UTC 마지막 기록까지 source 470사건/tick3,087/capture325·큐 age287.14초·손실0이었다. 이 운전은 **주 에이전트 지시로 SIGINT 중단(exit130)**했다. 원래 요구는 기본 100ms 공정 설정 보존인데 실행기가 임의로 `30분 동안 process tick ≥17,800`이라는 추가 hard threshold를 넣은 오류를 발견했기 때문이다. 실제 wall-clock scheduling·SQLite/OPC 비용이 포함된 tick 진행률을 정확히 10Hz에 가깝게 강제하는 것은 사용자가 지정한 기본 100ms 설정과 다른 추가 기준이며, 이 조건이 30분 뒤 회복 측정을 통째로 생략하게 만드는 것도 부적절하다. **세 번째 실행 전에** 이 추가 조건을 제거하고 기본 CLI 0.1초 ticker 소스/해시 보존, 실제 tick 증가·run_output=true·원래 생산 사건 대조와 tick 추세 기록으로 수정한다. 원래 48태그/1Hz, 실제 1,800초 단절, 30분/100MB 한도, 실제 300초 회복 기준은 변경하지 않는다. 두 단축 실행은 실패/중단이며 세 번째 1,800초에 합산하지 않는다.

`.venv/bin/python -m pytest tests/unit/test_long_run_acceptance.py -q`: **7 passed**(0.17초). 빈/비정상 지연 자료 거절, driver 원본 불변, 단절 중 관측 실패 또는 포트 미폐쇄 실패 시 동일 API args/env/log handle 재시작과 driver child 교체 보장, CX21 하드웨어 미증명 조기 차단, transport 오류의 credential header redaction, 최종 await 이후 300초를 넘긴 회복의 성공 판정 거절을 검증했다. Ruff 검사·포맷 통과. 수정 도중 mock 적용 시점이 evidence의 Git subprocess 생성까지 가려 2개 단위 시험이 실패한 원문을 확인했고 mock 적용 전에 evidence를 생성하도록 수정했다. 단위 통과와 아래 실제 복구 실패를 구분한다. high 검토 대상은 아니다.

원인은 수치와 코드에서 확인할 수 있다. 30분 경계 eviction이 첫 source event hole을 만든 뒤 `GatewayPump.capture_once`가 recoverable gap의 시작부터 최대1,000개 사건을 조회한다. 아직 API ACK가 해당 hole을 닫지 못한 동안 매 1Hz 캡처가 같은 범위의 큰 재전송 payload를 기존 FIFO 적체 뒤에 추가한다. 원래 약28MB였던 큐는 복구 중 증가하여 100MB에 먼저 닿았고 새 eviction과 추가 누락을 만들었다. 300초 내 최신 상태까지 도달하지 못한 실제 실패다. 주 에이전트가 최소 제품 수정·집중 검증 뒤 **새로운 실제 1,800초** 실행을 조정하며 이 실패 시간을 합산하지 않는다. 실행 호스트의 SSD 근거는 CX21처럼 미확정이며 이 결과를 4코어·8GB·SSD 전체 기준 충족 성능으로 주장하지 않는다.

다음 실제 재실행 전 실행기의 300초 경계도 명확히 보강했다. while 진입 때 300초 이하여도 HTTP/DB/DOM await 뒤에는 넘을 수 있으므로 성공 직전에 별도 monotonic 실측과 `≤300초` assertion을 둔다. 실패 시 driver가 PG/SQLite를 정리하기 전에 **이미 보유한 Observer.engine와 원래 source/queue 경로만** 사용하여 원본 사건·inbox·커서·gap 및 gateway ACK의 대조 snapshot을 남기고 engine을 정리한다. 원래 5분 기준을 느슨하게 하지 않는다. run3의 보존 자료를 이 새 snapshot 코드로 소급 생성한 것처럼 기록하지 않는다.

## 제품 수정 후 실제 run4 — 큐 폭증은 해소, 전체 회복은 실패

`GatewayPump.capture_once`의 recoverable gap 재조회 한도를 `min(1000, through_seq-from_seq+1)`로 제한했다. 일반 새 사건 조회 한도1,000은 유지한다. 작은 hole에 관계없는 후속 사건까지 매초 재포함하던 문제만 줄이는 변경이다. 주 에이전트가 조정한 실제 PG/암호화 OPC 집중 검증은2개(47.80초), 관련 회귀58개(32.58초) 통과였다. 이 검증은 1,800개 적체 **전체를 300초 내 소진하는 처리량**을 입증한 시험은 아니었다.

새 실제 명령은 `.venv/bin/python scripts/run-outage-acceptance.py --web-dir /tmp/hmi-v3-polling-web --artifacts /tmp/hmi-v3-cx19-real-4`였다. 대상 `e571358af84f79ee33e603f214235349b23ffb4a`, dirty=false. 이전 실행 시간을 합산하지 않았다. 측정 중 실행 소스와 기준을 변경하지 않았다.

## 원인 수정 집중 회귀 이력

`GatewayPump.capture_once()`가 작은 recoverable gap에도 항상 ReadEvents limit=1000을 요청하여, FIFO 뒤의 복구 batch가 ACK될 때까지 이미 수신한 인접 사건을 매초 다시 큐에 넣었다. `limit=min(1000, through_seq-from_seq+1)`로 **API가 보고한 첫 누락 구간의 크기만큼** 요청하도록 한정했다. 원래 source/stream·event ID·본문/digest·ACK·커서·48태그·큐 한도는 변경하지 않는다. 추가적인 큐 우선순위/중복 억제 기능은 넣지 않았다.

- 수정 전 실제 OPC/HTTP/PG 회귀: 누락2건에10건이 반환되어 **1 failed / 44.39초**, `/tmp/hmi-v3-gap-bounds-old-worker.xml`. 이는 실패 재현 근거다. 최초 fixture 속성명 오류는 별도 `/tmp/hmi-v3-gap-bounds-baseline.xml`로 보존한다.
- 수정 후 동일 회귀 **2 passed / 47.80초**, `/tmp/hmi-v3-gap-bounds-fixed.xml`. 48태그1,800개 대기 캡처 위의 작은 gap2를3번 재조회하여 매번2건만 받고 추가 큐47,588bytes; 큰 gap1,200은 매번1,000건 상한 유지. 원래 사건 JSON/digest/ACK·커서도 대조했다.
- 관련 실제 network pipeline·buffer·measured clock **58 passed / 32.58초**, `/tmp/hmi-v3-gap-bounds-regression.xml`.
- 실행기도 성공 직전 HTTP/DB/DOM await가 끝난 시점의 elapsed≤300을 명시적으로 확인한다. 이 검증의301초 거절을 포함한 단위7개 통과. 앞으로 실패할 경우 기존 Observer.engine으로 원본/PG/cursor/gap을 정리 전에 저장하며, 프로세스 환경에서 자격 증명을 찾지 않는다.

이 집중 회귀는 실제30분/5분 수락의 대체가 아니다. 이후 수정된 코드에서 run4를 처음부터 실행했으나 위와 같이 실패했다. 사용자 마무리 지시에 따라 추가 실행은 하지 않는다.
