# CX-16 조회 성능 결과

## 범위와 판정

구현 커밋: `c8a24c1` (`codex/kuls-backend-v2`). 측정 산출물의 4개 소스 SHA-256이 이 커밋의 현재 파일과 모두 같음을 루트가 확인했다.

최신 main 병합 후의 보고·대시보드 조회를 로컬 일회용 PostgreSQL 17에서 측정하고 반복 작업을 줄였다. 최종 측정의 서비스 중앙값은 일일 보고 **2.599 → 0.712초**, 대시보드 **4.156 → 0.672초**다. 인증된 ASGI HTTP 요청도 변경 전후 모두 200이며 JSON 구조와 값이 정확히 같았다. 공개 Neon·Vercel에는 접속하거나 변경하지 않았다. 공개 5.2초/2.7초가 개선되었다는 운영 검증은 아니다.

목표는 이 로컬 3,800배치 표본에서 조회 1초 이하로 정했다. 최종 서비스 중앙값과 각각 한 번 측정한 HTTP는 목표 안에 들어왔다. 다만 앞선 중간 실행의 일일 중앙값은 **1.050초**였으므로 1초를 항상 보장하거나 p95 목표를 충족했다고 판정하지 않는다. 추가 반복으로 유리한 표본을 고르는 최적화는 하지 않았다. 최종 추가 실행의 목적은 WITH 질의 계획과 실제 HTTP 동등성 기록이었다.

## 변경

- 보고서의 배치마다 수행하던 알람 결정 조회를 현재 라인/소스/스트림의 단일 집계로 바꾸었다. 보고서가 실제 읽는 `clock_assessment`만 반환한다. 시각 증거의 검증 조건은 그대로다.
- durable clock evidence가 없는 과거 배치만 보고 태그 세 개(`Line.State`, `Line.ActiveExecutionId`, `Line.FaultCode`)와 원래 첫 표본을 원순서로 반환한다. 첫 표본을 남겨 디지털 전용 등 비어 있지 않은 배치를 표본 없는 통신 장애로 바꾸지 않는다. durable evidence가 있는 배치는 GOOD/UNKNOWN/잘못된 바인딩 여부와 관계없이 **전체 원본 body**로 기존 digest 검증을 수행한다. 원본 저장값은 수정하지 않는다.
- 대시보드는 기존 Line 공유 잠금 안에서 snapshot의 선택적 빠른 경로를 사용한다. 현재 gateway/generation의 최신 비어 있지 않은 표본 배치가 모든 enabled 태그를 중복 없이 포함할 때만 그 배치를 태그순으로 반환한다. 부분·디지털 전용·부재 배치는 기존 전체 이력 `DISTINCT ON`으로 돌아간다. 사건 전용 배치는 최신 표본 배치를 대체하지 않는다. 표본 메타데이터는 원래 테이블 열을 사용한다.
- snapshot의 기본 호출은 기존 경로다. 제어·freshness·heartbeat·BAD 품질·소유 판정, API 필드, 권한, 마이그레이션/인덱스는 변경하지 않았다. 역행 전체 이력, durable cutoff 동시성 overlay, receipt fence와 invalidated canonical UNKNOWN barrier도 유지한다.

## 재현 표본과 방법

실행 스크립트는 `/tmp/cx16_bench_http.py`, 산출물은 `/tmp/cx16-query-evidence/`다. 생성된 비밀번호를 사용하는 테스트 fixture의 로컬 전용 PostgreSQL 17 컨테이너를 사용했고 종료 시 해당 컨테이너와 볼륨만 제거했다. Docker build/prune 및 운영·공개·사용자 runtime 접근은 하지 않았다.

기존 실제 보고 fixture로 소스·실행·규칙을 등록하고 정상 배치 하나를 수집한 뒤, SQLAlchemy bulk insert로 나머지 배치와 과거 알람 증거를 복제한 **조회 계획용 합성 표본**이다. 3,800배치·48태그·182,400표본·3,800알람 결정 행을 실제 count로 확인했다. capture 순서는 1Hz이며 첫 표본부터 마지막까지 3,799초, 표본당 1초 범위로 약 **63분 20초**다. 24시간 86,400배치의 대표 표본이 아니다. 별도 24시간 용량·부하 시험은 미실행이다.

DB는 schema18이며 첫 실제 배치에 durable GOOD proof가 있고 나머지 3,799행은 durable evidence 도입 전의 legacy fallback 형태다. 공개 과거 데이터 형태의 비용을 측정하는 목적이며, 3,800개 모두 canonical18 proof인 부하를 재현했다고 주장하지 않는다. canonical18 GOOD/UNKNOWN·측정 오프셋·digest·역행 처리는 기존 실제 PG 회귀 시험으로 검증했다.

동일 DB에서 변경 전 모듈 복사본과 변경 후 모듈을 고정 now로 호출했다. 각 서비스 3회, 인증된 ASGI HTTP 각 1회를 측정했다. 서비스와 두 HTTP 응답의 전체 dict/JSON을 `before == after`로 비교했다. 기본 fixture에는 생산 사건이 없으며 해당 생산 수량은 0이다. 비영 수량·정산·UInt64 문자열·범위 격리는 별도의 기존 회귀 시험에서 검증했다. DB를 ANALYZE한 뒤의 warm-cache 측정이고 모든 계획의 주요 shared read blocks는 0이다. 네트워크 왕복·Neon suspension/cold start·Vercel CPU/직렬화·실제 다중 요청 성능은 포함하지 않는다.

## EXPLAIN ANALYZE

실제 실행된 SELECT/WITH SQL을 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`으로 다시 실행했다. 원본 SQL 및 전체 노드 계획은 `before-plans.json`, `after-plans.json`에 있다. 아래는 같은 daily 요청의 대응 계획이다. PostgreSQL execution time은 Python 파싱과 응답 직렬화 시간을 포함하지 않는다.

| 질의/노드 | 변경 전 | 변경 후 |
|---|---:|---:|
| 보고 evidence SQL 전체 실행 시간 | 1,128.455ms | 334.548ms |
| 보고 최상위 actual rows / loops | 3,800 / 1 | 3,800 / 1 |
| 보고 shared hit blocks | 437,290 | 115,235 |
| 보고 temp read / written blocks | 668 / 669 | 919 / 920 |
| 알람 결정 조회 | Index Scan, rows 1 × loops 3,800 | Seq Scan, rows 3,800 × loops 1 |
| 알람 결정 노드 shared hit blocks | 345,800 | 950 |
| snapshot 전체 태그 DISTINCT SQL | 1,552.860ms | 완전한 최신 배치 경로에서 실행하지 않음 |
| snapshot 펼친 표본 / 결과 | 182,400 / 48 | 최신 배치 48 / 48 |
| 기존 snapshot shared hit blocks | 558,894 | 해당 전체 이력 질의 없음 |
| 역행 전체 이력 SQL | 137.860ms | 132.606ms |
| 역행 결과 actual rows / loops | 0 / 1 | 0 / 1 |

집계 결과 정렬의 임시 블록은 오히려 증가했다. 공유 버퍼 접근과 수행 시간 감소를 모든 자원 사용 감소로 해석하지 않는다.

일일 보고의 주 병목은 3,800번의 상관 조회와 사용하지 않는 48태그 body 전송/파싱이었고, 대시보드에는 182,400표본 정렬이 추가됐다. 역행 검사는 약 0.13초였으며 안전성을 유지하려고 전체 이력 검사를 축소하지 않았다. legacy context 집계와 역행 검사는 여전히 범위 내 보관 이력 규모에 비례한다. 인덱스 추가나 감사 근거 삭제 없이 위 비용만 줄였다.

## 검증 명령과 실패 기록

- `.venv/bin/python /tmp/cx16_bench_http.py`: **PASS**, 3,800개 실제 DB 행, 변경 전후 계획/BUFFERS/3회 시간/실제 인증 HTTP JSON 동등성. 총 스크립트 wall-clock 시간은 별도로 기록하지 않았고 위 질의/요청별 시간만 기록했다. 로그 `benchmark-http.log`, 세부 시간 `before-timings.json`, `after-timings.json`.
- `.venv/bin/pytest -q tests/integration/test_analytics_query_performance.py tests/integration/test_reports.py tests/integration/test_reports_receipt_fence.py tests/integration/test_dashboard.py tests/integration/test_analytics_clock_consumers.py tests/integration/test_analytics_merge_business.py tests/integration/test_snapshot.py`: 최초 **49 passed / 2 failed, 74.36초**. 기존 44개는 모두 통과했고 신규 fixture 2개만 실패했다. 로그 `regressions.log`.
- 실패 원문: `Value error, empty batches are not ingest operations`; `ForeignKeyViolation: update or delete on table "source_streams" violates foreign key constraint "alarm_capture_frontiers_source_id_stream_id_gateway_id_cap_fkey"`. 신규 fixture를 실제 생산 사건이 있는 event-only 배치와 원본 digest가 일치하는 다른 generation 행으로 수정했다. 제품 기대값을 완화하지 않았다.
- `.venv/bin/pytest -q tests/integration/test_analytics_query_performance.py`: 수정 후 **7 passed, 12.75초**. 전체/부분/디지털/event-only/BAD+stale/다른 generation의 fast/default snapshot 값 동등성과 legacy 비어 있지 않은 표본 구분을 확인했다. 로그 `new-regressions.log`. 앞선 기존 44개 통과와 합쳐 이 범위 51개가 통과했다. 두 실행을 전체 동시 51 passed로 표기하지 않는다.
- `.venv/bin/ruff check apps/api/reports.py apps/api/dashboard.py apps/api/snapshot.py tests/integration/test_analytics_query_performance.py`: **PASS**.
- `.venv/bin/ruff format --check`에 같은 4개 파일: **PASS**.
- 최초 benchmark seed는 `alarm_capture_decisions_channel_id_assigned_position_key` 중복으로 실패했다. 실제 초기 frontier 위치를 기준으로 복제하도록 고친 뒤 새 일회용 DB에서 실행했다. 초기 실패를 성능 통과 표본에 포함하지 않았다.

별도 high 신규 마이그레이션 검토 대상은 없으며 루트가 SQL/전체 body digest 보존/표본 존재와 snapshot 메타데이터 바인딩을 검토했다. 공개 배포의 read-only 실측, cold-cache/네트워크/p95, 24시간 규모 및 전체 check-local 결과는 이 보고서의 통과 범위에 포함하지 않는다. 전체 검증은 루트가 단독 PG 창에서 이어간다.
