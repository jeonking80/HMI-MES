# CX-29 — 종료 후 재시작 정산: 설계 검토 후 중단

- 기준: main `a213e28`, 11차 지시서 `58b2225`의 `docs/work-orders/CODEX_KULS_보강_v11.md`.
- 판정: **차단·미구현**. API bind 접수만을 실제 다음 작업 연결 성공으로 표시하지 않는다.
- 검토: `gpt-6.1-sol high`가 정산·사건 귀속 및 원격 정산 신뢰 경계를 읽기 전용으로 검토했다. 시험 준비는 medium에 분리했으며 중단 결정 뒤 준비 변경을 모두 취소했다.

## 원인과 확인 범위

지시서에 기록된 공개 사건 820·821은 종료된 실행의 복구 상태 전이이며, API `_reconcile`은 최종 경계 뒤 원래 실행 사건을 종류 구분 없이 `EVENT_AFTER_FINAL_BOUNDARY`로 판단한다. 수량이 같아도 다음 bind 트랜잭션이 재정산 후 거절될 수 있다. 공개 DB의 해당 행을 이번 작업에서 다시 직접 조회하거나 수정하지 않았다. 공개 현상과 순번은 Claude의 11차 지시서 근거다.

현재 코드와 문서를 추가 확인한 결과 API 이후에도 독립적인 차단이 있다.

- `apps/simulator/controller.py`, `_remote_settlement_final`: `final.last_event_seq != self._head()`이면 원격 정산 근거를 인정하지 않는다.
- 같은 controller의 원격 admission 및 실행 tick 재검증이 이 근거를 사용한다. API의 bind 접수 성공만으로 PLC의 LOAD_JOB 성공을 보장하지 않는다.
- `docs/architecture/REMOTE_SETTLEMENT_ATTESTATION.md`는 최종 순번과 현재 source head의 일치 및 후속 상태 사건에 의한 attestation 무효화를 명시한다.

## 설계 결정과 중단 이유

API 측에서는 (나)가 기존 사건을 유지하면서 공개 데이터도 처리할 수 있는 최소 방향이다. (가)처럼 앞으로의 ENDED 사건 귀속만 바꾸어서는 이미 저장된 820·821을 해결할 수 없다. 사건 삭제·다른 실행으로 이동·최종 요약 경계 갱신·실행별 정산 우회는 채택하지 않는다.

(나)의 보수적 구현 후보는 적용 완료(`applied_at` 존재)된 원본 전체 `StateEvent`를 계약으로 엄격 검증하고, RUNNING으로 들어가는 전이가 아닌 명시적 상태 사건만 최종 경계 이후 허용하는 것이다. 생산·불량·폐기·기타 사건·미적용/격리·잘못된 payload는 계속 불일치여야 한다. RUNNING에서 빠져나오는 전이까지 허용할지는 다음 설계에서 명시적으로 정해야 한다. 기존 누락·격리·verified 커서·미확정 명령·epoch·설정·수량 검사는 유지해야 한다.

이 API 변경 자체는 주요 기획서·개발계획서·계약과 충돌하지 않는다. `SETTLEMENT.md`의 기존 모든 사건 차단 설명은 지시서가 검토를 허용한 영역이다. **중단 근거는 별도의 원격 attestation 불변 조건**이다. 이를 그대로 두면 API 409를 제거한 뒤에도 PLC에서 실제 다음 작업이 거절된다.

11차의 “기준 문서를 바꿔야 하면 멈추고 보고한다”에서 원격 attestation 신뢰 설계 문서도 기준에 해당한다고 해석했다. 주요 기획서가 반드시 충돌한다는 뜻은 아니다. API만 바꾸어 부분 성공을 완료로 푸시하지 않고, 별도 PLC 신뢰 규칙 변경 전에 중단한다.

후속 설계에는 최종 경계 뒤 원본 상태 사건 구간의 연속성·허용 전이·수량 불변·현재 물리 정지·미결 명령 없음 검증, admission 때 승인한 정확한 후속 구간의 근거 고정, 실행 tick에서 그 근거가 바뀌면 거절하는 규칙이 필요하다. 단순히 `final.last_event_seq == head` 검사를 제거하거나 과거 attestation을 재사용하면 안 된다. 이 내용은 제안이며 구현·승인 완료가 아니다.

## 변경·검증·운영 상태

- 변경: 이 보고서와 개발 상태 한 줄만 작성. 제품 코드·시험·설계 기준 문서는 변경하지 않음.
- 정산 및 실행 연결 회귀 시험: 미실행.
- 전체 단위 시험·Ruff·포맷 검사: 미실행. 설계 차단 전에 불완전한 제품 변경을 검사 통과로 표시하지 않음.
- 공개 DB 수정/삭제·새 source/generation·SQLite 초기화·배포·새 실연: 수행하지 않음.
- 기존 사용자 운전 runtime: 중지·재시작·commission·생산 조작하지 않음. 사용자 종료 지시까지 유지한다는 앞선 요청을 유지함.
- UI 부수 현상: 409 이후 충돌/원래 ID 조회가 사용자에게 로딩처럼 보였다는 지시서 관찰을 인계하며 UI는 수정하지 않음.

## 12차 구현 — 승인된 정산·PLC 복구 꼬리 규칙

12차 지시서와 사용자가 두 설계 문서 변경을 명시적으로 승인해 앞 절의 설계 차단을 해소했다.
기준 main은 `edde46c`이며 PR·배포·공개 확인은 Claude 담당이다.

### 변경 내용과 high 검토

- API: 원래 최종 순번 뒤 현재 same-source/stream 사건 구간 전체를 검사한다. 전체 StateEvent 계약·행/본문 식별·적용 완료·연속 순번·verified/latest 일치·후속 gap 없음·마지막 STOPPED를 확인한다. 두 전이 끝점은 모두 STOPPED 또는 RECOVERY_REQUIRED만 허용한다. 생산·다른 사건·RUNNING·미완 복구·누락·격리·잘못된 본문은 불일치다.
- PLC: 동일한 전체 꼬리의 계약·식별·연속성·상태를 확인하며 누락·보관 삭제 구간도 허용하지 않는다. 원래 final 경계/해시와 별도로 접수 audit에 `tail_end_seq`, 정규화된 순서 있는 전체 StateEvent 배열의 `tail_sha256`을 고정한다. 실행 tick은 head/hash가 모두 같은지 다시 검사하고, 변동·과거 audit의 pin 누락 시 기존 실패/무효화 경로로 거절한다.
- 기존 재공·출력·피드백·속도·recovery·conflict·미결 명령·수량·epoch·설정 검사와 최종 요약 불변 규칙을 유지했다. 사건 삭제·귀속 이동·최종 경계 변경·새 마이그레이션은 없다.
- gpt-6.1-sol high의 최종 읽기 전용 검토에서 남은 차단 문제 없음. API와 시험 구현은 medium, PLC와 문서·통합 검증은 주 에이전트가 맡았다.

### 문서 변경 이유와 영향

`SETTLEMENT.md`, `REMOTE_SETTLEMENT_ATTESTATION.md`에 승인된 정확한 꼬리 조건과 head/hash 고정, 변경 이유 및 영향을 기록했다. 재시작 복구의 비수량 상태 사건은 허용하지만 접수 이후의 추가 사건은 허용 가능한 복구 사건이더라도 기존 admission을 무효화한다. 과거 audit을 자동 승격하거나 자동 재시도하지 않는다.

12차의 전체 stream 조건을 그대로 적용하므로 이후 다른 실행의 정상 생산 사건이 생긴 뒤 과거 실행을 재정산하면 그 과거 실행의 현재 판정도 MISMATCH가 될 수 있다. 이를 넓은 예외로 바꾸지 않았고 해당 회귀 시험과 두 문서에 명시했다. 원래 최종 요약·수량·생산 귀속은 보존된다.
