## 고정한 기준과 실행기

`scripts/benchmark-history.py`는 기본 9개 아날로그 ×604,800초=5,443,200개 원시 행, 90,720개 분 집계 행을 생성한다. 축소 자료로 목표를 대신하지 않는다. 0018 실제 PostgreSQL 스키마·인덱스를 그대로 쓰고 SQL `generate_series`를 시간 단위로 커밋하여 Python 수백만 객체·파일 복사를 피한다. backup/restore에서 검토한 `deploy.backup_set.local_url`을 재사용하여 libpq 환경의 `PGHOSTADDR/PGSERVICE/PGSERVICEFILE/PGOPTIONS`와 모든 DSN query override를 거절한다. 해당 poison case 8개를 DB 연결 없이 확인했다. 사용자 DB를 덮어쓰지 않으며, 로컬 TCP 주소와 `cx20_` 접두어의 빈 일회성 DB만 허용한다. 공개 DB와 공개 6시간/14일 프로필은 사용하지 않는다.

실제 `IngestionService`에서 명시한 SAME_HOST_SHARED_KERNEL_UTC 설정으로 한 배치를 접수하여 9개 `RawObservation` 템플릿을 얻는다. 이후 7일 행은 **합성 성능 fixture**다. 각 capture_seq/tag/sample/batch 식별자·시각은 독립이고 canonical UTC가 fixture 시간축을 따른다. 복제한 raw의 `clock_assessment`에는 `synthetic_performance_fixture=true`와 원본 템플릿의 assessment를 구분하여 저장한다. 과거 7일의 실제 수집·측정 근거나 604,800개의 실제 불변 시간 증거를 만들었다고 주장하지 않는다. 실제 clock evidence/ingest receipt는 템플릿 1개뿐이다. 이 시험은 이력 읽기 경로의 부하이며 intake 처리량 시험이 아니다.

원시 값은 태그별 일정한 서로 다른 값(0,100,…,800)이다. 생산 코드 `points_for`로 60초의 분 집계를 만든 뒤 전 구간에 확장한다. 실행 전 모든 태그의 원시 행 수·서로 다른 capture_seq 수·시간 경계·값 min/max·aggregated 여부와 분 집계는 전9태그·7일의90720행 모두에 대해 scope/policy·minute범위·중복/누락·point.t·GOOD·60/60·value/min/max를 SQL 집계로 검사한다. 예상 point는 production `points_for`로 다시 만들며500 태그의500.00000000000006 평균도 그대로 비교한다. HTTP 응답은 4개 태그×1,440분의 모든 시각·값·min/max·GOOD·60/60을 매번 대조한다.

실제 TCP Uvicorn/FastAPI와 실제 세션 권한 검사를 거친다. 독립 viewer 계정/세션 10개가 barrier로 동시에 `/api/v1/trends`의 4태그·24시간·minute 질의를 시작한다. 인증 없는 401도 확인한다. 기본 첫 10표본 + warm 10회×10=100표본의 HTTP 응답 본문 수신까지 시간을 측정한다. JSON 파싱·검산은 응답 이후에 한다. p50/p95는 nearest-rank, max·각 표본·응답 bytes를 JSON에 남긴다. minute/pending SQL의 `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)`, 테이블별 전체 크기·DB 크기도 남긴다.

**cold 조건:** `--cold-postgres-container <ID>`를 명시하면 seed/inventory 검증과 10개 계정/세션 준비 뒤, 첫 HTTP 조회 전에 `engine.dispose` → 해당 작업의 전용 PostgreSQL container restart → `SELECT 1` ready만 확인한다. 이후 raw/minute inventory를 다시 읽지 않는다. Docker의 관리 로컬 소켓을 명시하며 `hmi.task=cx20` label, Compose label 없음, 실제 DSN과 같은 loopback published port, host/container가 같은 `/tmp` writable bind PGDATA를 모두 대조한 컨테이너 ID만 재시작한다. 기존 preview/다른 DB/공개 port는 거절한다. 재시작 전후 UTC와 조건을 JSON에 남긴다.

이 조건은 **PG shared buffers cold / OS tmpfs cache warm**이다. 전역 OS cache flush는 하지 않으며 true OS/SSD cold 성능이라고 주장하지 않는다. opt-in이 없으면 기존처럼 `first HTTP use after fixture validation; DB/OS caches NOT evicted`를 기록한다. 실제 cold/warm 수치는 아직 실행 대기다.

## 자원 산정과 사전 관측

08:14:35 UTC `/tmp` 사전 관측: CPU count=5, MemTotal=34,906,016kB, MemAvailable=32,672,952kB. `/tmp`는 `tmpfs`, free=17,356,865,536bytes다. 루트 overlay는 약3.6GB 여유다. tmpfs는 RAM이며 SSD가 아니다. Docker VFS 추가 복사와 겹친 PG 부하를 피하기 위해 주 에이전트의 실행 슬롯을 기다린다.

추정 산식(실측 DB 크기 아님): raw JSON observation 약0.6–0.9KB + assessment/식별자/행 overhead 약0.3–0.6KB → 원시 heap 약5–8GB. PK·unique·범위/정리 인덱스 약2–4GB, 분 집계 약0.1GB, WAL·임시/안전 여유 약2GB. 보수적 사전 reserve=14GiB로 고정한다. 실제 9개 템플릿의 `pg_column_size` 합×604,800을 실행 JSON에 기록하여 예측을 보정한다. 이는 페이지 fill·인덱스·WAL을 포함하지 않으므로 최종 DB 크기를 대체하지 않는다. 적재 전 실제 `SHOW data_directory` 파일시스템도14GiB 이상인지 확인하고, chunk마다 그 여유가1GiB 미만이면 중단한다. 런타임 예산은 적재10–30분, 측정2–5분으로 **추정**이며 아직 실측하지 않았다.
