# CX-20 — 7일 이력 조회 성능

**전체 규모 실측 통과.** 2026-10-23 UTC, 제품 HEAD `fc6296ec9bd618388b1b5dfe6dda05342e94f06a`에서 원시5,443,200행·분 집계90,720행을 준비하고, 독립 인증 사용자10명의 4태그·24시간 HTTP 질의를 측정했다. cold p95=**1.398692초**, warm p95=**1.343585초**로 각각 목표3초 이하다. 저장 장치는 **tmpfs RAM disk**이며 SSD/OS cold 성능으로 해석하지 않는다. 8시간 시험과 프로젝트 전체 완료를 뜻하지 않는다.

최종 원본은 [full-result.json](evidence/CX-20/full-result.json), 자원 정리는 [full-lifecycle.json](evidence/CX-20/full-lifecycle.json), 실행 소스·이미지 식별은 [execution-provenance.json](evidence/CX-20/execution-provenance.json)에 보존했다. 사용자 재개 지시 전의 미실행 상태를 이번 실제 결과로 갱신한다.

## 기준·환경·실행 범위

- 9개 아날로그 ×604,800초 = 원시5,443,200행, 9×10,080분 = 분 집계90,720행. 공개6시간/14일 프로필이나 축소 자료를 쓰지 않았다.
- 로컬 PostgreSQL17.11, pinned image `postgres@sha256:3645570cccdfa447589da9f57dd740faa29b30938e861289a5574b6ca6b03826`. 실제0018 스키마와 인덱스를 유지했다.
- 실행기의 os.cpu_count()=5, 실제 cgroup cpu.max=400000/100000으로 quota4core, MemTotal34,906,016kB. 실제 PGDATA의 시작 여유 약17GB, 사전 reserve14GiB, 시간 chunk마다 여유1GiB 미만 중단 guard를 유지했다. 최종 적재까지 guard에 닿지 않았다.
- 별도 `cx20_history` DB, `hmi.task=cx20` 전용 컨테이너, host/container가 같은 `/tmp/cx20-20261023T130153Z` bind와 PGDATA. OS가 고른 random39353을 `127.0.0.1`에 명시 publish했다. 환경 파일0600, DB 자격은 자식 환경으로만 전달했다. 공개 DB·preview·유료 자원은 사용하지 않았다.
- 실행기는 `deploy.backup_set.local_url`을 재사용해 `PGHOSTADDR/PGSERVICE/PGSERVICEFILE/PGOPTIONS` 및 모든 DSN query override를 연결 전에 거절한다. 빈 로컬 `cx20_` DB만 seed하며 기존 DB를 덮어쓰지 않는다.

이는 **합성 보관 이력의 읽기 성능 시험**이다. 실제 `IngestionService`의 명시적 SAME_HOST_SHARED_KERNEL_UTC 설정으로 template1배치·9개 원시 관측을 접수한 뒤 SQL `generate_series`로 자료를 확장했다. 각 capture_seq/tag/sample/batch 식별자와 시간은 독립이며, 확장한 raw의 `clock_assessment`에는 `synthetic_performance_fixture=true`를 표시했다. 실제 과거7일 수집·측정 근거를 만들었다고 주장하지 않는다. 실제 ingest receipt/불변 clock evidence는 template1개뿐이다.

태그별 원시 값은 서로 다른 일정 값0,100,…,800이다. `points_for`로 계산한 실제 집계 point를 전 구간에 확장했다. 전체 원시 행 수·서로 다른 seq·시간 경계·값 min/max·aggregated 상태를 확인했고, **전9태그·7일의 모든 집계 행**에 대해 scope/policy·minute범위·중복/누락·point.t·GOOD·60/60·value/min/max를 SQL 집계로 검산하여 태그별 invalid=0을 얻었다. 값500의 평균500.00000000000006도 생산 집계 코드의 결과 그대로 대조했다.

## 실측 결과

실제 TCP Uvicorn/FastAPI와 실제 세션 권한 검사를 사용했다. 독립 viewer10명을 생성하고 각각 비밀번호를 변경한 별도 세션으로 barrier를 통과해 동시에 질의했다. 인증 없는 요청의401을 확인했고, 각 응답의 4×1,440개 point 전체를 시간·값·min/max·GOOD·60/60과 대조했다. 질의 구간은 `2026-10-22T13:00:00Z` 이상 `2026-10-23T13:00:00Z` 미만, resolution=minute이며 첫4개 태그를 사용했다.

| 조건 | 표본 수 | p50(초) | p95(초) | max(초) | 목표 |
|---|---:|---:|---:|---:|---|
| PG buffers cold / OS tmpfs cache warm, 첫10명 동시 wave | 10 | 1.177243 | 1.398692 | 1.398692 | p95≤3초 통과 |
| warm, 10명 동시 wave×10회 | 100 | 1.161837 | 1.343585 | 1.389747 | p95≤3초 통과 |

p50/p95는 nearest-rank이며 모든 개별 지연·응답 bytes를 원본 JSON에 남겼다. 시간은 HTTP 요청 시작부터 본문 수신 완료까지다. JSON 파싱·값 검산은 그 뒤에 한다.

**cold 조건:** 전체 raw/minute 검산과 사용자/세션 준비 후 `engine.dispose()` → task-owned PG 컨테이너 재시작 → `SELECT 1` ready만 확인했다. 재시작은13:06:29.712827 UTC, ready는13:06:30.177726 UTC다. 이후 첫 측정 전 history inventory를 다시 읽지 않았다. OS cache flush는 하지 않았고 true OS/SSD cold라고 주장하지 않는다. 컨테이너 label·Compose label 없음·실제 DSN과 같은 private published port·동일 `/tmp` writable bind를 대조한 뒤에만 재시작했다.

| 단계 | UTC / 소요 |
|---|---|
| 전용 runtime 시작 | 13:01:53.797268 |
| seed 시작 → 완료 | 13:01:59.303257 →13:06:13.151383, **253.848126초** |
| PG cold 재시작 → ready | 13:06:29.712827 →13:06:30.177726 |
| 최종 JSON 종료 | 13:06:45.380695 |
| runner 전체 소요 | **287.297822초**, exit0 |

실제 seed 로그는 [full-seed.log](evidence/CX-20/full-seed.log)에 있다. template `pg_column_size`는 각936bytes, 합×604800=5,094,835,200bytes였다. 이는 페이지·인덱스·WAL을 제외한 추정 기초이며 아래 실측 DB 크기와 구분한다.

| DB/관계 | bytes |
|---|---:|
| 전체 DB | **10,474,501,811**(약9.755GiB) |
| analog_history_raw 전체 관계 | 10,421,608,448 |
| analog_history_minutes 전체 관계 | 42,082,304 |
| ingest_batches | 81,920 |
| capture_clock_evidence | 65,536 |

쿼리 계획은 warm 측정 뒤 실제 reader와 같은 SQL에 `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)`을 적용했다. 대표 첫 태그의 minute 조회는 `analog_history_minutes_pkey` Index Scan, 실제1,440행, Execution Time0.500ms·shared hit83이었다. pending 조회는 `ix_analog_history_raw_pending` Index Scan 뒤 Sort/Unique, 실제0행, Execution Time0.029ms·shared hit1이었다. 전체 계획은 원본 JSON에 있으며 이 SQL 시간 자체를 HTTP 성능으로 대체하지 않았다. HTTP p95가 목표 안이므로 제품 최적화는 추가하지 않았다.

## 실제 실행에서 발견·교정한 실패

실패와 HTTP표본0을 통과로 바꾸지 않았다. 모두 전용 자원에 한정했다.

1. 12:46:03~12:46:52 UTC PG 초기 기동은 host umask077로 bind 부모가0700이 되어 postgres 사용자가 통과하지 못했다. runtime에서 명시 chmod0755로 교정했다. 준비 재시도 중 발생한 정리 권한 문제도 전용 컨테이너 helper로 해결했다.
2. 12:48:25~12:48:30 UTC migration 단계에서 `InvalidRequestError`, 적재0행. 실행기의 `engine.begin()`과 Alembic env의 `connection.begin()`이 중첩됐다. root 승인 후 실행기 바깥을 `engine.connect()`로 변경하고 migration env가 transaction/advisory lock을 소유함을 좁은 회귀로 확인했다. [실패 원본](evidence/CX-20/failed-migration-result.json).
3. 12:53:12~12:53:17 UTC template9행 이후 첫 bulk SQL에서 `ProgrammingError`, SQLSTATE42725. `generate_series(:first,:last)`의 정수 경계에 명시 CAST를 추가하고 `1≤first≤last≤604800<2**31`을 검사했다. bulk 추가0행, HTTP0표본이었다. [실패 원본](evidence/CX-20/failed-series-result.json). 원본에는 exception type/SQLSTATE/위치가 남아 있으며 드라이버 메시지 전문은 비밀 노출 방지로 저장하지 않았다.
4. 12:54:18~13:00:12 UTC 첫 전체 seed/검산은 성공(raw5,443,200·minute90,720, DB10,474,534,579bytes)했지만 cold 재시작 뒤45초 ready 실패로 HTTP0표본이었다. [실패 원본](evidence/CX-20/failed-cold-result.json), [정리 기록](evidence/CX-20/failed-cold-lifecycle.json). 최초 Docker ephemeral publish port는 재시작 시 달라질 수 있었다. 데이터/PG 프로세스가 없는 동일 image의 전용 sleep-container 재현에서33780→33781 변경을 확인하고 즉시 제거했다. [port 재현](evidence/CX-20/ephemeral-port-reproduction.json). 이후 OS선택 random39353을 명시 publish하고 실제 PG 사전 재시작에서도39353 유지 확인 후 최종 전체 seed를 다시 실행했다.

## 재현·소스 식별·검증·정리

```sh
# 전용 pinned PG17에 동일 /tmp bind/PGDATA, task label, 명시 random loopback port를 준비한다.
# HMI_DATABASE_DSN은 mode0600 환경 파일을 읽은 runtime의 자식 환경으로만 제공한다.
.venv/bin/python scripts/benchmark-history.py --seed --run \
  --data-path /tmp/<task-directory> \
  --cold-postgres-container <task-owned-container-ID> \
  --output /tmp/<task-result>.json
.venv/bin/ruff check scripts/benchmark-history.py tests/unit/test_history_benchmark.py
.venv/bin/python -m pytest tests/unit/test_history_benchmark.py -q
```

최종 실행본은 [executed-runner.py.txt](evidence/CX-20/executed-runner.py.txt), SHA256 `1fffb48c4cfbf858a1c47ef29176587e935170e5be255d898e135f6a5b08ef6c`다. 제품 HEAD와 dirty=true 및 관련 소스121개의 시작/끝 hash를 원본 JSON에 남겼고 `source_changed_during_run=false`다. 직전 실패 실행본도 [보존](evidence/CX-20/failed-cold-runner.py.txt)했다. 직전본과 최종본 차이는 E501을 고친 SQL 줄바꿈뿐이며, 정확한 diff와 문자열 공백을 정규화한 AST 동일 검증은 provenance JSON에 있다.

마지막 unit 실행27개 통과(0.96초), 최종 Ruff와 담당 파일 `git diff --check` 통과. 이 단위 검사는 실제 부하를 대체하지 않으며 위 full run을 별도로 실행했다. 제품 backend·UI·공개 자원 변경은 없고 실행기의 초기화/SQL 바인드 오류만 수정했다.

최종 lifecycle은 `container_removed=true`, `data_removed=true`, `secret_file_removed=true`다. 안전 JSON·로그·실행 소스만 저장소 evidence에 복사하고 DB·개인 비밀은 보존하지 않았다. 독점 PG/performance 슬롯을 root에 반환했으며 이후 추가 서비스·성능 실행은 하지 않았다.
