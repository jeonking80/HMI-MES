# CX-40 — 18차 수집 원본 보관 종료

- 기준: `codex/kuls-backend-v3`, 17차 `f8fd6ef` 다음 작업.
- 사용자 승인: 정산 끝난 원본의 기본 7일 보관과 기준 문서 변경. 공개 이관·배포는 Claude 담당.
- 상태: 구현 및 분할 backend 검증. 실제 브라우저 결합 경로는 UI 첫 등록에서 차단됐다. 프로젝트 전체 완료를 뜻하지 않는다.

## 변경과 보호 조건

schema 0022에 영구 최소 영수증, 연속 보관 종료 범위, 정리 스케줄을 추가했다. 이관 자체는 기존 원본을 지우지 않는다. 생성한 Neon upgrade·grants 배치는 renderer 재생성 결과와 `cmp` 일치했다.

기본 `HMI_INGEST_RETENTION_DAYS=7`, 최소 1일이다. DB 저장 시각과 DB clock을 사용한다. 적용된 사건과 SETTLED 실행의 최종 요약·수량·설정 이력·커서 근거를 확인하고 gap·격리·미결 명령이 없는 배치만 지운다. null execution 제어 사건은 관측 배치로 간주하지 않는다. 미정산·불일치·충돌·불충분 증거는 남긴다. 다른 실행의 후속 진행과 검증 가능한 속도 조정 이력도 검토한다.

원본·해당 clock 근거·정확히 연결된 소비 probe와 만료 기록은 한 트랜잭션에서 처리한다. 생산 사건·실적·정산·작업지시·명령·알람·감사·계정·분 집계는 유지한다. 런타임의 직접 삭제·메타데이터 변경과 GUC 우회를 실제 권한 시험으로 거절했다. 기존 알람 FK와 gateway 전체 capture 유일성은 영구 영수증에 유지한다.

수집 커밋 뒤 별도 정리를 분당 한 번, 기본 200건 삭제·400건 후보로 제한한다. 500ms soft budget, 1,500ms statement timeout과 100ms lock timeout을 둔다. 후보별 savepoint로 잠금을 해제하고 스캔 커서를 유지한다. 오류 때 삭제·만료 기록은 롤백하며 이미 커밋된 수집은 유지한다.

만료 identity는 원래 ACK 대신 HTTP 410/RETENTION_EXPIRED다. 게이트웨이는 같은 ID와 버퍼를 유지하고 중단한다. 트렌드는 남은 분 값을 유지하되 원본 만료를 명시하고, 보고서는 해당 구간을 UNKNOWN/RETENTION_EXPIRED로 표시한다. 후속 clock 역행도 반영하며 시각 불명 구간은 보수적으로 덮는다. 상세 계약과 해시 누적 방식은 [INGEST_RETENTION.md](../../architecture/INGEST_RETENTION.md)에 기록했다.

## 검증 기록

- high 읽기 전용 검토: 삭제 자격·권한·잠금·트랜잭션·clock·재전송 및 최종 정수 해시 연산을 검토했다. 최종 정수 해시 및 clock/probe 호환성 수정까지 critical/high 지적 없음.
- 신규 57개 최초 실행: **22 통과/35 실패, 31.06초**. 관측 태그가 없는 시험 데이터, SQL trigger의 다른 relation OLD 필드 바인딩, 미사용 downgrade의 이전 함수 본문 차이를 고쳤다.
- 실패한 통합 35개만 재검: **33 통과/2 실패, 38.59초**. 남은 항목은 probe fixture의 실제 input digest 연결과 256비트 누적 해시 정수 나눗셈이었다. 제품 해시 연산은 정확한 `pg_catalog.div`로 수정했다.
- 남은 2개만 재검: **2 통과, 3.69초**. 독립 Python 해시 oracle, 삭제 오류 rollback과 관련 probe 보존을 확인했다. 신규 57개는 분할 검증했으며 단일 실행 57개 통과로 표시하지 않는다.
- 기존 회귀: 전체 unit 749개와 기존 통합 45모듈 643개, 합계 1,392개를 선택했다. 일반 sandbox에서 158개 통과 뒤 로컬 socket 제한에 막혀 중단했다. 동일 collection의 완료 prefix 158개를 제외하고 로컬 권한을 확보해 재개한 결과 **1,232 통과/2 실패, 1,103.77초**였다. 따라서 분할 결과는 **1,390 통과/2 실패**이며 단일 전체 실행 통과가 아니다. 실패는 receipt clock-context의 `utc_read_span_seconds` 누락과 기존 scope 우선 100건 probe 정리 계약 변경이었다. 두 제품 회귀를 수정하고 원본 만료 후 CaptureTime 전체 유지 검증을 추가했다. 영향받는 신규 retention 3모듈·기존 internal/measured-clock 2모듈을 재검해 **84 통과/새 fixture 1 실패, 67.00초**였다. 기존 회귀 2개는 통과했다. 남은 신규 fixture는 schema 1.2에 필수 통신 근거를 넣지 않은 데이터 오류로, 데이터를 보정하고 해당 1개만 재검해 **1 통과, 5.70초**였다. 테스트 파일 최종 Ruff·format도 통과했다. 전체 1,449개 distinct 선택 항목은 분할 검증했으며 최종 소스로 전부 다시 실행했다고 주장하지 않는다. [검증 집계](evidence/CX-40-verification.json).
- Ruff 전체 통과, format 검사 **272개 통과**. 이후 수정된 Python **20개**를 대상으로 Ruff·format 재검도 통과했다. 호환성 수정 4개 파일의 최종 Ruff·format도 통과했다.
- polling 웹 build 통과. 브라우저 사전 시도는 **PermissionError (setup)**로 시작하지 못했다. 로컬 socket 권한을 확인한 뒤 실제 실행 1회에서 simulator 복구·REMOTE/AUTO·App A 로그인까지 통과했으나 첫 레시피 등록 확인에서 실패했다: `FAIL: AssertionError (recipe submitted; await confirmed registration)`.

브라우저 실패는 17차와 같은 빈 master 목록의 UI 첫 품목 등록 경로다. Claude 소유 UI·검사 스크립트는 수정하지 않았고 우회 seed·재시도도 하지 않았다. 브라우저 이후 전체 생산/정산 경로를 통과했다고 주장하지 않는다. [실패 원문](evidence/CX-40-operable-failure.txt), [기존 통합 모듈 목록](evidence/CX-40-integration-manifest.json).

## 가속 적재와 한계

임시 DB 두 개에 일당 **1,000 capture의 합성 자료**를 각각 8일·9일 적재했다. 실제 1Hz 8일이나 8시간 운전이 아니다. 테스트 전용 owner가 scheduler의 실행 시각만 조정해 제한된 정리를 반복하며 DB의 원본 저장 나이 조건은 유지했다.

| 스냅샷 | 남은 원본 | 영구 영수증 | 만료 identity | 원본 bytes | 영수증 bytes | 범위 bytes |
|---|---:|---:|---:|---:|---:|---:|
| 8일 | 7,000 | 8,000 | 1,000 | 14,483,456 | 6,103,040 | 458,752 |
| 9일 | 7,000 | 9,000 | 2,000 | 16,261,120 | 7,487,488 | 843,776 |

[측정값](evidence/CX-40-accelerated-storage.json). 원본 **행 수**는 7일분으로 유지됐다. 물리 크기는 독립 DB의 적재·인덱스·dead tuple 영향을 포함하므로 감소·고정을 주장하지 않는다. 영구 UUID 영수증은 capture마다 증가한다. DELETE 공간 재사용에는 vacuum/autovacuum이 필요하다. 1Hz·약 6KB 배치의 7일 원본은 약 3.6GB이므로 이 변경만으로 Neon 무료 0.5GB는 보장하지 못한다.

기준 문서 DATA_AUTH·INGESTION·SETTLEMENT·PUBLIC_DEMO_RUN과 TREND_HISTORY·REPORTS에 승인 이유·원본 재검증 불가·시간 품질 영향을 기록했다. 공개 DB·Vercel·운영 SQLite·runtime·WO-T1·생산 조작은 수행하지 않았다. 공개 적용과 UI 갱신은 Claude가 이어서 한다.
