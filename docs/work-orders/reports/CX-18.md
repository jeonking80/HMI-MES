최종 상태: **구현·실제 로컬 전체 복원/회귀 통과**. T01~T12 전체·비기능·프로젝트 완료

- 대상: `codex/kuls-backend-v3`, HEAD `a5d9d1931b6ed68ea88147fe00dae3c337f188b3`, dirty 작업 트리. 핵심 구현은 이후 `d11800f`로 커밋했다.
- 구현: `deploy/backup_set.py`, `scripts/backup-set.py`, `apps/api/recovery.py`, command 경계 guard.
- 운영: [BACKUP_RESTORE.md](../../architecture/BACKUP_RESTORE.md).
- 공개 DB·기존 preview DB·보호된 `.local` 데이터 미접근. 기존 PostgreSQL17 고정 이미지의
  새 disposable fixture만 사용했다. 해당 fixture 포트로만 컨테이너를 식별해 도구를 실행했다.
  build/pull과 일반 스키마 migration은 없다.

## 검증한 결합

- 실제 생산 5 투입 = 양품 4 + 불량 1 + 폐기 0, 재공 0. 원본 최종 순번 10.
- 실제 API 커밋 직후 응답 유실로 gateway 미ACK 배치 1개를 남기고, 동시에 API pending
  START 명령과 미복귀·미확인 열린 알람을 보존했다.
- simulator/gateway 소유자의 flock 종료 장벽, PostgreSQL schema advisory 배타 잠금과
  모든 public 테이블 SHARE 장벽을 확보했다. 비협조 UPDATE는 lock_timeout으로 거절되고
  다른 연결의 실제 pg_dump는 성공했다. dump/inventory는 모든 쓰기가 막힌 같은 구간이다.
- 같은 set ID/checksum으로 PostgreSQL dump + typed 비밀 없는 설정 + 두 SQLite를 보관했다.
  SQLite backup API와 integrity/FK 검사를 사용했다. archive 추가/누락/symlink/손상/혼합,
  실행 중 writer, loopback 우회 URL 및 inherited libpq redirect 환경을 거절했다.
- source/stream/epoch/gateway/line/schema 설정과 실제 잠긴 snapshot의 일치를 확인했다.
  ProcessConfig/PLCConfig/seed는 원래 객체가 아닌 archive JSON에서 재구성했다.
- 새 경로·새 `hmi_restore_*` DB에만 복원하고 실행 snapshot의 물품·세 수량, 원본 사건,
  simulator/API 명령, 알람, 연속 커서/누락, gateway 미전송 배치의 전체 행을 대조했다.
- 복원된 controller/OPC/gateway/실제 API HTTP를 새로 구성했다. 실제 simulator
  `RECOVERY_REQUIRED`와 출력 OFF를 검증했다.
- 세션/auth_version 회전 후 옛 사용자 세션 401, 새 viewer 직접 제어 403을 확인했다.
  새 API는 새로 재주입한 credential만 등록하고 옛 service token 401을 확인했다.
  새 키의 실제 HTTP 재전송은 수량을 늘리지 않고 기존 배치의 ACK를 회복했다.
- DB owner 전용 database COMMENT 복원 marker를 매 command transaction에서 읽는다.
  **wrapper 없는 일반 API**의 claim과 authorized enqueue도 거절된다. 기존 pool이나
  session SET으로 marker를 우회하지 않는다. 일반 DB의 기존 command/workflow 회귀도 통과했다.
- 원본 manifest/receipt, DB 실행·수량·명령·알람·커서, simulator 원본 사건/실행,
  gateway identity/source/커서/ACK 연속성, 정지 PLC를 검산하고 pending/gap이 없을 때만
  명시적 operator acknowledgement로 resume을 허용했다. false ack와 변경된 DB 근거는
  거절했다. 실제 재기동·ACK 회복·writer 종료 후 resume 성공도 확인했다. resume은
  DB marker만 해제하고 PLC recovery/출력 OFF를 유지하며 명령·자동 START를 만들지 않는다.

fixture 종료 시 exact-name restored DB들과 disposable 컨테이너를 정리했다. preview에는
접근하지 않았다. archive/비밀은 `/tmp`의 보호된 산출물이며 Git에 넣지 않았다.

## 실패·수정과 독립 high 검토

초기 실행에서 PLC 유효 정지 상태 목록 누락, SQLite backup WAL sidecar와 엄격한 멤버
검증 충돌, hidden-parameters engine 설정 누락, 실제 user HTTP exact-origin 누락을
수정했다. 최종 durable 재실행의 첫 시도는 claim 요청에 필수 JSON `{}`가 없어 422를
받은 driver 오류였다. 유효한 body로 수정한 뒤 위 153건을 모두 재실행했다.

독립 high 지적과 수정:

1. pg_restore의 `--dbname` 누락을 Docker helper가 가리던 P1: production 인자에 명시하고
   helper의 숨은 `-d` 삽입을 제거했다. 최종 실제 restore는 같은 인자 계약을 쓴다.
2. `PGHOSTADDR`/`PGSERVICE`/`PGSERVICEFILE`/`PGOPTIONS` inherited redirect P1: engine/도구
   준비 전에 거절하고 네 poisoned selector 회귀를 추가했다.
3. 간접 명령을 만드는 work-order bind 경로가 optional gate에서 빠지던 P2: canonical/query
   alias workflow mutation도 막고 ASGI 회귀를 추가했다.
4. optional wrapper만으로 복원 제어 제한을 보장하던 P1: DB owner marker와 실제 enqueue/
   claim/submission/result 경계 검사를 추가했다. wrapper는 추가 방어로만 문서화했다.
5. 비기본 controller 전역 설정 누락 P2: typed process/plc/seed 보존·재구성과 실제 identity/
   schema 대조를 추가했다. resume은 restart의 RECOVERY_REQUIRED 추가 사건만 허용하며
   gateway identity/source/커서/ACK 연속성도 검산한다.

이전 `/tmp/v3-backup-restore-final-junit.xml`의 7건 통과는 위 추가 수정 전 중간 근거다.
최종 판정은 이 보고서의 **153건과 durable evidence**로 대체한다.

## 한계

실제 네트워크·세 저장소 전체 복원을 검증했으나 프로세스 객체 종료/재생성 시험이다.
OS SIGKILL/Compose 전체 재기동·임의 crash 지점·장시간 재기동 시험으로 확대하지 않는다.
로컬 host에 pg_dump가 없어 운영 CLI PATH 호출 자체는 미실행이다. 실제 PG17 도구 실행은
동일 인자를 쓰는 private fixture Docker exec 운송으로 검증했다. 외부 인증서/개인키/새
service credential은 별도 재주입하며 archive에 평문 secret을 묶지 않는다.

## 후속 운영 CLI 실제 검증

사용자의 전체 미완료 항목 재개 후 `tests/e2e/test_backup_cli.py`에서 실제 `scripts/backup-set.py backup/restore/resume`를 별도 프로세스로 실행했다. **1 passed /10.452초**, backup0.7116초·restore0.9466초·resume0.5119초, 모두exit0. 원본 생산/설정·전체 inventory, 복원 marker, 명시 resume 후 DB 제한만 해제·PLC RECOVERY_REQUIRED/출력 OFF 유지 등6개 assertion을 확인했다. 최초 실행 통과이며 재실행/제품 변경은 없다.

PG17 도구는 정확한 fixture image와 loopback mapped port로 고정한 동일 컨테이너의 Docker exec PATH adapter다. 운영 Python CLI 진입점 검증이며 **host-native pg_dump/pg_restore 검증은 아니다**. DSN/비밀번호는 자식 환경에만 전달하고 raw 출력 대신 hash를 기록했다. 자체 복원 DB·컨테이너를 정리했고 기존 preview를 보존했다. [JSON](evidence/CX-22-backup-cli.json), [JUnit](evidence/CX-22-backup-cli.xml). 명령: `HMI_ACCEPTANCE_ARTIFACTS=/tmp/cx22-backup-cli .venv/bin/python -m pytest tests/e2e/test_backup_cli.py -q --junitxml=/tmp/cx22-backup-cli.xml`.
