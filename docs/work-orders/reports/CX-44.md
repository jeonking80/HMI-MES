## 결론과 근본 원인 우선순위

1. **제품 수명주기가 원본 수명주기에 묶였다.** 최종 실적 수량은 정산되지만 시간 보고는 만료될 capture JSON을 다시 읽는다. 시간 불명 만료 기록의 영향 범위도 조회 창 전체여서 과거 불확실성이 새 작업까지 전파된다.
2. **무료 용량 예산이 전체 영속 데이터 계약에 들어 있지 않다.** 원본 TTL만 줄이고 알람 판단 FK·영수증·정확 ID 목록을 계속 보존해 저장량 증가의 차수 자체는 바뀌지 않았다. 압축은 증가 속도만 낮춘다.
3. **사용자 업무·PLC·화면·복구 상태를 연결하는 계약이 분산됐다.** 다음 작업 연결에 START 준비 조건을 재사용하는 오류, 내부 요청 확인을 운전자에게 넘기는 단계가 같은 경계 문제를 드러낸다.
4. **배포된 웹/API와 설비 실행 호스트의 운영 책임이 분리돼 있다.** 자식 프로세스 감지는 있지만 호스트 수명, COMMITTED 진전, backlog를 감시·복구하는 지속 운영 계약이 없다.
5. **회귀 시험이 동일 배포 조합의 전체 업무·시간 경과·보관 만료를 대표하지 못했다.** 개별 시험 통과, 합성 이력, 분할 결과, 과거 버전 수락을 최신 공개 릴리스와 혼동하면 반복 결함을 막지 못한다.

이 결론은 '전부 다시 작성'을 의미하지 않는다. OPC UA, PLC 판정, 원래 명령 ID, 수량 원자성, 인증은 유지할 자산이다. 변경 중심은 증거 저장·시간 projection·업무 orchestration·운영/릴리스 경계다.

## B. 데이터 모델·보관·용량 / C. 시간·증거

## 1. 판정과 근본 원인

1. 현재 구조는 0.5GB에서 무기한 수렴하지 않는다. 원본을 3시간으로 줄여도 capture마다 영구 영수증/은퇴 ID/알람 판정을 남긴다. `0024_ingest_retired_segments.py:356-370,425-429`는 UUID를 16바이트 배열로 바꿨지만 삭제되지 않는 UUID 수와 GIN이 계속 증가한다. 1Hz UUID 본문만 `86,400×16=1,382,400 byte/일`(약1.38MB/일)이며 인덱스·행·기존 chunks는 별도다. 압축률을 높이는 것은 O(t)를 O(1)로 바꾸지 않는다.
2. 기능의 확정 결과와 재검증용 원본 수명이 분리되지 않았다. 보고서는 봉인된 가동 구간을 읽지 않고 매번 전체 batch 본문+시각 증거에서 재구성한다(`reports.py:295-431,462-468,820-829`). 수량 정산의 SETTLED는 가동 시간 정산과 별개다(`settlement.py:331-381`, `reports.py:832-838`). 따라서 원본 만료 후 수량은 남아도 시간이 다시 불명이 되는 것은 구조의 직접 결과다.
3. 미지의 시간 범위를 안전하게 국소화할 좌표가 없다. `ingest_retention.py:177-192`는 과거 `effective_time_unknown` 범위를 날짜 조건과 관계없이 모두 반환한다. `retention_provenance.py:19-38`은 이를 요청 전체 `[start,end)`로 확장한다. `reports.py:660-679`가 UNKNOWN 증거로 넣고 `reports.py:106-128`이 정상 증거보다 우선한다. 따라서 시각 불명인 옛 범위 하나만 있어도 같은 line/stream의 미래 보고서 전체에 RETENTION_EXPIRED 장벽이 생길 수 있다. 이는 실제 공개 DB를 재현 측정한 결과가 아니라 **코드로 확인한 충분조건**이다.
4. 180일 정책과 미해결 보호는 최대 사건 생성률·payload·실행 수·미해결 수 상한 없이 용량 보장을 만들지 못한다. 기획서 `:403`, 개발계획서 `:223`은 180일/미해결 보호를 명시하지만 운영 DB에는 그 전체 생명주기를 끝내는 설계가 없다. `alarm_capture_decisions`는 append-only(`0011_alarm_capture_context.py:35-59`), `alarm_receipts/actions/outbox/rule_versions`도 append-only(`0010_alarm_store.py:55-72`)다. FK를 receipts로 옮겨 원본 삭제만 허용했을 뿐(`0022_ingest_retention.py:86-95`), 판정이 참조한 receipts는 압축에서도 제외된다(`0024...:406-408`). 알람 NO_CHANGE도 상태 영수증을 늘린다(`alarm_lifecycle.py:270-273,335`, `alarm_store.py:223-235`).
5. 시간 엄격성 자체보다 보장의 범위가 과도하게 결합되어 있다. RTT는 원래부터 50ms drift 가정+최대60초 유효 구간에 기대며 절대적 참시각 증명이 아니다(`measured_clock.py:220-249`). same-host는 공유 kernel UTC라는 운영자의 **명시 가정**이고 PLC source clock의 공유를 보장하지 않는다(`capture_clock.py:83-88,120-135`). 공개 Vercel API와 외부 gateway에 same-host를 설정해 성공 처리해서는 안 된다.

## D. 운영 구조

- 현 상태는 완전한 무감시가 아니다. `deploy/plant_runtime.py:359–363`은 0.25초마다 자식 프로세스 종료를 감지하지만 RuntimeError로 supervisor를 끝낸다. 같은 source의 자동 재기동은 여기 없다. `deploy/plant_service.py:75–87` health는 자식 PID가 살아 있는지만 보며, 수집/OPC/ACK가 전진하는지는 보지 않는다. 그 wrapper도 자식 종료 뒤 종료한다(`:103–107`). `compose.yaml:64–71`은 gateway만 restart:on-failure이며 이 로컬 구성의 존재를 공개 runtime 자동 복구 증거로 볼 수 없다.
- 근본 원인은 공개 HMI의 생존성을 개발 세션/사용자 PC의 생존성과 결합한 운영 계약이다. 증상은 오래된 데이터, 제어 잠금, 전체 사이트 정지처럼 보이는 화면이다. alive HTTP 200이나 Vercel 루트 200은 설비 데이터 경로 정상의 대체 지표가 아니다.
- PC 이동 절차는 이미 있고 같은 identity 복제 동시 실행을 금지한다(`deploy/plant-hosting.md:76–84`). PC 절전·전원·네트워크가 중단되면 멈추며 24시간 보장은 없고 인증서는 30일 유효하다(`:86`). host가 꺼지면 그 host의 systemd와 watchdog도 꺼진다.
- 최단 개선: 기존 소유자 관리의 켜진 Linux/WSL 장비에 영속 scope 전체를 보존하고 OS 서비스 감독을 적용한다. 단일 소유 잠금, 재시작 backoff, 반복 실패 차단, 부팅 후 자동 시작, 로그 회전, 인증서 만료 경고를 함께 둔다. 자동 재시작은 프로세스 복원까지이며 START 같은 생산 명령을 새 ID로 자동 발행하지 않는다. 손상·identity 충돌·영구 증거 손실은 자동 reset하지 않고 recovery_required로 멈춘다.
- process liveness, OPC 연결, 마지막 capture, 마지막 COMMITTED ACK, 큐 최오래 나이/건수/bytes, 디스크, 인증서 만료일을 분리한다. 마지막 capture/ACK가 정해진 시한을 넘으면 상태를 degraded로 전환한다. API DB 부하는 감시 자체가 원인이 되지 않도록 15–30초 표본·최신 상태 테이블만 읽는다.
- 외부 감시가 있어야 host 전체 중단을 알 수 있다. 별도의 이미 보유한 장비/기존 무료 상태 감시 수단에서 heartbeat를 확인하는 방식을 제안한다. 새로운 외부 알림 전송/계정 연결은 계획 승인 후 별도 구성한다. 외부 감시 수단이 없으면 host 종료 경보는 미충족으로 명시한다.

## E. 성능·배포 구조

### 실제 경로와 확인된 한계

- 실제는 gateway → HTTPS → Vercel FastAPI → **psycopg PostgreSQL/TLS → Neon**이다. 'Neon HTTP driver'는 현재 코드와 다르다. `apps/api/serverless.py:217–229`는 SQLAlchemy NullPool, prepare_threshold=None, connect_timeout=10, verify-full이다. 요청에 연결 획득·TLS·DB 왕복 비용이 들어갈 수 있지만 이번 조사에서 해당 비용을 공개 분해 측정하지 않았다. 단순히 HTTP driver 탓으로 단정하면 안 된다.
- `vercel.json:4–9`: sin1, polling 빌드, maxDuration 60초. 60초는 성능 목표가 아닌 종료 상한이다. query 한도를 늘리는 것은 cold start/DB wake/쿼리 부하를 줄이지 않는다. 'cold start가 50초 지연의 원인'은 미입증이다.
- screen은 응답 완료 후 1초 대기, timeout 2.5초(`apps/web/src/screenPolling.ts:6–8,107–133`). 각 요청 0.5초라면 갱신주기는 대략 1.5초다. 요청 즉시 고정 1Hz와 같지 않다. 10명이 응답시간 무시 시 screen만 최대 약10req/s이고 명령/보고서 요청이 추가된다. polling을 유지하려면 최신 projection/짧은 query, DB 연결 수와 지연 예산이 필요하다.
- analytics 조회 timeout은 **이미 45초**(`apps/web/src/analytics/api.ts:367–374`), write는15초(`:406–414`)다. '현재 모든 보고서가15초로 잘린다'는 서술은 오래된 증상이다. 18초 관측의 현장 원문/측정시각은 총괄 보고서의 공개 실측과 연결해야 한다. 45초 변경은 사용자 대기 문제를 해결하지 않는다.
- gateway는 delivery lock 아래 한 건 lease→HTTP→ACK를 수행한다(`apps/gateway/worker.py:251–263`). 전송 성공 후0.01초, 실패 backoff≤5초(`:318–332`). CX-38의 원래 현장 기록은 왕복 약0.7초, 약50초 정지 뒤 약3분 회복이며 정지 원인은 미확인(`docs/work-orders/CODEX_KULS_보강_v14.md:104–115`). 수집과 전송 분리는 이미 되어 있어도 배출률 여유가 낮으면 최신성이 회복되지 않는다.
- 1Hz 수집, FIFO1800건을300초에 비우려면 신규300건까지 총2100건, 평균 **7건/초 이상** 배출이 필요하다. 단건0.7초면1.43건/초여서 달성 불가다. 로컬 평균40.75ms는 WAN·TLS·실제 Vercel 부하 증거가 아니다.
- `docs/work-orders/reports/CX-42.md:24–31`의 같은 Codex기계 복구119.95→114.53초는 standalone 각1회다. `docs/DEVELOPMENT_STATUS.md:573`의 Claude컨테이너는 main/병합본 모두300.2초 실패다. 평균 개선/시험개수는 목표 실행환경의 기준 충족을 대신하지 못한다.
- profile `docs/work-orders/reports/evidence/CX-42-fifo-result.json`은 ingest1916호출78.08초 중 capture_trends47.42초, analog_history_raw.UPDATE17010회22.36초를 기록한다. 중첩 구간이므로 합산하지 않는다. 데이터 정리만 압축해도 trend·query fanout·전송 왕복 구조는 남는다.

### 권고 설계

1. immutable batch ID/내용해시/커서·ACK 원자성 계약을 먼저 고정하고 bounded 묶음 수집을 설계한다. 최대30건/256KB는 출발점이며 실제 payload 기준 조정한다. 부분 충돌의 앞부분 커밋, 같은 ID 재시도, 중간 응답 유실, 함수 종료의 재실행을 명세한다. source별 단일 writer/순서는 유지한다. 무제한 병렬 업로드는 채택하지 않는다.
2. API 요청 내 작업을 bounded 최신 projection/증거 append/필요한 원자성으로 제한한다. 무거운 과거 분 집계·보관을 영속 worker의 재시작 가능한 작은 chunk로 분리하되, 원본 삭제는 관련 파생 증거 확정 뒤만 한다. serverless 응답 뒤의 daemon thread를 유지보수 완료 보장으로 쓰지 않는다.
3. 확정 실행의 보고서는 원본 전체 재스캔 대신 버전 있는 봉인 summary/시간 구간·품질·누락 카운트에서 읽는다. 잠정/확정, 원본 만료, legacy 불명은 구별한다. 상세 query는 페이지/기간/응답bytes 제한을 둔다. free DB/컴퓨트 비용을 함께 계측한다.
4. 요청 ID별 API 수신/인증/DB연결/잠금/쿼리/commit/직렬화, gateway timeout/재시도/큐 나이, cold/warm 조건을 비밀값 없이 기록한다. cold start와 DB wake는 분리해서 추정하고 미확인 원인을 확정하지 않는다.
5. cloud 전체 재호스팅은 데이터 모델과 API 비용을 안정화한 뒤 비교한다. 상시 backend 통합은 배포 단순화 장점이 있지만 공개 TLS/백업/보안/가용성 책임이 커지고 무료 compute가 확보되지 않으면 추천안의 선행조건을 충족하지 못한다.

## H. 개발·검증 방식

근본 원인은 제한된 증상/fixture의 성공을 통합 제품과 공개 환경의 수락으로 확장한 작업 게이트다. 개발 규칙 자체는 이를 금지한다(`AGENTS.md:14–19`). 규칙이 없어서가 아니라 단일 release 게이트와 환경별 증거 연결이 약해서다. `docs/DEVELOPMENT_STATUS.md:573`은 확장 업무 시나리오에서 첫품목/플래그/속도변경/대기열 결함을 찾고 수정했음을 직접 기록한다. 기존 회귀가 없는 신규 화면 전이·실제 PLC 조건·재로그인·다음작업 경계를 검사하지 않은 것이 개별 모듈 시험으로 숨었다.

- 최신 한 커밋/빌드/스키마/권한 SQL/runtime 구성의 release manifest를 남긴다. git SHA, migration head, UI artifact hash, Python/PG/CPU·디스크, transport, host 위치, load, 시작/종료, cold/warm, 시험 입력과 실패·skip 원문을 기록한다. 여러 커밋/분할 실행은 각각 표시한다.
- 매 기능 완료는 관련 집중 시험, 다음 gate는 실제 DB/OPC/브라우저 확장 시나리오, release gate는 최종 동일 manifest의 단일 관련 회귀+확장 검사+승인된 공개 수락이다. 실패 원인 수정 후 실패1개만 통과한 기록을 전체 rerun 통과로 바꾸지 않는다.
- 기존 `check-operable-system.py --analytics-dir --guest-dir --extended-dir`를 release gate로 삼는다. flags의 의미는 `scripts/check-operable-system.py:1097–1110`; E1 자동목표 종료, E2 운전중 속도변경, E3 다음대기열까지 포함한다. 통과 이력은 공개 환경 통과가 아니다.
- 새 시나리오는 빈DB 첫등록→선택/배포→LOAD/READY→START→PAUSE/재개/속도→END/정산→보고서→다음작업, 잘못된 입력/권한/새로고침/재로그인, 원래ID 응답유실 복구, raw 만료 후 전후 결과 동일성, runtime process와 host 중단, backlog 복구를 포함한다.
- 시간/증거/용량 불변조건을 cross-feature 시험으로 둔다. raw 만료 후 특정 legacy 불명 구간이 확정 정상 실행까지 오염하지 않는지, 알람채널0/1/전체 구성에서 FK·id ledger가 계속 증가하지 않는지 확인한다.
- 긴 시험은 승인받기 전 실행하지 않는다. 실제24시간/8시간/30분 네트워크단절 및 실제7일 적재는 미실행 상태로 유지한다. 가속 TTL/입력은 로직 검증이고 실제 기간 안정성 증거가 아니다.


## 후속 결정

추천안·수명주기 예산과 보장 변경은 [REDESIGN_PROPOSAL](../../architecture/REDESIGN_PROPOSAL.md), 공개 안정화/전체 수락 경로는 [RECOVERY_PLAN](../../architecture/RECOVERY_PLAN.md)을 따른다. 21차는 독립 구현하지 않고 원본 만료 이후 보고서 유지 요구를 R1에 흡수한다. 공개 DB 실제 크기·행 수·증가율은 차단 상태이므로 이번 진단의 완전한 현장 실측 완료를 주장하지 않는다.
