# CX-22 — clean build 재현 실행기 준비

최종 정리: 2026-10-23 사용자 마무리 지시에 따라 새로운 no-cache build·runtime·전체 수락 묶음은 시작하지 않았다. 실행기 준비와 분할 수락 근거를 인계하며 **릴리스 수락은 미검증**이다. 아래 다음 실행 절차는 인계용이며 자동 실행 예약이 아니다.

후속 재개: 사용자가 이후 **8시간 시험을 제외한 미완료 항목 전체**를 명시했다. 최신 main `51f2383` UX-11의 기존 `same-host`를 릴리스 wrapper가 재사용하도록 보완했고, 인자가 없으면 추가한다. 실제 동작을 manifest에 `reused`/`appended`로 기록한다. compiled wrapper의 인자·환경 보존/중복·충돌 거절/호출 횟수/원래 실패 전파 **15개 통과**, Ruff 검사·형식 통과. 실제 no-cache build와 릴리스 수락은 자원 독점 순서에 맞춰 실행할 예정이며 아직 통과가 아니다.

운영 CLI의 별도 검증은 `tests/e2e/test_backup_cli.py`의 실제 backup/restore/resume 프로세스1개가10.452초에 통과했다. 전체 inventory·명시 재개·PLC 정지 유지 확인, PG17은 동일 fixture의 Docker adapter이며 native host 도구가 아니다. [증거 JSON](evidence/CX-22-backup-cli.json)·[JUnit](evidence/CX-22-backup-cli.xml). 이후 clean checkout의 전체 수락 묶음에도 이 시험을 포함한다. 이 단일 통과는 clean build/릴리스 전체 통과를 대신하지 않는다.

2026-10-23 UTC. **실행기 구현·clean clone의 실패 경로 검증만 완료했다. 새 Docker build, 전체/독립 runtime, 데이터 보존 재시작, 릴리스 CX-17 묶음은 미실행이다.** 기존 이미지 runtime이나 과거 clean build를 이번 성공으로 대체하지 않는다. 프로젝트 완료/릴리스 수락 통과 판정은 하지 않는다.

## 구현

`scripts/check-release.py`를 추가했다. `--target`의 **커밋된** 소스를 별도 일회성 `git clone --no-hardlinks --no-checkout`에 받고 detached checkout·clean 여부·tracked 파일 SHA256을 확인한다. 원래 working tree의 untracked/dirty 소스를 몰래 가져오지 않는다. Git worktree/브랜치/커밋은 만들지 않는다. 대상 커밋에 CX-17 runner가 없으면 거부한다.

기본은 준비 모드이며 build/runtime을 수행하지 않고 exit2(INCOMPLETE)를 반환한다. `--run`은 다음 실제 명령과 assertion을 수행하도록 구현했다. 아직 실행 성공을 확인한 목록은 아니다.

| 단계 | 실제 실행 예정 동작 | 현재 결과 |
|---|---|---|
| clean checkout | local clone → target detached checkout → clean 확인 → tracked SHA256 | 아래 구버전 target에서 clone까지 통과, 필수 CX-17 파일 부재로 거부 |
| no-cache build | 명시적 unix Docker socket의 `compose build --no-cache`; checkout/Docker data-root 공간 guard | 미실행 |
| image manifest | 새 프로젝트 image tag별 image ID와 RepoDigests 기록. local build의 빈 RepoDigests는 빈 값 그대로 둠 | 미실행 |
| Compose 전체 | `up -d --no-build`는 **이번 no-cache build가 만든 고유 tag**만 사용. 기존 `compose_acceptance.py`를 API 컨테이너 안에서 실행해 실제 생산·GOOD trend·가동>0·SETTLED 대조 | 미실행 |
| 데이터 보존 재시작 | source/gateway writer 정지 → PG·SQLite inventory → `down`(volume 유지) → `up` → 원래 사건 prefix·실행/수량/명령/열린 알람·커서 미후퇴·RECOVERY_REQUIRED·자동 START 없음 | 미실행 |
| 독립 실행 | 이번 clean image에서 web dist를 추출하고 기존 `check-operable-system.py`를 별도 child wrapper로 읽기 전용 import하여 실제 별도 CLI API/simulator/gateway+Chromium 경로 실행 | 미실행 |
| CX-17 | clean target의 `pytest tests/e2e -q --junitxml=...` 실제 실행, 각 T JSON과 JUnit 보존 | 미실행 |
| cleanup | 이 실행의 고유 Compose 프로젝트만 down-v; 요청 시 이 실행의 두 image tag만 제거. 광역 prune 없음 | 컨테이너를 시작하지 않아 해당 cleanup 미실행; 일회성 clone은 제거됨 |

외부 `--compose-file`로 현재 세션의 proxy build args와 BuildKit `proxy_ca` secret만 추가할 수 있다. merged runtime service/volume/network 또는 build context/Dockerfile/additional context를 바꾸면 거부한다. 현재 working tree를 mount한 cached-image 우회는 clean build로 인정하지 않는다. `DOCKER_CONFIG`·registry 인증·상속된 proxy 변수는 보존하며 Docker endpoint/context/TLS selector만 제거하고 명시적 `unix:///var/run/docker.sock`을 쓴다. TLS 검증을 끄지 않는다. CA는 기존 Dockerfile의 RUN secret mount만 사용한다.

독립 CLI child wrapper는 정확히 `[sys.executable, "-m", "apps.api", "serve", ...]`인 `subprocess.Popen` 호출 한 곳에만 `--trend-clock-policy same-host`를 추가한다. `serve-user`, simulator, gateway, 나머지 CLI 인수/환경은 그대로 전달한다. 기존 driver에 이미 clock policy가 있거나 해당 확장이 정확히 1회 적용되지 않으면 성공을 거부한다. original driver SHA와 변경 없음, wrapper SHA, 확장 내용·횟수를 JSON에 남긴다. 이는 같은 호스트의 명시적인 시간 가정이며 원래 driver의 실제 GOOD/가동/정산/CSV assertion을 완화하지 않는다. Claude 소유 파일은 수정하지 않는다.

`release.json`에는 target SHA, 원래 source dirty 여부, runner/전체 tracked 파일/override SHA256, UTC, 단계별 상태, 실제 명령 인수·exit·output bytes/hash, 새 image ID·RepoDigests와 결과를 기록한다. proxy 진단에 비밀값이 섞일 수 있으므로 raw subprocess stdout/stderr를 출력하거나 파일로 보존하지 않는다. 알려진 `no space left on device`는 ENOSPC 식별자로만 기록한다. restart inventory도 raw 계정 정보 대신 비교 결과와 digest만 manifest에 넣는다. cleanup 실패 시 복구용 checkout 경로를 보존한다.

## 이번 실제 검증

```sh
.venv/bin/python scripts/check-release.py --help
.venv/bin/python scripts/check-release.py \
  --target 4490a4c --output /tmp/hmi-v3-cx22-prepare
.venv/bin/ruff check scripts/check-release.py
.venv/bin/ruff format --check scripts/check-release.py
```

- help·lint·format 통과. embedded stopped-writer inventory Python의 AST parse 통과.
- 일회성 child wrapper probe 통과: fake Popen에서 internal `apps.api serve`에만 policy가 1회 붙고, `serve-user`/gateway 인수와 env가 정확히 유지되며, 기존 policy가 있으면 exit1로 거부함을 확인했다. 이 probe는 Docker/실제 CLI 업무 수락 통과를 뜻하지 않는다.
- 준비 실행: `2026-10-23T08:27:47.732948+00:00`~`08:27:47.827598+00:00`, 약0.095초. target `4490a4cbef7c46e5dff9017d059ddc6b312df161`, source_dirty=true.
- 일회성 clean clone과 detached checkout까지 성공했다. 해당 커밋에는 새 `tests/e2e/test_core_acceptance.py`가 없으므로 **`Committed target lacks required release acceptance runners`**, exit1/FAILED로 정확히 거부했다. `/tmp/hmi-v3-cx22-prepare/release.json` 원본 보존. Git 명령 5회 외 Docker 명령은 0회다. clone은 제거했다.
- 준비 manifest의 checkout 경로 파일시스템 여유는 17,354,801,152 bytes였고 CPU count는5다. **Docker VFS의 실제 가용 공간, RAM≥8GB, SSD는 이 값으로 입증되지 않는다.** `--run`은 별도로 daemon의 storage driver/data-root/version과 data-root 여유를 확인하게 했다. 기본 최소 여유 guard는8GiB이며 하드웨어 수락 조건을 대체하지 않는다.
- managed cloud runtime/Docker 지침을 읽었다. 환경 상태의 네트워크 policy state는 unknown이어서 enforced로 해석하지 않았다. 공개/유료 서비스에는 연결하지 않았다.

과거 ENOSPC 원인은 관리형 VFS가 큰 image/container root filesystem을 복사하는 동안 PostgreSQL 시험·build가 겹치고 여유가 부족했던 것이다. 주 에이전트가 공간과 독점 실행 슬롯을 조정 중이다. 이 작업에서는 daemon 재시작·build·prune·기존 image/container 제거를 하지 않았다. 기존 preview PostgreSQL은 그대로다.

## 다음 실행

주 에이전트가 모든 runner를 커밋하고 공간/독점 실행을 확정한 후 실행한다.

```sh
.venv/bin/python scripts/check-release.py --target <최종커밋SHA> \
  --output /tmp/hmi-v3-release-final --run \
  --compose-file /tmp/현재세션-proxy-ca-build-only.yaml
```

외부 override가 필요 없는 일반 Docker 호스트는 `--compose-file`을 생략한다. 빌드·브라우저·복원 경계 등 한 단계라도 실패하면 원래 exit를 기록하고 release 전체는 nonzero다. 원래 `check-operable-system.py`는 Claude 소유이며 수정하지 않았다. 동일호스트 시간 정책은 기록된 child wrapper에서만 추가하며 target의 브라우저 selector·polling web build도 실제 실행에서 확인해야 한다. 새 clean build와 수락 묶음 통과를 아직 주장하지 않는다.
