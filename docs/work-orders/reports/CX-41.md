# CX-41 — 19차 시간 단위 원본 보관·영수증 압축

시간 단위 보관·정확 ID 압축·회귀 수정을 구현했다. 단일 전체 통합 실행의 실패는 아래 원문대로 기록하고, 수정 후 관련 39개는 통과했다. **무료 DB 물리 용량 목표는 이번 측정에서 충족하지 못했다.**

## 범위와 결정

`codex/kuls-backend-v3`의 18차 `2cea66c`에서 이어서 최신 Claude 브랜치 `8dfa0a4`를 병합했다. 화면 수정 `f1f0ec4`가 포함돼 있다. UI·README·기존 미커밋 E2E 파일 2개는 수정하지 않는다. 공개 DB·Vercel·운영 runtime은 변경하지 않았다.

19차 승인에 따라 `HMI_INGEST_RETENTION_HOURS` 기본 **168**, 최소 **3**으로 바꿨다. 정수가 아니거나 3 미만이면 시작을 거절한다. 기존 `HMI_INGEST_RETENTION_DAYS`는 단독·동시·빈 값 모두 거절한다. schema22의 일 단위 함수를 시간으로 잘못 해석하지 않도록 자동 정리는 schema23에서만 실행하고, schema22 조회 호환은 유지한다.

### 사용자에게 확인한 제한

실제 `alarm_capture_decisions`는 알람 발생 여부와 무관하게 매 capture의 영수증을 FK로 참조한다. 따라서 기존 참조 보존과 사건 수에만 비례하는 영수증 수를 동시에 보장할 수 없다. 사용자는 **“기존 참조 보존·한계 보고”**를 선택했다. 이 변경은 알람 판단·알람·정산·감사 등을 삭제하거나 참조를 재설계하지 않는다. 알람 소비가 활성인 경우 참조된 영수증은 계속 capture 수에 비례할 수 있다.

## 구현과 이관

- 추가 이관 `0023_ingest_compaction`: 기존 원본·영수증을 삭제하지 않고 시계 경계와 기존 역전 기록을 보강한다. Neon HTTP 업그레이드·권한 배치와 renderer target을 추가했다.
- 원본 삭제 자격은 18차의 정산·사건·커서·gap·격리·미결 명령 검사를 유지한다. 수집 커밋 뒤 분당 한 번, 기본 삭제 200·후보 400건, 500ms soft budget/1,500ms statement timeout을 유지한다. 오래된 schema22 만료 영수증도 같은 제한 아래 후속 압축한다.
- 만료된 미참조 영수증은 실제 FK 참조를 카탈로그와 참조 행으로 검사한 뒤 삭제한다. 모르는 RLS·권한 문제는 보수적으로 보존하며 실제 FK도 최종 보호한다. 원본 삭제·범위·ID 청크·영수증 압축은 같은 트랜잭션으로 처리한다.
- 연속 범위는 기존 SHA256 정수 합 누적값을 보존한다. 정확한 임의 batch ID는 gateway/generation/256 capture 버킷의 최대 256개 `text[]` 청크에 남긴다. GIN으로 ID를 조회하고, 순번은 source와 관계없이 gateway/generation 전체 범위에서 검사한다. 해시나 확률 필터로 ID 판정을 대체하지 않는다.
- API 재전송은 HTTP 410/RETENTION_EXPIRED이며 원래 ACK를 재생성하지 않는다. 직접 DB INSERT도 같은 gateway advisory lock 아래 압축 ID·순번 재사용을 거절한다. 런타임은 메타데이터를 임의 수정·삭제할 수 없다.
- 범위별 epoch의 첫·마지막 시각 좌표와 최신 capture 메타데이터를 보존한다. 영속 최초 역전 순번을 합쳐 raw·개별 영수증이 모두 없어져도 clock neighbor·알람 frontier·보고서 cutoff·내부 context를 유지한다. 새 내부 필드는 분석 응답에 노출하지 않는다.

임의 문자열 ID를 정확하게 기억해야 하므로 ID 청크·GIN 저장량은 여전히 capture 수에 비례한다. 개별 영수증 행의 overhead를 줄였다는 뜻이며 전체 영구 저장량이 고정된다는 주장이 아니다. 압축 ID 청크가 있거나 각 만료 범위의 영수증 보존이 불완전하면 schema23 downgrade를 거절한다. 압축이 없고 영수증이 완전하면 22의 원래 함수·권한을 복원하고 23 전용 메타데이터만 제거한다. 시계 역전 projection은 보존하며 더 낮은 이관의 기존 손실 방지 검사를 계속 적용한다.

## 기존 회귀 4건

품목 이관의 고정 schema21 기대값 두 곳은 실제 Alembic head와 정확히 비교한다. 과거 schema21 자체를 시험하는 고정 기준은 유지했다.

혼합 알람 집합은 정확히 schema23까지 허용한다. schema19~21은 등록·큐·품목 추가이며 혼합 coordinator를 제거하지 않았고, schema22~23도 판단 기록의 실제 FK와 시계·frontier 근거를 보존한다. 기존 구버전 배제와 정확한 집합 일치 검사는 유지했다.

FIFO 합성 이력은 실제 kernel uptime에서 1,800을 빼지 않고 별도 epoch와 양수 monotonic bracket을 사용한다. 실제 OPC 수집기·물리 동작·시간 정책은 변경하지 않았다.

## 검증

- high 읽기 전용 검토에서 schema23 트렌드 gate 누락과 직접 INSERT/압축 경쟁을 발견해 수정했다. SQL 변수와 테이블 별칭의 충돌도 선행 실행에서 수정했다.
- 전체 단위+신규/영향 통합 선행 실행: **800 통과/41 실패, 127.42초**. 단위 **787개는 모두 통과**했다. 공통 원인은 PL/pgSQL `p`·`receipt` 변수와 SQL 별칭의 충돌이었다. 두 변수명을 분리하고 실패 41개만 재검해 **41 통과, 48.28초**였다.
- Ruff 전체 통과, format 검사 **275개 통과**. 처음 long SQL 줄 오류는 수정 후 재검했다.
- 통합 전체 단일 실행: **1,844 통과/26 실패/6 오류, 1,950.63초**. 선택 **1,876개**를 분할하지 않고 끝까지 실행했다. 원문 요약은 [CX-41-integration-failures.txt](evidence/CX-41-integration-failures.txt)에 보존했다. 모든 실패·오류는 23이 미사용 상태에서도 downgrade를 무조건 거절한 경로와 연결됐다. 이를 안전한 보존 검증을 갖춘 미압축 downgrade로 고쳤다. 전체 실행은 한 번만 수행했다. 이후 실패·오류 32개와 보존·권한·이관 신규 검증을 포함한 **39개를 재검해 모두 통과, 105.32초**였다. 새 검증은 압축 전의 정확한 schema22 catalog·자료·권한 복구와 실제 압축 뒤 거절을 모두 확인한다. 최종 소스에서 전체 통합을 다시 실행해 통과했다고 표시하지 않는다.
- polling build 통과. 실제 `check-operable-system.py --chromium /usr/bin/chromium` **1회 통과**: 로그인·복구·REMOTE/AUTO·작업 등록/배포/실행 연결·START·실제 생산·PAUSE·END_RUN·SETTLED를 확인했고 브라우저/API 실적이 실제 simulator final summary와 일치했다. 원문 [operable.txt](evidence/CX-41-operable.txt), 결과 [operable.json](evidence/CX-41-operable.json).
- renderer upgrade·grants 재생성 결과와 저장 배치 `cmp` 모두 일치했다. 최종 Ruff·format 275개도 재검 통과했다. [검증 집계](evidence/CX-41-verification.json).

## 24시간 가속 용량

독립된 임시 PostgreSQL에 86,400 capture를 적재하고 3시간 보관으로 정리한다. 각 배치는 실제 태그 27개·고유 ID·검증된 계약 본문·개별 canonical SHA256을 사용한다. 첫 배치는 실제 ingestion service, 나머지는 저장 트리거를 켠 bulk INSERT다. PLC·생산 수락 시험이나 실제 24시간 운전을 대신하지 않는다. FK 참조 없는 기준 측정이며 알람 소비가 활성인 환경의 영수증 수를 대표하지 않는다.

원본 수는 DB의 실제 적재·정리 경과 초만큼 10,800보다 줄 수 있다. 시계를 고정하거나 보관 경계를 우회하지 않는다. 일반 VACUUM ANALYZE 전후를 모두 기록하며 VACUUM FULL이나 공개 DB 삭제는 하지 않는다.

측정 **1회 통과, 231.93초**. 본문 평균 **6,858.87 bytes**, 적재 59.58초·정리 166.55초, 제한 정리 321회였다. 75,825개 원본·영수증을 정리하고 원본 10,575·영수증 10,575·만료 구간 1행·정확 ID 청크 297행(최대 256 ID)을 남겼다. 실제 DB 경과 225.89초를 적용한 기대 원본 10,575와 일치하며 마지막 정리 시점의 3시간 초과 원본은 0개다. 만료된 영수증 잔존은 0이다.

테이블·인덱스별 분리 수치는 [원본 측정 JSON](evidence/CX-41-capacity.json)에 있다. 제한 정리를 빠르게 반복한 이번 적재에서는 청크 배열·인덱스와 범위 갱신의 dead tuple/빈 공간이 물리 파일에 남았다. 일반 VACUUM은 공간 재사용과 일부 끝 페이지 정리를 하며 파일 전체 축소를 보장하지 않는다. 실제 1Hz 운전의 autovacuum 간격·장기 정상 상태 파일 크기를 측정한 결과로 확대하지 않는다.

**행 수와 미참조 영수증 압축 조건은 확인했지만, 이번 측정의 물리 DB는 VACUUM 뒤에도 약 540MB로 무료 0.5GB를 넘었다.** 무료 용량 충족을 통과로 표시하지 않는다. FK 참조가 활성인 실제 알람 경로는 추가 영수증·판단 기록까지 남으므로 이 기준 측정보다 커질 수 있다. 더 작은 물리 크기를 위한 갱신/저장 방식 조정이나 운영 용량 판단은 후속 검토이며 공개 적용으로 숨기지 않는다.

기준 문서 7개에 변경 이유·영향·18차 이력과 현재 19차 정책을 구분했다. 배포 환경변수·공개 이관·PR·main 병합은 Claude 담당이다. 이 보고는 프로젝트 전체 수락·성능·복구·운영 완료를 뜻하지 않는다.
