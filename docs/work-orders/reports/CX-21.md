# CX-21 — 실제 8시간·10브라우저 장시간 운전 실행기

판정: **사용자 지시로 실행 제외 / 미실행**. 2026-10-23 사용자가 “8시간 시험은 하지마. 마무리하고 정리해”라고 지시하여 이번 작업에서 실행하지 않는다. 실제 8시간 운전은 시작하지 않았고 통과로 표시하지 않는다. 이전 SSD 근거 부족에 따른 사전 차단 기록과 원래 기준은 아래에 이력으로 보존한다. 재개 예정 작업으로 취급하거나 자동 실행하지 않는다.

## 실행 조건과 명령

하드웨어 실측 JSON은 `effective_cpu_cores` ≥4, `effective_memory_bytes` ≥8,589,934,592(8GiB), `ssd_proven: true`를 포함해야 한다. 주 에이전트가 실제 디스크 provenance와 제한을 기록한다. 시작 시각을 사용자에게 알린 뒤 그 UTC를 인자로 전달하고 독점 슬롯에서 실행한다. 조건 미증명 시 실제 driver/PG 시작 전에 blocked JSON/JUnit(skip)을 남긴다.

```sh
.venv/bin/python scripts/run-endurance-acceptance.py \
  --artifacts /tmp/cx21-real-endurance \
  --hardware-evidence /tmp/cx21-hardware.json \
  --start-announced-at-utc 2026-10-23T00:00:00Z
```

위 UTC는 명령 형식 예시이며 실제 사용자 공지나 실행 증거가 아니다. 아티팩트 위치는 SSD 조건을 충족한 실제 디스크의 별도 경로로 정한다.

## 사전 고정 판정 기준

- 실제 CLI 기본 100ms 공정·48태그·1Hz 수집, 실제 Chromium 인증 context 10개가 모두 조회/화면을 유지한 상태로 최소 28,800 monotonic 초를 운전한다. 세션 로그인과 준비 시간은 8시간에 포함하지 않는다. 목표 수량은 장시간 생산을 위해 uint32 최댓값으로 설정한다.
- 기본 인증 idle/absolute 만료는 변경하지 않는다. 실제 활성 조회로 idle을 갱신하며 4시간 시점에 새 브라우저 인증 context를 먼저 준비하고 각 기존 context를 교체하여 동시 10개 이상을 유지한다. 원래 명령/시뮬레이터 세션도 실제 재인증 쿠키로 갱신한다. 지원되는 same-host 시간 정책을 같은 커널의 로컬 CLI stack에만 명시한다.
- 매분 실제 source production event의 occurred_at/원래 사건과 GoodTotal을 DOM에서 대조한다. 10개 context가 해당 수량 이상을 렌더링한 관측까지를 각각 기록한다. 수집 전송·웹 polling·관측 지연을 포함한 보수적 상한이며 중간의 모든 PLC 변화 지연을 측정한다고 주장하지 않는다.
- 매분 시뮬레이터의 실제 시험 온도 sensor offset +30°C를 적용하고 설치된 analog rule을 통과한 alarm instance의 qualified evidence 시각(`occurred_at`)부터 해당 원래 alarm_id가 각 DOM에 나타나는 시각까지 측정한다. 원인 주입 시각과 qualification 시각은 구분한다. 이후 offset 0으로 복귀한다. PLC 물리 열·tick은 바꾸지 않는다.
- PLC→화면 p95≤2초, qualified alarm→화면 p95≤3초. 각 지연의 p50/p95/max·표본 수를 저장한다. 음수·빈·NaN/무한대 표본은 실패다. 원래 source 사건/inbox body·적용 여부, 연속 cursor, 미해결 gap 0을 최종 대조한다. 프로세스 종료·조회 오류·알람 미발생·DOM 표시 timeout은 실패로 남긴다.
- 매분 CPU(process `/proc` 누적 tick 차이), RAM(감독 중인 CLI RSS 합계), 세션 cgroup CPU·memory.current/peak(브라우저 자식 포함), host meminfo, PostgreSQL DB/WAL, gateway payload queue·SQLite/WAL·손실의 추세를 기록한다. CLI RSS 합계를 호스트 전체 사용량으로 바꾸어 해석하지 않는다. Docker PG 프로세스는 별도 daemon cgroup일 수 있으므로 그 CPU/RAM 별도 추적은 남은 보강 범위다.
- 실제 수집·동시 세션·8시간 최소 기간, 두 지연 목표, 원래 사건·cursor/gap 대조와 driver의 최종 원래 execution 정산이 모두 충족되어야 성공이다. 하드웨어 미증명·실패·중단·단축 운전은 통과가 아니다.

## 구현과 현재 검증

`scripts/run-endurance-acceptance.py` 및 공통 `tests/e2e/long_run_runtime.py`. CX19와 같은 읽기 전용 CLI driver AST 확장을 사용한다. source anchor·driver SHA256·확장 목록을 기록하며 서비스 token은 일회성 로컬 시험용으로 12시간 만료한다. `latencies.json`, 원래 사건/알람 ID·순번·시각·각 session index를 포함한 `latency-observations.jsonl`, `resources.jsonl`, `reconciliation.json`, 최종 수락 JSON/JUnit/정산 JSON을 저장한다. 비밀 파일은 임시 runtime 경로에서 정리하며 저장소에 넣지 않는다.
