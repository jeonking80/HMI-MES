# CX-34 — 명시적 시작 예약

CX-33 뒤 LOAD_JOB/bind에 start_when_ready 기본false를 추가했다. 신규 요청의 두 정책을 각각 명시하고 기존 canonical은 필드별 원래 모양을 보존한다. API 직접 명령과 workflow 모두 load_job+operate 권한이 필요하다.

PLC의 성공한 원래 LOAD·execution·요청자·authority·설정을 검증한 예약만 READY에서 한 번 RUNNING으로 전이한다. 신규 START ID는 없다. 안전/모드 변경·재시작·복구·유효한 수동 START/END는 예약을 취소/소비하고 원인 감사를 남긴다. 정상 예열은 취소하지 않으며 취소 후 자동 재무장하지 않는다. 상태·사건·요약·감사·명령 결과를 같은 트랜잭션에 저장한다. 구버전 snapshot/저널은 예약 없음으로 처리하고 final hash를 변경하지 않는다.

START_RESERVATION.md·PROTOCOL.md와 command-request schema를 갱신했다. 구버전 snapshot 시험은 새 필드도 제거해 실제 이전 형식을 유지했다. 제어 안전·권한·exactly-once·원래 LOAD provenance·크래시 원자성 high 읽기 전용 검토에서 남은 backend 차단 사항은 없다. 구현·시험은 6.1-sol medium, 위험 검토만 high로 수행했다.

검증 결과는 아래에 기록한다. 공개 runtime·WO-T1·공개DB·생산 조작·배포는 수행하지 않았다. Claude 소유 UI parser가 LOAD 두 정책 필드와 기존 형식을 함께 지원하는 것은 공개 배포 선행조건이다.

## 검증 결과

최초 pytest 1회: 신규 policy/reservation, protocol, PLC, CX33 호환/자동종료, controller/retention, command store/API, workflow/control HTTP를 묶어 **404통과/fixture6오류,135.53초**. 오류는 신규 PostgreSQL fixture가 FK 대상 manager를 만들기 전에 recipe를 등록한 시험 데이터 문제였다. manager bootstrap만 추가하고 해당 두 함수의 매개변수6개만 재실행해 **6통과,11.56초**. 제품 추가 변경은 없다. 전체410개를 한 번에 통과했다고 표시하지 않는다.

변경 Python8개 Ruff check1회 및 format --check1회 통과. 이후 fixture의 사용자 생성 순서만 고쳤고 전체 검사 반복은 하지 않았다. 실제 예열/한 번 실행·안전 취소·구버전/독립 canonical 정책·유효한 수동 명령·재시작/복구·provenance 변조·arm/cancel/fire 트랜잭션 rollback 및 전후 subprocess 종료·실제 PG/ASGI 양쪽 경로 권한을 확인했다. 로그 `/tmp/hmi-cx34-tests.log`, `/tmp/hmi-cx34-fixture-recheck.log`.
