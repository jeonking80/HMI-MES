# CX-27 — 게이트웨이 메타데이터 장기 용량: 실측·설계 검토

## 범위와 판정

8차 지시서(`01a1480`)를 읽고 최신 main 반영을 확인했다. 운영 SQLite는 읽기 전용으로 backup API를 통해 복사했고 사본만 한 번 열어 조회했다. 독립 `gpt-6.1-sol high`가 설계와 기존 계약을 검토했다.

**판정: 현 지시서의 두 대체안을 그대로 고정 크기 해법으로 채택하지 않는다.** §2의 “기존 불변 조건을 해치면 채택하지 말고 이유를 적는다”에 따른 설계 차단이다. 단순 순번 체크포인트는 영구 batch-ID 충돌 검사를 대체하지 못하고, 범위·해시만으로 유실 근거를 바꾸면 원본 근거가 사라진다. 가역 압축은 가능하지만 무제한 누적을 고정 용량으로 바꾸지는 못한다.

원본 이관·실연은 실행하지 않았다. 관련 시험과 Ruff는 구현을 채택하지 않아 이번에 실행하지 않았으며, 과거 37개 통과를 이번 설계의 검증으로 재사용하지 않는다.

## 1. 사본 조회 1회

보호 사본과 수치 JSON은 Git 밖 `/tmp/hmi-v8-capacity/`에 보관했다. 원본 GatewayBuffer 생성자를 호출하지 않았으므로 INFLIGHT 재설정 등 시작 시 쓰기도 하지 않았다. 비밀값·업무 원문은 출력하지 않았다.

| 표 | 행 수 | sum(metadata_bytes) |
|---|---:|---:|
| batch_ledger | 4,753 | 4,334,969 |
| source_progress | 1 | 654 |
| missing_ranges | 453 | 5,664,074 |
| loss_intervals | 0 | 0 |
| 합계 | — | **9,999,697** |

한도는 그대로 10,000,000바이트이며 **여유는 303바이트**다. outbound_batches는 **0건**(PENDING/INFLIGHT 모두 없음)이다.

| ACK 표현 | 건수 | 저장된 ACK 본문 bytes |
|---|---:|---:|
| BLOB(기존 무손실 압축) | 3,813 | 1,204,535 |
| TEXT | 487 | 221,598 |

현재 확정 frontier와 기존 압축 제외 조건을 적용했을 때 미압축 확정 ACK **487건**, 같은 무손실 압축의 추가 회수 가능량은 **67,314바이트**다. 이는 향후 원장 기본 행 증가를 막지 않으므로 장기 해법은 아니다.

**현재 정체 경로는 사본과 코드로 확인된다.** 새 원장 한 행의 기본 계상량만 `512 + batch_id의 UTF-8 bytes + 64`로 여유 303바이트보다 크다. enqueue는 예산 검사에서 롤백되지만, 압축은 ACK 경로에서만 실행된다. 현재 큐가 비어 있어 새 ACK를 만들 배치도 없다. 회수 가능한 영수증이 남아 있음에도 이 경로로 회수할 수 없다. 이를 8차 전체 해법으로 오인해 압축 호출만 추가하지 않았다.

### 유실 1행의 구성

첫 loss body는 **11,991바이트**, 행 여유분 512를 포함한 계상량은 12,503바이트다. 다음은 필드 값의 개별 JSON 직렬화 크기이며 키·구분자 비용은 포함하지 않아 합계가 body와 같지는 않다.

| 필드 | 값 JSON bytes |
|---|---:|
| samples(48개) | **11,515** |
| capture_time | 137 |
| batch_id / loss_id | 각각 38 |
| detected_at | 34 |
| source_id / stream_id | 26 / 13 |
| reason_code | 18 |
| affected_execution_ids / event_ranges / reported_gaps | 각각 2 |

body의 약 96%는 48개 샘플의 ID·태그·품질·원래 시각 근거다. 원래 reading 값은 기존 유실 기록 정책에 따라 이미 제외돼 있다. 이 근거를 해시 하나로 바꾸는 것은 무손실 압축이 아니다.

동일 generation/source/stream/reason에서 연속된 loss capture는 **102~554, 453건의 한 구간**이다. 이는 **capture 구간**이며 생산 사건의 source-event 유실 구간을 뜻하지 않는다. 첫 loss의 event_ranges는 빈 배열이다. 숫자 102~554를 생산 사건 gap으로 만들어서는 안 된다.

453개 원문을 보존한 JSON 배열은 5,432,592바이트, zlib 압축 크기는 696,532바이트였다. 이는 메모리에서 측정한 가역 표현의 크기이며 운영 이관·복원 검증은 아니다. 미래의 임의 UUID·시각·품질 기록까지 계속 생성되면 이 표현도 계속 증가한다.

## 2. high 설계 결정

### A. 순번 체크포인트만으로 원장 대체 — 채택하지 않음

기존 계약은 동일 gateway/batch ID의 내용 충돌을 영속적으로 거절하고 동일 요청의 원래 ACK를 보존한다(`contracts/TRANSPORT.md`, `docs/architecture/GATEWAY_BUFFER.md`). 예를 들어 과거 `(batch_id=A, capture_seq=1)`을 접은 뒤 `(A, capture_seq=checkpoint+1)`을 넣으면 체크포인트 이하 순번 거절 규칙은 이를 막지 못한다. 서버의 후속 충돌 거절과 기존 게이트웨이의 로컬 영속 충돌 검사는 서로 다르다.

또한 verified_through_seq는 **source 사건**의 frontier이고 capture_seq는 **관측 배치**의 순번이다. 사건 없이 수천 개 capture가 같은 verified 값을 가질 수 있다. 두 숫자를 직접 비교해 접으면 안 된다. 원래 배치와 연결된 인증된 COMMITTED 영수증, 사건별 검증, gap/격리·보고 소유 관계를 각각 확인해야 한다.

순수 ACK 접두어만 접으면 102번부터 남은 EVICTED 원장이 뒤의 ACK 접기를 가로막는다. 예외 행을 남기는 별도 규칙이 필요하며, missing_ranges와 loss_intervals의 외래키·보고 영수증 소유 관계도 함께 보존해야 한다. 체크포인트 1행으로 바꾸는 것만으로 이 조건이 충족되지 않는다.

### B. 유실을 범위·개수·해시로 대체 — 채택하지 않음

범위·누적 해시는 내용의 약속이지 원본 데이터의 복원 수단이 아니다. 개별 sample_id, source/server/acquired 시각, 품질, capture_time, 사유, 원래 execution 영향, 보고 gap을 재구성할 수 없다. 해시 목록·차분·가역 컨테이너에 원문 정보를 모두 유지하면 안전한 공간 최적화는 가능하지만 임의 유실 이력을 영구히 고정 크기로 저장할 수는 없다.

서버 ingest_batches에는 수신한 배치와 영수증이 있어도 **한 번도 전달되지 않고 제거된 유실 샘플 근거 전부가 있는 것은 아니다.** 서버에 이미 있다는 전제로 해당 로컬 근거를 삭제할 수 없다. 유실 보관 여부가 바뀌어도 UNKNOWN·영구 gap·미정산을 정상/복구 완료로 바꾸어서는 안 된다.

## 3. 필요한 설계 변경과 영향 — 제안, 미구현

고정된 로컬 운영 창을 만들려면, 최소한 다음 보관 계약이 먼저 필요하다.

1. 접을 원장 ID·원래 ACK·유실 본문·보고 연결을 정확히 보존하는 영속 archive. 업로드한 ordered content/hash와 결부된 인증된 영속 수신 확인을 받는다. 미전송 유실 근거도 대상으로 포함한다.
2. 네트워크 업로드는 SQLite 트랜잭션 밖에서 수행하고, 확인된 보관 영수증을 검증한 뒤 **한 로컬 트랜잭션**으로 checkpoint·참조·원장 회수를 확정한다. 중단되면 재조회·재시작해도 근거가 먼저 사라지지 않아야 한다.
3. capture checkpoint와 source 사건 frontier를 별개로 정의한다. retired 로컬 요청은 명시적으로 retired/reconciliation 결과를 주고, 서버의 원래 영수증 재조회·충돌 검사는 유지한다.
4. 과거 ID의 새 순번 재사용을 막는 권위 있는 archive 조회 또는 사전 충돌 검증을 거친 주입적 신규 ID 규칙을 정한다. UUID 이력은 checkpoint 숫자만으로 대체할 수 없다. source·generation 초기화는 해법이 아니다.
5. archive가 닿지 않는 동안 유지할 미보관 창과 backpressure를 정한다. 제한된 저장 공간에서 임의로 긴 단절·새 유실 생성을 모두 무손실 수용한다는 보장은 하지 않는다. 원격 저장도 기존 무료 용량 한도·보관/복원 정책을 검토해야 하며 이 제안은 유료 서비스 생성 승인이 아니다.

이 변경은 로컬 영수증 재조회·중복 응답·외래키 소유 관계·복구 절차와 서버 보관 범위를 바꾸므로, 단순한 SQLite 표현 이관으로 취급할 수 없다. 원래 execution 귀속, 서버 사건 중복 제거·커서 원자성, UNKNOWN 보존은 계속 유지해야 한다.

## 9차 구현 — 검사 실패로 중단

9차 지시서(`eb4acba`)는 8차의 체크포인트·해시 대체안을 철회하고 가역 압축만 채택했다. 장기 archive는 범위 밖으로 남긴다. 최신 main 반영을 확인했고, 다음 코드를 준비했다.

- missing_ranges 행·ID·외래키·보고 소유 관계를 유지하며 본문만 버전 표식이 있는 zlib BLOB으로 저장한다. 기존 TEXT와 원래 UTF-8 바이트를 계속 읽고, 잘못된 버전·손상·미완결·후행 데이터·복원 한도 초과를 거절하는 경로다.
- body를 JSON으로 직접 조회하던 두 SQL 조건은 이미 검증된 소유 원장의 source/stream 조인으로 바꿨다. 압축 본문에 json_extract를 적용하지 않는다.
- enqueue와 ACK 처리의 같은 트랜잭션에서 용량 압박 시 확정 ACK·유실 본문 압축을 시도하고, 여전히 부족할 때만 METADATA_FULL로 롤백한다. 한도나 안전 조건은 바꾸지 않았다.
- 강제 압축 API와 명시적 오프라인 CLI `scripts/compact-gateway-metadata.py`를 추가했다. INFLIGHT를 바꾸지 않는 recover_inflight=False로 열고, 원래 ACK·유실 본문 bytes를 복원한 뒤 나머지 모든 행·필드·순번·참조·큐 상태가 같은지 비교하도록 준비했다. 새 DB 초기화·알 수 없는 기존 스키마는 거절한다.

독립 high 검토는 구현의 읽기 경로·바이트 계상·외래키 보존·압축 트랜잭션·오프라인 상태 보존을 확인했다. CLI의 최종 전체 의미 비교는 압축 커밋 **후** 검사이므로, 그 사후 비교의 불일치까지 롤백된다고 주장하지 않는다. 압축 자체의 오류와 내부 검증은 로컬 트랜잭션 경계 안에 있다. 아직 실제 사본 이관으로 검증한 것은 아니다.

### 검사 결과 — 각 1회

관련 네 시험 파일의 한 번 실행 결과는 **2 failed, 37 passed in 1.54s**다. 실패한 신규 시험은 다음 두 개다.

- test_queue_empty_303_bytes_free_enqueue_compacts_loss_before_budget_check
- test_force_compaction_exact_bytes_validation_and_atomic_rollback

두 시험 모두 fixture가 `Line.GoodTotal.0`~`.39`라는 **등록되지 않은 태그**를 만들어 BatchBody 검증에서 실패했다. 태그는 단순히 서로 다른 식별자이기만 해서는 안 되고 v1 태그 사전과 선언 자료형에 맞아야 한다. 이 조건을 사전에 충분히 확인하지 않은 Codex의 시험 데이터 오류다. 신규 압축·303바이트 정체 해소·롤백 검증에 도달하기 전 실패했으므로 해당 동작을 통과로 표시하지 않는다. 운영 데이터나 실제 태그 사전이 잘못됐다는 뜻은 아니다.

구현 파일 3개에 formatter를 한 번 적용한 후 Ruff check와 format --check를 한 번씩 실행했고 모두 통과했다. 실패 뒤 코드 수정·시험 재실행은 하지 않았다.
