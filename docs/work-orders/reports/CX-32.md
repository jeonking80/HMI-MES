## 변경과 계약

RecipeRegistrationRequest/WorkOrderRegistrationRequest는 별도 입력 모델이며 기존 불변 Definition은 그대로다. recipe id/version 모두 생략/null/빈 문자열이면 서버가 그룹의 다음 숫자 vN과 `{recipe_id}-vN`을 발급한다. 부분 생략·공백은422다. work-order id 생략/null/빈 문자열은 KST planned_date의 `WO-YYYYMMDD-NNN`을 발급하며3자리는 최소 폭이다. 자동 방식에는 request_id가 필수이고 수동 방식은 기존대로 또는 선택적 키와 함께 동작한다.

request별 잠금과 종류별 공유 registration 잠금이 자동/기존 직접 Python 수동 writer를 직렬화한다. counter는 기존 번호 및 점유 ID를 반영하고 안전하게 건너뛰며 길이를 자르지 않는다. 범위 초과는 고정422다. counter 증가·정의·audit·불변 원래 응답 영수증이 같은 트랜잭션에서 커밋/롤백된다. 임의 SQL로 잠금을 우회한 삽입 경로를 자동 재시도하는 것은 범위 밖이다.

같은 key/원래 actor/정규화된 본문은 최초 응답을 그대로 반환한다. 다른 본문/actor는409 ID_CONTENT_CONFLICT다. GET /api/v1/registration-receipts/recipe 또는 /work-order의 request_id query로 원래 계정의 새 세션도 조회 가능하고 다른 actor에는404다. work order가 이후 변경돼도 최초 DRAFT 응답을 보존한다. 결과 불명 시 새 key를 만들지 않는다. 기존 역할·Origin/CSRF·body size 및 수동 응답 형식은 유지한다.
