# CX-28 — 화면 API 조회 경로 개선

## 상태

10차 지시서(`af4515e`)를 읽고 최신 main 반영을 확인했다. 관련 PostgreSQL/HTTP/WS 검사 **111개는 통과**했으나 새 성능 측정 스크립트의 Ruff E402 **15건**으로 단일 검사 단계가 실패했다. 기존의 실패 시 중단 지시와 검사 각 1회 조건에 따라 추가 수정·재실행 없이 중단했다. **5,000건 성능 측정·EXPLAIN 실측은 미실행**이며 p95 목표 통과 또는 배포 준비 완료라고 판정하지 않는다.

제품·UI·공개 DB·Vercel은 실행 또는 변경하지 않았다. 테스트는 각 모듈 전용의 새 PostgreSQL 17 컨테이너만 사용했고 정상 정리됐다. 보호된 기존 preview 컨테이너는 유지했다. 실연·이력 삭제·폴링 2.5초/최신성 3초 조건 변경은 하지 않았다.

## 변경

### 완전 수집 경로

현재 작업 브랜치의 `apps/api/user_http.py` 두 read_snapshot 호출은 이전 `fc6296e`에서 이미 prefer_complete_capture=True를 사용한다. origin/main에는 아직 이 두 인자가 없다. 이번 작업에서 이를 유지하고 `apps/api/screen_ws.py`에도 같은 인자를 추가했다. 최근 관측 배치가 완전할 때만 한 건을 읽고, 그 배치의 BAD·불명·null도 그대로 보존한다.

**통합 주의:** 이번 신규 커밋만 선별 적용하면 기존 HTTP fast-path 변경까지 자동 포함되는 것은 아니다. Claude가 전체 브랜치를 통합하거나 기존 HTTP 인자 변경을 함께 반영해야 한다. 배포는 Claude 담당이다.

### 부분 수집 경로

기존 DISTINCT ON은 해당 scope의 모든 배치에서 samples를 펼친 뒤 태그별 최신값을 골랐다. 변경 경로는 활성 태그별로 다음을 수행한다.

1. 같은 source/stream 및 현재 gateway/generation에서 해당 태그를 포함하는 배치를 찾는다.
2. capture_seq 내림차순 LIMIT 1로 먼저 배치 한 건을 선택한다.
3. 그 배치의 samples만 펼쳐 해당 태그를 반환한다.

이력 시각·최근 N건·품질로 자르지 않는다. 따라서 수천 건 이전의 BAD 관측도 최신 해당 태그라면 남고, 새로운 BAD/null/UNCERTAIN을 건너뛰어 과거 GOOD으로 채우지 않는다. capture 순번이 같은 현재 gateway/generation 배치는 기존 unique index가 금지하므로 순서가 모호해지지 않는다.

**상한의 의미:** 유효한 intake는 배치당 최대 48개 고유 태그이므로 JSON 펼침은 최대 활성 태그 수×48개다. 다만 드물거나 없는 태그의 JSON containment 검색이 살피는 원본 배치 수까지 고정된 것은 아니다. 기존 `uq_batch_capture_identity(gateway_id,capture_generation,capture_seq)`의 역순 탐색을 이용하며, 이 방식만으로 모든 분포에 대한 이력 독립적인 I/O·지연 상한을 보장하지 않는다. 새 인덱스·이관은 추가하지 않았다.

독립 gpt-6.1-sol high 검토는 source/generation 격리, 오래된 BAD 보존, 최신 BAD/null 우선, 트랜잭션 일관성에서 차단 결함을 발견하지 않았다. 실제 쿼리 계획·성능 검증을 대신하지 않는다.

## 시험

한 번의 실행:

```sh
.venv/bin/python -m pytest -q \
  tests/integration/test_snapshot.py \
  tests/integration/test_analytics_query_performance.py \
  tests/integration/test_screen_http.py \
  tests/integration/test_screen_ws.py \
  tests/integration/test_app_screen_ws.py \
  tests/integration/test_user_http.py \
  --junitxml=/tmp/hmi-v10-tests.xml
```

**111 passed in 121.51s.** 로그는 `/tmp/hmi-v10-tests.log`, JUnit은 위 경로다. 완전/부분/사건 전용/기존 generation/나쁜 품질의 opt-in 동등성, HTTP·WS·인증 경로를 포함한다. 신규 회귀는 더 오래된 GOOD 뒤의 BAD/null이 5,000개 무관한 부분 수집 후에도 seq2의 원래 BAD로 남고 heartbeat는 최신 seq5003에서 읽히는지 직접 확인한다. 동일한 새 함수를 서로 비교하는 것만으로 의미 보존을 주장하지 않았다.

구현 단계에서 formatter를 적용한 후 변경 5개 Python 파일의 Ruff check를 한 번 실행했다. **scripts/benchmark-screen.py의 E402 15건**이 실패했다. sys.path 조정 뒤의 모듈 import 배치를 Ruff 규칙에 맞게 준비하지 못한 Codex의 오류다. 연결된 format --check는 앞선 lint 실패로 미실행이다. 기존 제품·회귀 파일의 별도 lint 오류는 보고되지 않았으나 전체 Ruff 통과로 표시하지 않는다.

## 성능·계획 검증 준비물과 미실행 범위

`scripts/benchmark-screen.py`는 새 임시 PostgreSQL 17만 만들고 상속 DSN을 사용하지 않는 측정 도구로 준비했다. 유효한 48태그 첫 capture의 BAD 한 태그가 5,000개 후속 부분 capture에서 빠져 있는 fixture와 최신 완전 capture를 각각 읽도록 구성했다. 실제 localhost HTTP 로그인·비밀번호 변경 뒤 각 30회 직렬 화면 응답의 p95≤0.5초, 원래 BAD·증거 일치를 확인하고 기존 DISTINCT ON과 새 쿼리의 EXPLAIN ANALYZE BUFFERS를 남기도록 했다.

**이 도구는 아직 실행하지 않았다.** 도구가 기대대로 동작하는지와 5,001/5,002건 API p95 및 계획 전후 수치는 미검증이다. SQL fixture 복제는 intake 처리량 검증이 아니고, 준비된 측정은 DB/OS 캐시를 비우거나 10명 동시성을 검증하는 것도 아니다. 지시서에 인용된 공개 886ms/56ms는 Claude의 기존 측정이며 이번 로컬 전후 실측으로 사용하지 않았다.
