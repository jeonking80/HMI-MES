# CX-42 — 20차 FIFO 복구 비용과 보관 종료 ID 저장량

동일 기계에서 수정본의 FIFO 복구 시간과 API 호출당 비용이 main보다 줄었고, 통합1,893개 단일 실행·실제 browser 경로가 통과했다. ID 저장은 재작성 없는 세그먼트로 바꿨지만, 기존 알람 FK를 보존한 채널1은 계속 증가한다.

## 기준과 범위

`codex/kuls-backend-v3`의 `a5e2dd0` 이후, 지시서 커밋 `7287479`를 포함한다. 비교 main은 실행 시 원격의 최신 **`f9926d0aa0e09f85d90e2a06ff6337f7d5de9251`**로 고정했다. 지시서의 Claude 측정 `ea5ac0e`와 다른 기준임을 명시한다. 기존 E2E 미커밋 파일 2개·UI·공개 DB·Vercel·사용자 운영 runtime은 수정하지 않는다.

환경 중단 뒤 복구된 같은 기계에서 main 아카이브 사본과 수정본을 순서대로 측정한다. Git worktree를 새로 만들지 않았으며 Python 환경·Node 의존성·고정 PostgreSQL 이미지·시험 fixture와 1,800건/300초 기준을 공유한다. 성능 시험 중 다른 시험 부하는 겹치지 않는다.

## 원인과 수집 경로 변경

코드 이력에서 `2cea66c`는 수집 커밋 뒤 매 요청이 정리 함수의 새 연결·두 `SET LOCAL`·schema/스케줄 조회를 기다리게 했다. `a5e2dd0`는 clock 최근접 이웃 조회에도 영수증·범위 endpoint 전체의 중복 제거 `UNION`을 사용했다. 반복 정리 호출과 이력 조회의 추가 비용을 도입한 구체적인 커밋이다. 각 비용의 독립적인 인과 기여도를 수치로 확정하는 커밋별 이분 실행은 하지 않았으며, 실제 비교는 아래 동일 기계의 결과를 따른다.

- 수집 ACK 본문을 먼저 전송한 뒤 invocation 소유 `BackgroundTask`에서 제한된 정리를 실행한다. ASGI 완료는 정리를 기다리므로 daemon의 임의 종료에 의존하지 않는다. engine별 진행 중 1개·완료 뒤 60초 cooldown을 적용하고 DB의 전역 주기·잠금·500ms 예산·1,500ms timeout·원자적 보호는 그대로 유지한다.
- 같은 트랜잭션의 schema revision 조회를 공유한다. 연결 풀 전체에 revision을 영구 캐시하지 않는다.
- 최근접 clock 이웃은 중복 좌표가 무해한 `UNION ALL`로 조회한다. 최초 역행 재구성·보고서 이력은 중복 제거를 유지한다.
- 충돌 검사·gateway/source 잠금 뒤 실제 새 부모 행을 삽입한 경로만 clock 근거의 중복 존재 조회를 생략한다. 기존 근거의 PK/FK·해시·입력 검증은 유지한다. 이 조회는 main에도 있던 것이므로 회귀의 신규 원인으로 분류하지 않고 추가적인 비용 절감으로 구분한다.

## FIFO 비교

main 원래 fixture는 환경 재시작 후 kernel uptime이 1,800초 미만이라 음수 monotonic 검증에서 **8.85초에 실패, ingest 0건**이었다. 이는 복구 시간 측정이 아니다. 이후 이미 19차에서 검증한 양수 시각·별도 epoch fixture를 main 사본과 수정본 양쪽에 동일 적용했다. main 제품 코드는 바꾸지 않았고 사건 수·deadline을 완화하지 않았다.

| main `f9926d0`, 공통 fixture | PASS | 119.9514 | 147.53 | 1,921 / 84.2415 | 0 |
| 제품 `005d080` | PASS | 114.5299 | 143.96 | 1,916 / 78.0848 | 0 |

## 추가 이관과 정확 ID

`0024_ingest_retired_segments`는 기존 schema23 청크를 수정·삭제하지 않고 새 append-only 세그먼트를 추가한다. 정리 회차의 적격 영수증을 최대 256개씩 묶어 한 번 삽입하고, 같은 트랜잭션에서 미참조 영수증만 지운다. segment UPDATE/DELETE/TRUNCATE와 기존 청크 재작성을 거절한다.

소문자·하이픈 포함 36자 UUID 정규형만 `uuid[]`의 16바이트 값으로 저장한다. 대문자·하이픈 없는 표기·일반 ID는 원문 `text[]`로 남긴다. 입력 조회에도 동일한 조건을 사용하여 서로 다른 문자열을 UUID 정규화로 합치지 않는다. 이전 청크와 새 세그먼트를 함께 조회해 gateway 전체의 batch ID와 capture identity 410 거절을 유지한다. 확률 필터나 해시만의 판정으로 바꾸지 않는다.

실제 FK 참조와 정산·누락·격리·미결 명령 보호는 유지한다. 시계 endpoint·최신 context·최초 역전 기록을 보존하며 사용된 segment가 있으면 downgrade를 거절한다. 빈 segment만 schema 잠금과 테이블 잠금 아래 정확한 schema23 함수·권한으로 복원할 수 있다. 이관은 기존 원본·청크·영수증을 지우지 않는다.

## 교차 적재 용량 측정

알람 채널 0개와 1개를 각각 1,440회 × 60 capture로 적재하고 정리한다. 임시 DB에만 설치된 부모·자식 정리 함수의 복사본이 같은 `real clock + session offset`을 사용한다. 원래 DB 시계와 제품 함수는 바꾸지 않으며 두 함수의 500ms 차이·SQL timeout·잠금·주기는 유지한다. 실제 원본 SQL과 복제 SQL, 치환 목록·SHA를 측정 artifact에 남긴다. 정리 상태의 throttle을 초기화하거나 삭제 자격을 우회하지 않는다.

27개 실제 태그의 약 6.8KB 계약 본문·고유 ID·개별 canonical SHA를 사용한다. 채널 1개는 실제 AlarmConsumer를 매 capture마다 실행해 UNKNOWN 판단과 실제 FK를 남긴다. Bad/null·UNKNOWN 자료의 저장 측정이며 트렌드 투영·PLC·GOOD 시각 근거·실제 24시간 운전을 대표하지 않는다. 매시간 상당에 일반 VACUUM을 수행한다. 각 public 테이블의 파일 크기와 살아 있는 각 열의 `pg_column_size` 합을 구분한다.

## 6절 후속 — 종료 뒤 대기열 연결 (Claude e4d5815 기준)

사용자가 요청한 6절만 수행하고 Claude `e4d58154074115e2760f50d64ac66b864bcdc730`을 같은 브랜치에 병합했다. 1~5절의 FIFO·용량·통합 전체 시험은 반복하지 않았다.

`Sealer.Ready`는 예열 후 START 조건이며 실제 simulator는 종료한 실행에서 False를 내보낸다. `_safe_values`에서 **True 요구만 제거**했다. 해당 태그의 존재·GOOD/non-null·신선도와 정지·구간 출력/속도0·WIP0·REMOTE/AUTO·가드·permissive·fault·하트비트·정산·세대·권한·원래 명령 ID 검사는 유지한다. 최종 `bind_work_order`와 PLC의 LOAD/START 검증도 그대로다.

일시적인 대기는 `blocked_reason`으로 노출하되 자동 연결·정책 revision은 바꾸지 않는다. 값이 달라질 때만 기록해 반복 poll의 쓰기·감사를 늘리지 않는다. 원래 LOAD 대기, 이전 정산 대기, 초기 수동 연결 필요, 신선한 자료 부재와 구체적인 LOAD 조건 미충족을 구분한다. 연결 성공·수동 연결 확인·빈 대기열에서는 일시적 이유를 해제한다. 실패·만료·결과 불명·권한 회수 등의 기존 영구 `_block`은 유지한다.

시험 fixture의 강제 `Sealer.Ready=True`를 실제 simulator의 `project_tags` 출력으로 교체했다. ENDED/STOPPED·WIP0·ReadyFalse를 확인한 뒤 원래 대기열 LOAD ID가 실제 controller에서 SUCCEEDED가 되고 중복 명령을 만들지 않는 회귀 시험을 추가했다. Ready의 Bad/null 자료와 안전 조건 손상은 계속 거절한다.

- high 읽기 전용 안전 검토 통과.
- 관련 통합 **153개 모두 통과, 104.18초**. Ruff·format 변경2개 통과.
- 최신 Claude UI를 polling build해 수정하지 않은 `check-operable-system.py --extended-dir`를 **1회 실행**했다. 기본 생산/SETTLED, E1 목표 자동 종료, E2 속도 변경은 통과했다.
- E3의 첫 `queue-1`은 BOUND가 됐고 실제 simulator가 새 실행 ID로 LOADED/READY에 도달했다. 종료 상태 ReadyFalse 때문에 아무 동작도 하지 않던 서버 버그는 이 경로에서 해소됐다.
- **E3 전체 통과는 확인하지 못했다.** 이후 스크립트1031행의 `page.reload()`가 앱의 메모리 세션을 지우는데 재로그인하지 않고 `#workspace-operations`를 클릭해 TimeoutError로 중단됐다. `apps/web/src/App.tsx:26`에 새로고침 시 재로그인이 필요하다는 의도적 정책이 있다. 따라서 queue-1 START/종료와 queue-2 연결은 이번 브라우저 실행에서 미실행이다.

```text
playwright._impl._errors.TimeoutError: Locator.click: Timeout 25000ms exceeded.
  - waiting for locator("#workspace-operations")
FAIL: TimeoutError (E3 line queue loads the next order after settlement)
```

지시서6절의 “스크립트는 Claude 소유이며 실행만” 범위를 지켰다. UI·스크립트 변경이나 인증 우회·검사 monkey patch·재시도로 실패를 숨기지 않았다. Claude 측에서 새로고침 뒤 테스트 계정의 재로그인 단계를 보완해야 E3 후반을 검증할 수 있다. API의 일시적 `blocked_reason`에서 `auto_advance=true`를 유지하므로, 기존 UI의 일괄적인 재활성화 안내 문구도 향후 구분이 필요하다(UI 미수정).
