## 0. 새 기준 — 왜 다시 정하는가

사용자가 공개 사이트를 직접 써 본 평가(2026-10-25):

1. **입력이 수동적이다.** 설정 ID·그룹·버전·품목을 손으로 쳐야 했다. 품목과 설정이 많아지면 외울 수 없다.
2. **자동화 시스템답지 않다.** 배포·연결·시작·종료를 모두 사람이 단계마다 확인 버튼으로 넘겨야 한다. 목표 수량에 닿아도 멈추지 않는다.
3. **제어할 수 있는 것이 너무 적다.** 운전 중에 할 수 있는 것은 일시 정지·종료·고장 리셋뿐이다.

Claude가 화면에서 먼저 바꾼 것(`apps/web`, 서버 변경 없음):

- 공정 설정: 품목·기존 설정을 고르면 그룹·버전(vN+1)·설정 ID를 자동으로 채운다. 온도·속도는 최근 설정값으로 채우고 PLC 허용 범위를 먼저 검사한다.
- 작업지시: ID를 `WO-YYYYMMDD-NNN`으로 자동으로 채운다. 최근 설정, 오늘 날짜, 라인을 기본으로 고른다. **등록하고 바로 배포** 버튼과 **배포 확인 · 실행 연결로 이동** 버튼을 넣었다.
- 운전: PLC 상태별 단계 안내, 다음에 누를 버튼 강조, 목표 대비 양품 진행 막대를 넣었다. 끝난 명령(성공·실패 확정)은 다음 명령을 막지 않는다.

**화면만으로는 풀 수 없는 것을 이 지시서가 다룬다.** 새 기준은 다음과 같다.

- 사람은 "무엇을 만들지"와 "시작·중단·이상 조치"만 정한다. 번호 매기기, 단계 넘기기, 목표 도달 종료, 다음 작업 연결은 시스템이 한다.
- 안전 불변 조건은 그대로다: PLC 최종 판정, 결과 불명 시 새 ID 자동 재실행 금지, 원래 execution_id 귀속, 불명을 정상으로 대체하지 않음, 원격 비상정지 해제 금지.

## CX-31. 409 거절 사유 코드

- **현상:** `apps/api/work_orders_http.py` `mapped()`는 모든 충돌을 같은 문구 `registration conflicts with immutable content`로 돌려준다. 화면은 왜 거절됐는지 알려 줄 수 없다. 2026-10-25 실연에서 이 때문에 원인 파악에 30분 넘게 걸렸다.
- **요구:**
  - 409 본문에 고정 코드 `{"detail": ..., "reason_code": "..."}`를 넣는다. 예: `RESERVED_EXECUTION_NOT_SETTLED`, `WORK_ORDER_VERSION_CHANGED`, `WORK_ORDER_ALREADY_BOUND`, `FRESH_SOURCE_REQUIRED`, `PHYSICAL_EXECUTION_MISMATCH`, `ID_CONTENT_CONFLICT`.
  - 명령 API(`/api/v1/commands`)의 사전 판정 409도 같은 방식으로 사유 코드를 준다. 예: `CONTROL_VERSION_STALE`, `STATE_NOT_ALLOWED`.
  - 코드 목록을 `contracts/`에 고정한다. 비밀값이나 내부 경로는 넣지 않는다.
- **시험:** 사유별 409 코드 시험.
- **Claude 후속:** 화면에서 코드별 한국어 안내를 보여 준다.

## CX-32. 서버 ID 자동 발급

- **이유:** 지금은 화면이 목록을 보고 다음 번호를 계산한다. 두 사람이 동시에 등록하면 같은 ID가 겹칠 수 있다.
- **요구:**
  - `POST /api/v1/recipe-versions`: `id`·`version`을 비우면 서버가 그룹의 다음 버전(`vN+1`)과 `{recipe_id}-vN`을 한 트랜잭션에서 발급한다.
  - `POST /api/v1/work-orders`: `id`를 비우면 `WO-YYYYMMDD-NNN`(KST 예정일 기준)을 발급한다.
  - 응답에 발급된 ID를 담는다. 결과 불명 재조회를 위해, 클라이언트가 보낸 멱등 키(`request_id`)로 원래 발급 결과를 다시 찾을 수 있어야 한다.
  - ID를 직접 지정하는 기존 방식은 유지한다.
- **시험:** 동시 2건 등록 시 번호가 겹치지 않음, 같은 `request_id` 재요청 시 같은 ID 반환.

## CX-33. 목표 수량 도달 시 PLC 자동 종료

- **요구:**
  - 작업지시(또는 LOAD_JOB 인자)에 `auto_end_at_target`(기본 true)을 둔다.
  - PLC가 양품 수가 목표에 닿은 것을 판정하면 신규 투입을 멈추고 재공을 정리한 뒤 END한다. 판정 주체는 PLC다.
  - 상태 사건과 실행 요약은 원래 execution_id에 귀속한다. 종료 원인을 요약에 남긴다(`end_reason: TARGET_REACHED | OPERATOR`).
  - 재공 정리 중 초과 생산분은 지금 규칙대로 양품·불량·폐기로 셈한다.
- **시험:** 목표 도달 → 자동 END → SETTLED. false면 지금처럼 계속 운전. 결과 불명 중에는 자동 종료가 새 명령 ID를 만들지 않음.
- **Claude 후속:** 작업지시 화면의 선택칸, 운전 화면의 종료 원인 표시.

## CX-34. 시작 예약 (예열 완료 시 자동 시작)

- **요구:**
  - LOAD_JOB 인자 또는 별도 명령으로 `start_when_ready`를 받는다. PLC가 READY에 닿으면 스스로 START 전이를 한다.
  - 예약은 사람이 명시적으로 한 요청으로 감사에 남긴다. 예열 중 안전 입력·모드가 바뀌면 예약을 취소하고 사유를 남긴다.
  - 원격 비상정지 해제는 여전히 하지 않는다.
- **시험:** READY 도달 → 자동 RUNNING, 예열 중 가드 열림 → 예약 취소, 결과 불명 시 재실행 없음.

## CX-35. 운전 중 속도 조정

- **현상:** `control_http.py`는 `SET_PARAMETERS`를 실행 중이 아닐 때만 허용한다. 그런데 종료 뒤에도 `Line.ActiveExecutionId`가 남아 사실상 항상 거절된다.
- **요구:**
  - RUNNING·PAUSED 중 속도 변경을 허용한다. 허용 범위는 레시피 기준값의 ±20%이고, PLC 허용 범위(1~60 m/min) 안이어야 한다. 온도 변경은 이번 범위가 아니다.
  - 변경은 PLC가 판정한다. 상태 사건(`PARAMETERS_CHANGED`)으로 원래 execution_id에 귀속하고, 감사에 남긴다.
  - 실행 요약에 변경 이력을 남긴다. 정산 규칙과 충돌하지 않게 한다.
- **시험:** 범위 안 변경 성공, 범위 밖 거절, 변경 뒤 정산 SETTLED.
- **Claude 후속:** 운전 화면에 속도 조정 칸을 넣는다.

## CX-36. 다음 작업 자동 연결 (작업 대기열)

- **요구:**
  - 라인별 대기열 순서를 둔다. 배포된 작업지시에 순번을 매긴다.
  - 현재 실행이 SETTLED이고 라인이 STOPPED·재공 0이면, 서버가 대기열 첫 작업을 bind하고 LOAD_JOB을 보낸다.
  - 자동 연결은 사람이 켠 라인 설정(`auto_advance`)일 때만 한다. 결과 불명이면 멈추고 사람에게 넘긴다(새 ID 재시도 금지).
  - 감사와 화면 조회 API(대기열 목록·순서 변경)를 둔다.
- **시험:** 2건 대기열 → 첫 작업 종료·정산 → 두 번째 자동 연결 → SUCCEEDED. 정산 PENDING이면 연결하지 않음.

## CX-37. 품목 마스터

- **요구:** 품목 테이블(ID, 이름, 단위, 사용 여부)과 목록·등록 API. 공정 설정과 작업지시는 등록된 품목만 쓴다. 기존 데이터의 품목은 이관 때 자동으로 등록한다.
- 공개 DB 이관이 필요하다. 이관 배치와 롤백 계획을 만들고, 적용은 Claude가 한다.
