## 1. 원인 (Claude 측정, 2026-10-24)

마지막 실연에서 화면은 `stopped`("화면 연결 확인 필요")로 끝났다. 화면 갱신이 한 번도 제때 끝나지 못했기 때문이다.

- 공개 `/api/v1/screen`을 게스트로 15회 호출했다. **15회 모두 3.56~3.85초**가 걸렸다. 같은 경로에서 `/api/ready`는 0.44~0.80초, 정적 페이지는 0.22초였다. 즉 서버 처리에만 약 3초가 든다.
- 화면 폴링은 2.5초 안에 응답이 없으면 실패로 본다(`apps/web/src/screenPolling.ts` `SCREEN_POLL_TIMEOUT`). 5회 연속 실패하면 `stopped`가 된다. 그래서 응답이 매번 3.6초 걸리면 버튼은 한 번도 활성화될 수 없다. 이 시한은 3초 최신성 조건과 연결된 안전 조건이므로 늘리지 않는다.
- `/api/v1/screen`은 `read_snapshot(prefer_complete_capture=False)`를 호출한다. 이 경로는 `apps/api/snapshot.py` 145행의 `DISTINCT ON` 쿼리를 탄다. 이 쿼리는 보관된 **모든** 배치의 표본을 펼친다.
  - Neon `EXPLAIN ANALYZE` 결과: 4,798배치 × 48표본을 펼쳐 **886ms**가 걸렸다. 이력이 쌓일수록 느려진다.
  - 최신 완전 수집 1건을 읽는 쿼리(`latest_sample_capture`)는 **56ms**였다.
  - 대시보드는 이미 `prefer_complete_capture=True`를 쓴다(`apps/api/dashboard.py` 31행).

## 2. 할 일

1. **화면 API 빠른 경로.** `/api/v1/screen`과 WS 스냅샷이 최신 완전 수집이 있으면 그 1건을 쓰게 한다(대시보드와 같은 경로). 부분 수집일 때만 기존 태그별 조회를 쓴다.
   - 의미가 바뀌면 안 된다. 최신 완전 수집이 이전 관측을 모두 대체한다는 기존 주석(snapshot.py 124~126행)의 규칙 그대로다.
   - BAD·불명 표본을 더 오래된 GOOD 값으로 채우지 않는다.
2. **부분 수집 경로도 상한을 둔다.** `DISTINCT ON`이 전체 이력을 펼치지 않게 한다. 예: 태그별 최신 관측 인덱스나 최근 범위 제한. 단, 오래된 BAD 태그를 놓치지 않는 근거를 적는다.
3. **시험(각 1회).** 다음을 확인한다.
   - 완전 수집과 부분 수집에서 기존 스냅샷 시험이 같은 결과를 낸다.
   - 응답 시간 측정: 로컬 PostgreSQL에 5,000배치 이상을 넣고 화면 API p95가 0.5초 이하다.
   - 관련 단위 시험과 Ruff는 1회씩만 실행한다.
4. **배포 후 측정.** main 병합·배포는 Claude가 한다. Codex는 PR 준비까지만 한다.
