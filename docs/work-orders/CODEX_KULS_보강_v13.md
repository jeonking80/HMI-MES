# 작업지시서 — KULS 보강 13차 (Codex: 게이트웨이 메타데이터 한도 50MB)

- 발행: 2026-10-25, Claude
- 수행: Codex. 최신 `main`에서 브랜치 `codex/kuls-backend-v3`로 작업한다.
- 위험도: medium. 한도 숫자와 문서만 바꾸고 보존 규칙은 바꾸지 않는다.
- **사용자 결정(2026-10-25): A안.** 한도를 10MB에서 50MB로 올린다. 장기 보관 설계(B안)는 이번 범위가 아니며 미해결로 남긴다.
- PR·병합·배포·공개 확인은 Claude가 한다. Codex는 푸시하고 커밋 해시만 알린다. UI 파일은 수정하지 않는다.

## 1. 배경

- 2026-10-25 04:01:33Z부터 공개 runtime이 `BufferFull / METADATA_FULL`로 수집을 멈췄다. 확인 시점에 COMMITTED 140건, 수집 차단 282건이었다. 9차 무손실 압축으로 5.41MB까지 줄였지만, 원장은 운전 시간에 비례해 다시 찼다.
- 설계 때 10MB의 근거는 30분 단절 버퍼였다. 단절이 없어도 1초마다 쌓이는 확정 원장의 증가 속도는 계산하지 않았다.
- 공개 DB는 현재 152MB다(무료 0.5GB). 수집 원본만 건당 약 6.5KB가 들어 10~15시간 운전이면 DB가 먼저 찬다. 50MB는 이 운전 시간과 비슷한 수준이다.

## 2. 할 일

1. **실측(사본, 읽기 전용 1회):** 운영 SQLite 사본에서 표별 `metadata_bytes` 합계와 행 수를 기록한다. 수집 1건당 원장 증가량(바이트/건)을 계산한다.
2. **한도 변경:** `apps/gateway/buffer.py`의 기본 `max_metadata_bytes`를 50,000,000으로 바꾼다. 운영 실행 설정(`deploy/plant_runtime.py` 등)에서 따로 넘기는 값이 있으면 같이 맞춘다. 다른 한도(30분, 100MB)는 바꾸지 않는다.
3. **문서:** `docs/architecture/GATEWAY_BUFFER.md` 25행 부근에 아래를 적는다.
   - 변경 이유와 영향
   - 1번 실측 증가량으로 계산한 "50MB로 1Hz 연속 운전 시 버티는 시간"
   - 한도에 닿으면 지금처럼 `METADATA_FULL`로 안전 정지한다는 점
   - 장기 운영에는 서버 보관 설계(CX-27 §3)가 필요하며 미구현이라는 점
4. **시험(각 1회):** 한도 관련 기존 버퍼 시험이 새 기본값에서도 통과하는지 확인한다. 시험이 10MB를 직접 가정하면 시험에서 한도를 명시적으로 넘기게 고친다. 관련 게이트웨이 시험, `tests/unit` 전체, Ruff, 포맷 검사를 돌린다.
5. **푸시:** 커밋 해시만 알린다.
6. **운영 적용(배포 후, 사용자 요청 시):** 현재 runtime을 정상 종료하고 새 코드로 다시 시작한 뒤, `METADATA_FULL` 없이 수집이 이어지는지 확인한다. 기존 SQLite는 초기화하지 않는다.
