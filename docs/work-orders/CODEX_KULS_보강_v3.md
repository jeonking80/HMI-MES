## OPS-02. 공개 DB 0018 이관과 원격 시간 근거 활성화

[docs/architecture/OPS-02_CLOCK_MIGRATION.md](../architecture/OPS-02_CLOCK_MIGRATION.md)의 절차를 그대로 따른다. 추가 요구:

1. **선행 조건:** 공개 운영 배포가 `430fbf6` 이상이고 `/api/ready`가 ready다. 이관 전에 OPS-01과 같은 방식으로 전체 논리 백업을 받는다. 테이블별 행 수가 DB와 일치해야 한다. 비밀값이 든 백업은 저장소에 넣지 않는다.
2. **이관:** `deploy/neon-http/upgrade-0017-0018.json`, `grants-0018.json`을 각각 한 트랜잭션 배치로 적용한다. 같은 커밋에서 다시 생성한 결과와 `cmp`로 같은지 먼저 확인한다.
3. **runtime 권한 실측:** `hmi_app` 연결로 신규 테이블 조회, 허용 경로, 금지 UPDATE/DELETE/TRUNCATE/DDL 거절을 실제로 실행한다. 명시적 트랜잭션에서 실행하고 롤백한다.
   - OPS-01에서는 이 실측을 하지 못했다. 소유자는 `hmi_app`으로 `SET ROLE`할 수 없고, `-pooler` 시크릿은 헤더 오류였다.
   - 이번에도 runtime 연결을 쓸 수 없으면 "미실행"으로 기록한다. 카탈로그 조회로 대신했다고 통과 처리하지 않는다.
4. **활성화:** Vercel `HMI_CLOCK_MEASURED_ROUND_TRIP=true` → 재배포 → `/api/ready`, 로그인, 게스트, 분석 조회, 챗봇 응답 1회를 확인한다.
5. **짧은 실연:** [PUBLIC_DEMO_RUN.md](../architecture/PUBLIC_DEMO_RUN.md)대로 로컬 PC 게이트웨이를 `--clock-measured-round-trip`으로 연결해 짧게 운전한다. 다음을 확인한다.
   - 새 캡처의 트렌드 GOOD 값
   - 가동 시간 > 0
   - 불명 구간의 근거
   - 원래 실행의 수량 대조
   - 전후 DB 용량. 무료 0.5GB를 넘기지 않는다.
6. **권한:** 공개 DB·Vercel 변경 권한이 Codex 환경에 없으면 단계 1~2의 준비물과 검증 결과까지만 만든다. 남은 실행 단계는 보고서에 순서대로 적어 Claude에게 넘긴다.
7. 결과는 `docs/work-orders/reports/OPS-02.md`에 남긴다.
   - 실행 커밋
   - 단계별 UTC 시각
   - revision 전후
   - 배치 성공·실패
   - runtime 실측 여부
   - 실연 수치
   - 용량

## CX-18. 전체 백업 세트 생성·별도 복원 (P0)

[DATA_AUTH.md](../architecture/DATA_AUTH.md)의 정지 지점 `backup_set_id` 설계를 구현·실행한다.

- **백업:** 같은 `backup_set_id`로 PostgreSQL dump, 설정, 시뮬레이터 SQLite, 게이트웨이 SQLite를 묶고 체크섬을 만든다.
- **복원:** 별도 경로·별도 DB에 복원한다.
- **대조:** 다음 항목을 manifest와 대조한다.
  - 실행·물품, 양품·불량·폐기 수량
  - 명령, 열린 알람
  - 연속 커서, 누락
- **복원 후 동작:** 세션 회전, `RECOVERY_REQUIRED`, 자동 START 없음을 확인한다.
- 공개 DB를 쓰지 않는다. 작은 SQLite reopen 시험으로 대신하지 않는다.
- 운영 문서에 백업·복원 명령과 소요 시간을 적는다.

## CX-19. 실제 30분 단절 후 회복 (P1)

CX-15 P1 그대로 진행한다.

- 48태그·1Hz 수집을 유지한 채 API 연결을 **실제로 30분** 끊는다.
- 30분/100MB 중 먼저 오는 한도를 지키는지 확인한다.
- 재연결 후 5분 안에 다음이 끝나는지 측정한다.
  - 적체 반영
  - 최신 상태 회복
  - 원래 사건·커서·누락 대조
- 100MB에 먼저 닿으면 그 사실과 누락을 보고한다. 한도를 조용히 늘리지 않는다.

## CX-20. 7일 이력 조회 성능 (P1)

- 기본 보관 규모를 준비한다. 7일 원시·집계, 9개 아날로그 × 604,800초.
- 태그 4개·24시간 질의를 동시 10명 부하로 측정한다. 목표는 p95 ≤ 3초다.
- p50/p95/max, 표본 수, cold/warm, 쿼리 계획, DB 크기를 기록한다.
- 공개 무료 DB와 공개 6시간/14일 프로필로 대체하지 않는다.
- 목표를 넘으면 원인을 분석해 개선한다. 결과 값은 바꾸지 않는다.

## CX-21. 8시간·10명 장시간 운전 (P1)

- 기본 100ms 공정, 48태그·1Hz 수집, 동시 10명 조회·화면 세션을 **실제 8시간** 유지한다.
- 다음 지연을 p50/p95/max와 표본 수로 측정한다.
  - PLC 변화 → 화면: 목표 p95 ≤ 2초
  - 알람 조건 충족 → 표시: 목표 p95 ≤ 3초
- 다음 추세를 기록한다: 누락·중복, CPU/RAM, DB·큐·WAL 크기.
- 판정 기준은 실행 전에 보고서에 고정한다.
- 실행 전에 하드웨어 사양을 기록한다(4코어·8GB·SSD 이상 조건). 시작 시각을 사용자에게 알린다. 가속 시계나 짧은 운전으로 대체하지 않는다.

## CX-22. clean build 재현과 릴리스 manifest (P2)

- 깨끗한 체크아웃에서 이미지 빌드부터 다시 한다. 과거 ENOSPC 원인을 정리하고 다음을 확인한다.
  - Compose 전체/독립 실행
  - 데이터 보존 재시작
  - CX-17 수락 묶음
- 운영 안내의 각 명령을 일회성 환경에서 실제로 실행해 확인한다.
- 대상 SHA, 이미지 digest, 실행 결과를 담은 릴리스 manifest를 만든다.
