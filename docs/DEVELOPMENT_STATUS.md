## 운영 원칙

주 에이전트가 의존성과 통합 검증을 조정한다. 서브에이전트는 `gpt-6.1-sol` medium을 기본으로 사용하며, high는 DB 마이그레이션·데이터 격리 등 위험도가 높은 검토에만 사용한다. DEV 항목을 작은 작업으로 나누고 각 결과를 확인한 뒤 후속 작업을 배정한다. 아래 작은 작업의 통과는 상위 DEV나 전체 프로젝트의 완료를 의미하지 않는다.

## 현재 작업

M1의 독립 운전·원본 보관 보호·지속 온도 편차와 M2의 실제 OPC UA→게이트웨이→PostgreSQL 수집·명령·최종 정산 경로를 구현하고 집중 검증했다. M3는 인증·WebSocket 조회·제어 화면, 아날로그 알람 수집·저장·확인/메모와 실제 브라우저를 검증했다. M4는 작업지시 등록·배포·원자적 실행 연결·원래 결과 복구 화면과 수동 실행 조회 API를 검증했다.

최신 전체 로컬 검사는 `0014` 기준 **Python 1,913개 통과(1,060.63초), 웹 65개 통과, 정적 검사·형식 229개 파일·타입 검사·린트·빌드 통과**로 정상 종료했다. 혼합 알람 실행기/실제 고장 파이프라인·ID query 경로·Line 알람 화면·필드 DELAY V3 통합을 포함한다. 기존 WebSocket 의존성 deprecation 경고 2개가 있으며 실패는 없다. 추가 트렌드 T1과 OPC 차단 O1 초안은 포함하지 않는다.

정산된 실행의 기록 보관/다음 작업 준비 화면, PLC 고장 알람 판정·저장, 미연결 작업 취소 API와 필드 관측 주입 첫 단위를 집중·전체 회귀 검증했다. 신규 DB 이관의 독립 high 검토도 통과했다. 현재 취소 화면의 실제 브라우저 검증을 마쳤고, 명확한 취소 거절 후 명시적 새 준비 절차도 검증했다. 혼합 고장 알람 수집과 유효한 ID의 URL 왕복 결함은 수정·독립 검토·전체 회귀를 통과했다. Line 알람 화면은 실제 CLI/PG/Chromium 검증을 통과했고, 필드 DELAY V3는 선별 통합 후 353개 집중 시험을 통과했다. 이번 통합 변경의 전체 회귀를 통과했다. 추가 트렌드 T1·OPC 연결 차단 O1은 사용자 지시에 따라 보류하며 저장소에 통합하지 않았다. 필드 읽기 실패·채널 단절의 실제 결합 검증도 통과했다. 전체 T01~T12, 보고서·트렌드·보관, 성능·8시간 운전·백업/복원 등은 남아 있다. 세부 근거와 미완료 범위는 [수락 시험 대응표](ACCEPTANCE_EVIDENCE.md)에 기록한다.

## 검증 기록

### 첫 통합 검증

- `./scripts/bootstrap-python.sh`: uv.lock 기반 설치 통과.
- `./scripts/bootstrap-web.sh`: package-lock.json 기반 npm ci 통과.
- `./scripts/check-local.sh`: Python Ruff 검사·형식 검사, **92개 시험 통과**, 웹 TypeScript·ESLint·Vite 빌드 통과.
- 시험 구성: 프로토콜 73개 + 태그 9개 + 실제 OPC UA 호환성 10개. 태그 시험의 하위 검증 156개는 별도로 156개 테스트 함수라고 계산하지 않는다.
- `scripts/probe-postgres.py`: PostgreSQL 17.11 임시 컨테이너의 인증된 TCP 연결, UInt64 정밀도·범위 제약, 고유 제약, 트랜잭션 롤백 확인. 컨테이너·볼륨·임시 비밀번호 파일은 회수했다. 업무 DB 마이그레이션 시험과 구분한다.

독립 검토에서 날짜의 숫자 변환, 불리언 자동 변환, UInt64 스키마 경계, 음수 0의 명령 동일성, 모순된 명령 결과 상태를 발견해 회귀 시험과 함께 수정했다.

OPC PoC의 `SubmitCommand`는 `POC_ONLY`로 거절하고 조회는 계약 예제 fixture를 반환한다. 성공 결과 예제와 종료 요약 예제는 실제 운전 결과가 아니다. 인증서는 검증하지만 운영 사용자·역할 인증과 PLC 실행·영속성은 후속 작업이다. 시험 결과를 T01~T12 통과로 옮겨 적지 않는다.

### 두 번째 통합 검증

- `./scripts/check-local.sh`: Ruff 검사·형식 검사, **251개 시험 통과(13.49초)**, 웹 TypeScript·ESLint·Vite 빌드 통과.
- 구성: 프로토콜 73개 + 태그 9개 + 내부 전송 51개 + 실제 PostgreSQL 25개 + 실제 OPC UA 10개 + 순수 공정 모델 43개 + SQLite 저장 40개.
- M0 기준 대조를 별도 에이전트가 수행했다. 고정 의존성·48개 태그·실제 메서드 자료형·인증서 거절·상태 전이·내부 전송·DB/인증 설계가 계획의 M0 범위를 충족한다. 인증 구현·업무 통합을 통과했다고 판단한 것은 아니다.
- 전송 계약 검토에서 과거 누락 배치의 재전송이 이미 복구된 구간을 다시 미해결로 만드는 문제를 수정했다. 배치 수신 이력과 현재 미해결 구간을 분리한다.
- 공정 모델은 소수 속도의 경계 이송 오차를 정확한 유리수 계산으로 수정했다. UInt64 소진·실제 경계 미달·JSON 복원 시험과 독립 재검토를 통과했다.
- SQLite는 공정 snapshot·수량·사건·순번의 원자적 저장과 커밋 직전/직후 `os._exit` 복구를 검증했다. 복구 전 손상 사건 조회, 비활성 실행의 잔여 WIP 누락, 파일 별칭의 소유권 잠금 우회 결함을 수정하고 독립 재현으로 확인했다.
- 저장 계층의 일관성 확인은 PLC의 재가동 승인이나 사용자 인증이 아니다. 실제 운전 상태·명령·알람 영속화, 7일 보관, 전체 백업·복원은 후속 범위다.

### M1 컴포넌트와 실제 운전 경로 검증

- 위 M1 컴포넌트별 시험 수는 해당 파일의 수집 항목과 대조했다. 이 문서 갱신에서는 `pytest --collect-only`만 실행했으며, 수집 성공을 시험 통과로 계산하지 않았다. 통과 기록은 실행을 확인한 개별 작업과 아래 실제 브라우저 결과에 근거하며 새 전체 suite 합계는 만들지 않는다. 기존 92개·251개 통합 기록은 당시 실행 이력이다.
- [PLC](architecture/PLC.md), [명령 원장](architecture/COMMAND_STORE.md), [제어기](architecture/SIMULATOR_CONTROLLER.md)를 결합해 접수와 실행 성공을 분리하고 원래 ID의 결과를 추적한다. 중복·내용 충돌·재시작 후 미정 명령을 구별하며 timeout이나 재시작으로 새 ID의 자동 실행·자동 START를 만들지 않는다.
- [SQLite 저장](architecture/SIMULATOR_STORAGE.md)의 저장·상태 사건·트랜잭션 targeted suite는 67개 통과 기록이 있다. 원래 실행의 물품·수량·생산/상태/고장 사건과 제어·명령 결과를 같은 저장 경계에서 다룬다. 커밋 직전/직후 실제 자식 프로세스 종료 증거는 저장·명령의 해당 경계에 한정하며 전체 T09나 전원 장애 시험을 대신하지 않는다.
- [인증](architecture/SIMULATOR_AUTH.md)과 [HTTP 콘솔](architecture/SIMULATOR_CONSOLE.md)은 계정·세션·초기 암호 변경·viewer 직접 조작 거절·Origin/CSRF·감사를 적용한다. LOCAL 제어도 PLC 안전 조건을 통과하며 앱 A 인증·MES 정산을 대신하지 않는다.
- [실제 OPC UA](architecture/SIMULATOR_OPCUA.md)는 인증서를 검증하는 암호화 TCP 세션으로 실제 48개 읽기 전용 태그·명령 원장·사건·최종 요약을 제공한다. 고정 성공 응답의 PoC와 구분한다. 실제 LOAD_JOB→START→생산→END_RUN·동일 ID/내용 충돌·미신뢰/평문 거절을 검증했다.
- `scripts/check-simulator-browser.py`는 Playwright/Chromium에서 실제 `apps.simulator serve` CLI subprocess·HTTP·OPC listener·공정 ticker를 실행해 통과했다. 화면 클릭으로 로그인·초기 암호 변경·다섯 항목 복구·LOCAL/AUTO·LOAD_JOB·실제 가상 예열·START 생산·PAUSE 정지·원래 START ID 재요청의 중복 방지·END_RUN 최종 수량·현장 대조·작업 B의 초기 수량 0 및 A 최종 요약 보존·로그아웃 후 401을 확인했다. 잡히지 않은 JavaScript 예외가 없고 서버도 정상 종료했다. 자세한 범위와 제한은 [콘솔 UI](architecture/SIMULATOR_CONSOLE_UI.md), 재현 절차는 [별도 실행](architecture/SIMULATOR_RUN.md)을 따른다.

M1의 주요 독립 운전·권한·실제 생산 경로는 확인했지만, 원본 사건의 7일 보관 정리·검증 checkpoint와 명령/알람을 포함한 전체 crash 복구·T09는 남아 있다. 브라우저의 현장 대조는 다음 로컬 작업 연결을 위한 확인이며 앱 A의 MES 정산 완료가 아니다.

### 실제 앱 A 화면·명령 원장·정산 기반

- 실제 Chromium + 일회용 PostgreSQL + 별도 API 실행기로 로그인·초기 암호 변경·재로그인·로그아웃을 확인했다. 등록된 출처·영속 관측을 API를 통해 읽고 UInt64 최댓값·Bad/null·미수신·관측 만료를 화면에서 검증했다. `scripts/check-app-a-browser.py`는 제어된 시험 배치를 실제 수집 서비스에 넣으며 이 브라우저 시험 자체를 OPC 통신 시험으로 표시하지 않는다.

- 명령 원장·일회성 전달 예약·원래 ID 결과 대조: **34개 실제 PostgreSQL 시험 통과(13.18초)**. 검토에서 발견한 잠금 순서 교착, 같은 라인의 다른 스트림을 통한 미정 명령 우회, ID 내용 충돌의 잘못된 확정을 수정했다. 충돌은 영속 latch로 보류하며 원래 ID 조회만으로 다른 내용의 성공을 가져오지 않는다.

- 원본 보관 v3 저장 계층은 archive/checkpoint·중복 방지·원래 source/stream/epoch 보존·보관 시각 불변성·이관/실제 중단 복구를 구현했다. 관련 **96개 시험 통과**, 독립 위험 검토의 당시 **92개 시험 통과**. controller 보호 조건 연결은 최종 경계 근거를 추가 검토 중이며 자동 보관 실행은 아직 없다.
- 순수 알람 생명주기는 네 상태·정확한 인스턴스 확인·재발·메모 변경·설정 변경 종료·불명/지연 근거 보존을 구현했다. 집중 **22개**, PLC/공정 결합 **106개 시험 통과**. 규칙 지속시간·DB·권한 API·화면을 구현한 것은 아니다.
- 설정 버전과 작성 중 작업지시 등록/조회: migration 0008과 감사, 역할·CSRF·동시 등록을 구현해 **59개 PostgreSQL·ASGI 시험 통과(38.65초)** 및 위험 검토를 확인했다. 실행 연결·취소·MES 전체 업무는 남아 있다.
- 변경되지 않은 Good 값의 오래된 SourceTimestamp를 통신 장애로 취급하지 않도록 제어 조건을 수정했다. 실제 시간 오차는 변하는 heartbeat와 미래 시각 근거로 판정한다. 명령 HTTP **32개 통과(30.67초)**, 실제 Chromium에서 하루 전 원본 시각을 가진 정상 고정값과 최신 heartbeat로 START 접수·응답 유실 재조회가 통과했다.
- WebSocket 전송은 원래 v1 계약의 SNAPSHOT/전체 UPDATE·순번·bounded queue·실시간 권한 재확인을 구현했다. 새 WS/auth와 기존 auth 결합 **65개 시험 통과(57.34초)**, 재접속 idle 연장 방지 후 실제 WS suite **22개 통과(27.52초)** 및 위험 검토를 확인했다. 기존 REST 화면·명령 폴링도 idle을 연장하지 않도록 수정해 두 회귀 시험이 통과했다. UI WebSocket 연결은 후속 범위다. `websockets==15.0.1`을 고정해 실제 소켓 시험의 런타임을 구성했다. 화면의 기존 REST 품질/수집 근거를 발행 시각으로 대체하지 않는다.

### 후속 작업 순서

1. [게이트웨이 수집 경로](architecture/M2_RUN.md)와 [앱 A 인증 실행 경로](architecture/API_RUN.md)를 기반으로 실제 상태 조회와 브라우저 인증 화면을 연결한다.
2. 인증·권한을 적용한 앱 A 명령 전달 원장과 원래 ID 결과 추적을 연결하고 응답 유실·재전송·재시작·잘못된 권한 거절을 검증한다.
3. 최소 실행 등록→START→생산 사건→END_RUN→수량/커서 대조 경로를 운영 API·DB까지 연결한다. 버퍼 한도·영구 누락·복구 보류와 M1의 남은 보관/복구 항목을 별도 추적한다.

각 작업의 실행 결과를 검토한 뒤 M2 단계 게이트를 판단한다. 운영 HMI·MES 업무, 전체 T01~T12·성능·8시간 운전·운영 백업/복원은 이후 단계의 완료 조건으로 남는다.

### 작업지시 배포·원자적 실행 연결

- migration `0009_work_order_binding`: 배포 요청 원래 ID/행 버전/인증 사용자와 불변 receipt, 실행·목표 계획·LOAD 명령·라인 예약·감사를 한 트랜잭션으로 연결했다. 재시도는 기존 receipt를 조회하며 새 실행 ID/시각을 만들지 않는다. 동일 라인의 관리형 예약은 별도 legacy LOAD/START 우회도 막고, 원래 명령의 읽기 전용 재조회와 PAUSE/END 안전 동작을 유지한다. 취소 API는 아직 없다.
- 작업지시/설정/실행계획/명령 집중 **140개 시험 통과(94.09초)**. 실제 OPC UA·HTTP·PostgreSQL pipeline **7개 통과(29.83초)**: 관리형 작업 A의 정확한 정산 전 B 연결 거절, 정산 후 예약 교체와 B LOAD 1회, A 최종 요약 보존을 포함한다. 미사용 migration 왕복/과거 원래 LOAD 재조회 회귀 **2개 통과(7.82초)**. 독립 high 위험 검토의 실제 PostgreSQL 시험 **10개 통과(16.77초)**.
- 기존 사용자 제어 HTTP 회귀에서 정지 조건 추가로 이전 READY fixture의 성공 기대 2개가 실패했다. 실제 PLC의 STOPPED 조건에 맞춰 세 LOAD fixture를 수정했다. counter_epoch 거절 시험도 STOPPED에서 해당 조건 자체를 검증하도록 유지했고, **35개 시험 통과(37.06초)**를 확인했다.
- 화면의 작업지시 목록/원래 ID 조회는 실제 DRAFT/RELEASED 배포 상태를 구별한다. RELEASED를 설비 실행 성공으로 표시하지 않는다. 배포/실행 연결 버튼은 후속 화면 작업이다.

### 수집 시각 근거와 알람 입력 정규화

- 수집 배치 1.2는 collector clock epoch·단조 시각·UTC 읽기 구간을 원래 본문과 함께 보존한다. 기존 1.0/1.1 정규 본문과 해시를 유지한다. 시계 역행/비유한 값은 이전 정상 근거를 폐기하며 이벤트 조회 지연이 수집 시각을 바꾸지 않는다. 해당 변경은 원본 시간 근거만 제공하며 UTC 동기화나 실제 알람 발생 완료를 주장하지 않는다.
- 같은 배치의 phase/측정값으로 알람 입력을 만드는 순수 adapter의 집중 **101개 시험 통과(0.45초)**. 누락된 실제값/설정값은 UNKNOWN으로 지속시간을 끊고 원래 근거·범위·규칙/시각 평가 hash를 보존한다. 이후 주 에이전트가 UTC 읽기 구간 폭을 지속시간에서 보수적으로 반영하는 추가 경계를 발견해 후속 수정·검증 중이다. DB/실제 수집 연결과 시각 평가 생성기는 후속이다.


### 최신 결합 검증 진행 및 알람 저장

- 화면 WS 연결의 실제 Chromium·PostgreSQL·API 검증이 통과했다. 단절/재접속·3초 무수신·순번 누락·권한 회수·REST 대체 조회 없음·원래 명령 추적·공정도 모바일 표시를 확인했다. 실제 OPC/PLC 시험을 대신하지 않는다. 이후 순수 화면/MES/명령 UInt64 회귀는 **13개 통과**했다.

- 최신 전체 검사 첫 실행은 기존 제어 HTTP fixture의 줄 길이 오류로 정적 검사에서 중단됐다. 해당 파일의 형식을 수정하고 전체 검사를 다시 실행 중이다. 시험 수를 이전 실행과 합산해 전체 통과로 표시하지 않는다.

### 실제 시나리오 대조에서 확인한 잔여 항목

- 기획서 별도 앱 조작 기능의 지속적인 온도 편차 주입은 보완이 필요하다. 현재 controller.tick이 공정 모델 온도로 입력값을 갱신하므로 일회성 PLC 입력 변경만으로 지속적인 센서 편차를 시험할 수 없다. 제어된 OPC 측정 fixture의 실제 통신 검증을 실제 공정 고장 주입 완료로 표시하지 않는다.

### 알람 실제 통신 연결과 실행 설정 검증

- 사용량 제한으로 일부 에이전트가 중단된 뒤 사용자의 계속 진행 지시에 따라 저장된 변경에서 재개했다. 현재 화면 결합 순수 시험 **29개·TypeScript·ESLint·빌드 통과**, 실제 브라우저 결합 검증과 설비 앱 온도 편차/저장 이관은 진행 중이다. 후속 변경은 이전 전체 검사 합계에 포함하지 않는다.


### 결합 브라우저와 실행 조회

- 작업지시·알람 결합 실제 Chromium/PostgreSQL/API 검증이 정상 종료했다. 배포/연결 커밋 후 응답 유실, 조회 404 보류, 화면·계정 전환 후 원래 요청자/ID 유지, 독립 LOAD 추적과 기존 명령 추적 보존, 알람 네 상태·정확한 과거 발생 건 확인·메모 변경·역할 제한을 확인했다. 브라우저 알람은 제어된 DB 판정 fixture이며 실제 OPC 경로는 앞의 별도 통합 시험이다.
- 실행 조회 API 집중 **26개 실제 PostgreSQL/HTTP 시험 통과(28.20초)**. 원래 LOAD 성공·실제 사건 적용·최종 요약 정산, 하나의 SQL 문장으로 일관된 조회, 원래 범위/역할·legacy 미등록·UInt64 정밀도·손상 근거 거절을 검증했다. 조회가 정산/제어/유휴 연장을 수행하지 않는다. 저장된 SETTLED는 다음 작업 접수 허가를 뜻하지 않으며 연결 API가 다시 검증한다.
- 온도 편차 저장 이관 검토에서 확인한 문제는 이전 센서 PV와 현재 물리 온도의 재시작 직후 불일치였다. 복구 STOPPED 제한 때문에 즉시 START 우회는 재현되지 않았다. 재시작 시 센서값 재계산으로 수정했으며 독립 high 검토의 **9개 SQLite 검사**에서 이관·손상 거절·rollback·과거 감사 보존·편차 단일 적용·시작 조건을 확인했다. 설비 콘솔 결합 시험은 진행 중이다.
