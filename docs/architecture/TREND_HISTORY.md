# 아날로그 트렌드 이력

## 19차 현행 기준 (2026-10-26)

19차 사용자 승인으로 수집 원본 보관은 `HMI_INGEST_RETENTION_HOURS` 기본 168시간·최소 3시간을 사용한다. 3 미만·비숫자는 시작을 거절하고, 구 설정 `HMI_INGEST_RETENTION_DAYS`는 단독·동시·빈 값 모두 거절한다. 현재 runtime 자동 정리는 schema 0023에서만 실행하며 schema 0022의 보관 종료 조회·재전송 거절은 호환 지원한다. 아래 18차/CX-40의 일 단위·영구 개별 영수증 설명은 당시 이력이며 이 현행 기준으로 대체된다. 변경 이유와 영향은 [INGEST_RETENTION.md](INGEST_RETENTION.md)를 따른다.

schema 0023에서는 개별 영수증과 압축 범위의 epoch별 `clock_frontiers` 양 끝 좌표를 함께 사용해 인접 순서를 확인한다. 압축 전 영속화한 `analog_history_clock_state.reversal_seq`를 병합하므로 양 끝만 정상인 내부 역행을 GOOD으로 되돌리지 않는다. 최신 clock-context는 범위의 `latest_capture`와 개별 영수증을 원래 capture 순서로 비교한다. 만료된 digital-only capture의 순서 근거도 유지한다.

수집 원본 압축은 트렌드 원시/분 보관 설정과 별개다. 기존 유효 분 집계와 보수적 `RETENTION_EXPIRED`/TIME_UNKNOWN 규칙을 유지하며, endpoint만으로 지워진 표본을 재계산하지 않는다. 실제 FK 참조 영수증은 남고 매 capture 알람 FK 때문에 사건 비례 상한은 성립하지 않는다. 사용자의 **기존 참조 보존·한계 보고** 결정과 정확 ID 청크의 O(captures) 바이트 증가를 반영한다. 원본 6.5KB·1Hz·3시간 약 70MB는 추정이며 24시간 가속 적재·vacuum 전후 증분 실측은 대기 중이다. 무료 0.5GB 보장이 아니다.

CX-01은 9개 `analog_history` 태그를 배치 접수·중복 제거·커서와 같은 PostgreSQL 트랜잭션에 기록한다. `IngestionService`는 schema 14 이하에서 기존 수집을 유지하며, schema 15~23에서 새 저장 경로를 사용한다. 새 API는 `register_trend_routes(app, auth)`로 사용자 앱에 등록하며 read 권한과 `refresh_idle=False`를 사용한다.

## 저장과 시간 근거

`analog_history_raw`는 원래 sample·gateway·generation·capture sequence·clock epoch와 `ClockAssessment`를 보존한다. GOOD 시간은 명시적인 `ConfiguredClockPolicy`를 `IngestionService(trend_clock_policy=...)`로 전달한 경우에만 가능하다. 기존 `assess_capture_clock`의 범위·세대·epoch·유효 기간·±2초 검사를 재사용한다. 기본은 UNKNOWN이다. OPC GOOD, 수신 시각, source timestamp만으로 시간 품질을 GOOD으로 바꾸지 않는다. 미래 2초를 넘는 캡처도 TIME_UNKNOWN이다. 잘못된 시각의 값은 해당 시각 슬롯에 불명으로 표시하며 실제 발생 시각을 추측하지 않는다.

`analog_history_clock_state`는 epoch별 마지막 sequence/시각과 최초 역행 sequence를 보존한다. 아날로그 유무·원시 보관 범위와 무관하게 명시적인 capture clock이 있는 모든 캡처를 기록한다. 지연 캡처는 같은 generation/epoch 전후 캡처와 비교한다. schema22에서는 `ingest_receipts`를, schema23에서는 영수증과 압축 endpoint·영속 역행 registry를 함께 사용한다. 이전 스키마에서는 `ingest_batches`를 사용한다. UTC 역행뿐 아니라 sequence 증가에 따른 monotonic 좌표의 역행·동일값도 시간 불명으로 처리한다. 이 탐색은 기존 gateway/generation/sequence 고유 인덱스로 방향별 한 건을 반환하며, 원시 정리 뒤에도 digital-only 캡처의 근거가 사라지지 않는다. 역행이 확인되면 같은 epoch의 이후 보존 원시 표본을 UNKNOWN으로 바꾸고 분 집계를 재계산 대상으로 돌린다. registry가 없는 첫 캡처에서는 immutable 배치 이력을 SQL window LAG로 한 번 검사해 UTC/monotonic 최초 역행 sequence를 복원한다. 따라서 기존 schema14에서의 업그레이드와 downgrade→upgrade 후에도 이미 알려진 역행을 GOOD으로 초기화하지 않는다. 이 초기 재구성은 epoch의 전체 이력을 읽으므로 큰 이력에서는 첫 요청이 더 비쌀 수 있다. 이후에는 인접 캡처 탐색을 사용한다. epoch가 바뀔 때까지 자동으로 정상 복구하지 않는다. 이 작은 provenance registry는 원시 보관 종료 이후에도 남겨 역행 증거를 잃지 않는다. generation/epoch가 같은 분에 섞이면 그 분을 TIME_UNKNOWN으로 내보내며 서로 평균하지 않는다.

## 집계와 조회

새 배치가 완료된 UTC 분을 갱신한다. 요청당 최대 32개 tag/minute를 기존 `aggregate_minutes`, `POLICY_VERSION=utc-second-latest-capture-v1`로 계산해 `analog_history_minutes`에 upsert한다. 같은 배치의 재전송은 기존 ACK를 반환하므로 표본·집계를 중복 저장하지 않는다. 지연 배치가 과거 분을 다시 열면 해당 분의 전체 보존 표본으로 재계산한다. 수신 당시 진행 중인 분은 다음 수집에서 처리한다. 이후 수집이 없어도 조회는 원시 근거로 계산할 수 있다.

조회는 보존 집계를 우선 사용하고, 누락·재계산 대기·부분 경계 분만 인덱스 범위 탐색으로 원시값을 읽는다. 원시 일부가 삭제되어도 완성된 집계를 남은 원시 표본으로 덮지 않는다. 슬롯 선택·비GOOD 제외·평균은 기존 정책을 그대로 따른다. 모든 슬롯을 반환하며 값이 없으면 null/MISSING이다. minute의 expected_count는 60이고 부분 경계도 완전한 분처럼 GOOD으로 표시하지 않는다. 부분 경계는 요청 안의 표본만 계산하므로, 원시 보관 이후에 분의 일부를 조회하면 원시 근거가 없는 부분은 MISSING이다.

태그 1~4개, second 최대 1시간, minute 최대 7일이다. auto는 1시간 이하를 second로 선택한다. 알 수 없는 키·중복 스칼라·중복 tag·잘못된 scope·해상도·시각은 422다. UTC 분/초에 정렬되지 않은 최대 길이 요청이 점 수 제한을 넘으면 422다(예: 비정렬 7일은 10,081분과 겹친다). UTC ISO8601 Z 시각을 반환한다.

## 보관과 용량

기본 `TrendRetention()`은 원시 7일, 분 집계 90일, 테이블별 요청당 삭제 최대 1,000건이다. 원시 삭제 경계는 완료된 분 경계로 내린다. 아직 집계하지 않은 정상 과거 표본을 먼저 삭제하지 않는다. 미래 시각 표본도 수신 시각을 기준으로 만료되므로 잘못된 미래 시각으로 무한 보존되지 않는다. `FOR UPDATE SKIP LOCKED`와 제한된 삭제를 사용한다. 트렌드 정리는 `ingest_batches`, 기존 알람 결정·생산·인증 테이블을 삭제하지 않는다. schema22의 별도 수집 원본 정리는 아래 승인된 정책을 따른다.

로컬/배포 프로필에서 `IngestionService(trend_retention=TrendRetention(raw_days=1))`을 명시하면 원시 24시간을 선택할 수 있다. 기본값을 변경하지 않는다. Neon Free 같은 0.5GB 환경에서는 기본 7일 원시 보관을 수용한다고 가정하면 안 된다. 9태그×86,400초×7일=5,443,200행, JSONB 근거·인덱스 포함 행당 약 0.8~1.5KB를 가정하면 원시는 약 4.4~8.2GB다. 24시간도 777,600행으로 약 0.62~1.17GB이며 0.5GB를 넘을 수 있다. 원시 6시간(`raw_days=0.25`)은 약 0.16~0.29GB다. 90일 분 집계 1,166,400행도 행당 약 0.4~0.7KB 가정 시 약 0.47~0.82GB여서 별도 프로필·용량 증설 판단이 필요하다. 이는 추정치이며 실제 최대 규모 측정 결과가 아니다. minute_days도 배포 프로필에서만 줄일 수 있다.

공개 서버리스 배포(Vercel)는 환경변수로 이 프로필을 고른다(CX-12, 2026-10-23).
- `HMI_TREND_RAW_HOURS`: 1~168 정수(시간)
- `HMI_TREND_MINUTE_DAYS`: 1~90 정수(일)

둘 다 없으면 기준값(원시 7일, 분 90일)이다. 하나만 주면 다른 하나는 기준값을 쓴다. 소수, 앞자리 0, 공백, 범위 밖 값은 구성 오류로 앱 생성을 거절한다. 기준값을 바꾸지 않고 배포 프로필에서만 줄인다. 줄이는 이유는 Neon Free 0.5GB 용량이다.

공개 배포 권장값은 원시 6시간·분 14일이다. 위와 같은 가정이면 원시 약 0.16~0.29GB, 분 집계(9태그×1,440분×14일=181,440행) 약 0.07~0.13GB다. 영향은 다음과 같다.
- 6시간보다 오래된 구간은 초 단위 트렌드와 원시 기반 재계산을 할 수 없다.
- 14일보다 오래된 분 트렌드는 MISSING이다.
- SPC는 원시가 남은 범위만 계산하므로 초기 부분군 증명이 더 일찍 `ORIGINAL_PREFIX_RAW_UNAVAILABLE`이 된다.

트렌드 보관 설정 자체는 원본 `ingest_batches`를 줄이지 않는다. 18차 이전에는 원본 배치를 무기한 보존했다. schema22의 별도 수집 원본 보관 정책은 아래와 같으며, 미정산 원본과 영구 메타데이터 증가까지 DB 전체 용량이 제한된다는 보장은 아니다. 2026-10-23 공개 DB 실측(스키마 0014, 약 1시간 수집)에서 원본 배치는 3,814건·22MB(건당 약 6KB)였다. 1초 주기면 시간당 약 22MB, 하루 약 0.5GB다. 공개 배포는 짧은 시연용 수집만 전제로 한다. 사용량은 이관 보고(OPS-01)에 기록한다.

원시 보관 경계보다 오래된 지연 배치는 새 트렌드 표본으로 보존하지 않는다. 이미 지워진 원시 근거를 복원할 수 없으므로 과거 분을 남은 일부 값으로 재계산하지 않는다. 생산 사건 수집과 원래 ACK·알람 보존은 그대로 처리된다. 처리 한도보다 많은 과거 재계산·정리 적체는 여러 수집 요청에 걸쳐 해소된다. 시계 역행의 최초 무효화는 정확성을 위해 해당 epoch의 보존 원시 근거를 갱신하므로 큰 이력에서는 일반 수집보다 비쌀 수 있다. 최대 7일·9태그 규모 p95 성능 측정은 별도 운영 검증이다.

## CX-12 서버리스 배포 보관 프로필

Vercel 수집 앱은 다음 환경변수를 선택적으로 읽고 검증한 `TrendRetention`을 실제 내부 수집 `IngestionService`에 전달한다. 두 값이 없으면 기존 기본 원시 **7일(168시간)**·분 집계 **90일**을 그대로 사용한다. 하나만 지정하면 다른 값은 기본값이다.

| 환경변수 | 허용 범위 | 생략 시 |
|---|---|---|
| `HMI_TREND_RAW_HOURS` | 정수 문자열, `1 <= hours <= 168` | 168시간 |
| `HMI_TREND_MINUTE_DAYS` | 정수 문자열, `1 <= days <= 90` | 90일 |

v2 통합은 이미 공개 main에 반영된 정수 문자열 규칙을 유지한다. 소수·과학 표기·앞자리0·공백을 허용하지 않는다. 이전 backend 구현의 유한 소수 허용안은 이 통합의 환경변수 계약으로 채택하지 않았다. 원시 시간은 24로 나눠 기존 `raw_days`로 전달하며 실제 정리는 완료된 UTC 분 경계를 따른다. 빈 값·0·음수·상한 초과·NaN·Infinity·JSON boolean/object/array·숫자가 아닌 값은 앱 구성 오류다. 값이나 비밀 설정을 예외에 반영하지 않는다. 잘못된 설정을 기본값으로 조용히 대체하지 않는다. 설정은 실행 환경에서만 적용하며 앱 코드가 공개 환경변수를 설정하지 않는다. 프로그램 내부 `TrendRetention(raw_days=...)` 설정의 숫자 형식과 환경변수 계약은 별개다.

무료 DB 용량을 검토할 때 권장 출발 프로필은 원시 **6시간**·분 집계 **14일**이다. 다음은 운영자가 별도로 검토할 설정 예시이며 이번 작업에서 공개 환경에 적용하지 않았다.

```text
HMI_TREND_RAW_HOURS=6
HMI_TREND_MINUTE_DAYS=14
```

9태그가 매초 빠짐없이 기록된다는 가정에서 6시간 원시는 194,400행이다. 앞 절의 행·인덱스 포함 가정 0.8~1.5KB를 사용하면 약 **0.16~0.29GB**다. 14일 분 집계는 181,440행이며 0.4~0.7KB 가정에서 약 **0.07~0.13GB**다. 새 원시+분 테이블 합계는 약 **0.23~0.42GB**의 거친 추정이다. 실제 저장 크기를 측정한 결과나 Neon 0.5GB 수용 보장이 아니다.

이 합계는 기존 `ingest_batches`·알람 결정/FK/감사·생산 사건·인증·정지 사유·clock registry 등의 증가, 테이블/인덱스 여유 공간과 bloat, 정리 적체를 포함하지 않는다. 특히 기존 불변 배치와 알람은 이 프로필로 삭제하지 않으므로 DB 전체는 계속 커질 수 있다. 운영자는 전체 DB 크기와 증가율을 측정하고 추가 보관 정책이나 용량 증설을 별도로 판단해야 한다.

이 프로필은 기준 보관 수치를 바꾸지 않고 배포 환경의 용량을 위해서만 줄인다. 적용 시 6시간보다 오래된 원시 초 단위 근거는 조회할 수 없고, 분 집계는 14일 뒤 사라진다. 기존 조회 API의 second 최대 1시간·minute 최대 7일 요청 범위는 그대로다. 삭제 건수 상한·미집계 보호·서버리스 요청 내 정리 정책도 그대로 적용하므로 큰 적체는 즉시 사라지지 않는다. 시간 근거가 없으면 보관 프로필과 무관하게 `TIME_UNKNOWN`을 유지한다.

## CX-14 공개 짧은 시연과 DB 전체 용량

[PUBLIC_DEMO_RUN.md](PUBLIC_DEMO_RUN.md)는 OPS-01 이후 공개 head17·원시 6시간/분 14일의 운영 기준으로 Linux/Windows WSL2 PC에서 기존 연속 runtime만 짧게 연결하는 절차를 제공한다. 기존 supervisor와 GNU timeout으로 300초(295초+종료 여유 5초) 또는 600초에 한정하고 1Hz 기본 수집을 유지한다. 새 빈 queue를 기존 공개 scope로 초기화하거나 기존 원본·알람·proof를 지워 용량을 맞추지 않는다.

원본 6KB/배치 가정에서 300초·600초는 약 1.8MB·3.6MB이고, 하루는 518.4MB다. 원본 외 9태그 raw/분 행의 기존 크기 가정을 더한 부분 합은 약 4.0~5.9MB·8.0~11.8MB다. 여기에 알람·생산·감사·기존 backlog와 head18 시각 proof/nonce metadata, 인덱스/TOAST/bloat와 정리 적체가 추가된다. 새 schema의 전체 행 크기를 공개 DB에서 재측정한 결과가 아니며 0.5GB 한도를 보장하지 않는다.

권장 운영 시작 기준은 500MB를 계획 한도로 볼 때 기존 DB 350MB 이하·1회 25MB 계획 여유·종료 후 최소 100MB 미사용 여유다. 실제 플랫폼 한도와 수집 전/후 관측 증가량으로 운영자가 판단한다. 예산이 부족하거나 backlog가 검토되지 않았으면 수집을 시작하지 않는다. `HMI_DATABASE_DSN`이 이미 안전하게 주입된 운영자 셸에서 `python scripts/check-db-capacity.py`로 READ ONLY metadata snapshot을 읽을 수 있다. 이는 물리 크기·통계 추정이며 원본 삭제나 업무 행 조회를 수행하지 않는다.

1Hz보다 느린 수집을 무료 용량 대책으로 임의 제시하지 않는다. 특히 2초 초과 주기는 freshness/heartbeat·제어와 시간 구간의 UNKNOWN 증가에 영향을 준다. 압축 archive는 구현된 보관 보장이 아니다. 수집 원본 보관 변경은 아래 18차 사용자 승인에 따라 별도로 구현한다.

## CX-40 수집 원본 보관 종료와 트렌드 근거 (18차 이력)

2026-10-25 사용자 결정과 18차 작업지시서에 따라 무료 DB의 무기한 원본 증가를 줄인다.
공개 트렌드 원시 보관은 Claude가 1시간으로 변경했으며, 이는 수집 원본 정리와 별도다.
schema22는 기본 7일이 지난 정산 완료·관측 전용 수집 원본과 해당 시각 증거를
안전 조건을 만족할 때 정리한다. 분 집계는 이 정리로 삭제하지 않는다.
영구 `ingest_receipts`와 보관 종료 범위는 남지만 원본 본문·ACK·전체 시각 proof를
대체하지 않는다. 오래된 실행을 원본으로 다시 검증할 수 없다는 영향이 있다.

트렌드 응답은 보관 종료 범위를 `retention_expired`에 반환한다. 겹치는 태그·점에는
`raw_evidence.availability`와 `reason_code`가 `RETENTION_EXPIRED`인 근거를 붙인다.
유효한 보존 분 집계의 값·품질·개수는 유지한다. 값이 없는 해당 점의 품질은
`RETENTION_EXPIRED`이며 일반 `MISSING`으로 바꾸지 않는다. 보관 종료가 없으면
기존 응답 필드를 유지한다.

범위는 삭제 전 기록한 보수적 시간 포락선이며 개별 삭제 표본의 정확한 구간이 아니다.
알려진 시각은 analytical UTC 포락선과 마지막 표본의 1초 슬롯을 사용한다.
원래 UTC·저장 시각 포락선도 메타데이터로 남기지만 analytical UTC를 대신하지 않는다.
시각 불명·analytical 경계 부재이면 요청한 같은 scope 전체에 보수적으로 표시하며,
`raw_evidence.coverage_basis=CONSERVATIVE_ENVELOPE`로 명시한다.
영구 clock registry의 후발 역행이 해당 보관 종료 범위에 닿으면 조회 시
`time_unknown`으로 승격한다. 삭제된 표본의 정밀 재계산이 불가능한 역행은 해당
source/stream의 보존 분 집계와 재계산 입력을 보수적으로 불명 처리한다.
이는 일반 보관 종료에서 유효한 분 집계를 유지하는 규칙과 별개의 시각 무효화다.
